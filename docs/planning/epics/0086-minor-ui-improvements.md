# 0086: Minor UI improvements

## Status
Done — all five items implemented (2026-08-30). Not yet live-tested (Electron renderer). Ready to move to `completed/` once the user confirms.

## Goal
Grab-bag epic for small, low-effort UI/UX improvements that come up during regular use — each individually too small to justify its own epic, collected here and picked off as convenient.

## Tasks
- [x] Remember property panel section collapse state per session — closing e.g. "Transform" on one shape now stays closed when selecting a different shape/edge/container, for the rest of the app session (no persistence to disk). `CollapsibleSection` (`src/renderer/src/panels/fields.tsx`) now reads/writes a module-level `Map<string, boolean>` (`sectionOpenState`) instead of pure local `useState`, keyed by a new `sectionKey` prop that defaults to `title`. The four callers whose title is dynamic pass an explicit stable key instead: `RequiredTagsPanel.tsx`'s "Allowed values (n)" keys per-tag (`` `allowedValues-${tag.key}` ``, since collapsing one tag's list shouldn't affect another's); `StylePalettePanel.tsx`'s "Colors"/"Fonts" get plain constant keys (singleton sections); `PropertyPanel.tsx`'s multi-select type-group headers key per type (`` `group-${type}` ``/`"group-edges"`). Every other caller's static title already doubles as a stable key, so — deliberately — the same section (e.g. "Fill") shares its remembered state across every element type it appears on, matching what the user actually asked for.
- [x] `step`/`smoothstep` routing styles offered no way to drag a segment into position — only `catmullRom` supported manual points. Reported live: the user wants to pull a step/smoothstep edge's segments into position, citing React Flow's Pro "Editable Edge" example. **Checked (2026-08-24)**: that example is Pro-only and is a bespoke custom edge — draggable control points are not a `getSmoothStepPath` built-in — so this needed its own orthogonal-routing algorithm, parallel to the catmull-rom work. **Done (2026-08-30)** — see [ADR 0077](../../decisions/0077-orthogonal-edge-segment-dragging.md). New self-contained `geometry/orthogonalPath.ts` (zero dependency on `bendablePath.ts`, so it can't regress catmull-rom, per the user's explicit constraint). `DiagramEdge.points` reused as orthogonal waypoints under `step`/`smoothstep` (gravity unused). `LabeledEdge.tsx` renders these via the new module instead of `getSmoothStepPath`; a new, separately-gated block draws a drag handle at each **interior** segment's midpoint (both ends bend vertices, never source/target). Dragging moves the whole segment along its normal, corners stay 90°, redundant corners auto-drop on release. **v1 scope line: endpoint-adjacent segments are not draggable** (stub synthesis is where the fiddliness/risk is — the user pre-approved deferring it). The common case (mid crossbar between facing shapes) is interior, so it works; an L-shaped edge needs a waypoint added first. "Add point here" on a step/smoothstep edge now inserts an orthogonal waypoint instead of converting to catmull-rom. `typecheck`/`lint` clean (0 errors). Not live-tested (Electron renderer).

- [x] The icon picker's scrollbar partially covers the rightmost column of icons. **First attempt (`scrollbar-gutter: stable` alone) turned out not to fix it — reported still broken by the user.** Re-investigated by actually reproducing it: built a standalone HTML repro of the exact markup/CSS, served through the Vite dev server (not a static `file://` open, which gets sandboxed with a script-blocking CSP) so real layout/JS could run, and measured the DOM directly. **Real root cause**: `.icon-picker-grid button` never had `min-width: 0` — a CSS Grid item's default `min-width: auto` factors in its content's own intrinsic size, and each button holds a raw `<svg>` with a baked-in size (Tabler icon markup), so the 6 columns refused to shrink to fit the picker's fixed 220px width (`IconPicker.tsx`'s `PICKER_WIDTH`) regardless of the existing `width: 100%` on the svg/img. That forced genuine horizontal overflow, and since only `overflow-y` was set, the CSS Overflow spec auto-computes `overflow-x` to `auto` too — producing the unwanted bottom scrollbar, and the "overlap" was really the rightmost column being cut off/scrolled past, not just visually covered. Fixed: `min-width: 0` on `.icon-picker-grid button` (lets columns actually shrink) plus explicit `overflow-x: hidden` on `.icon-picker-scroll` (removes the now-unnecessary horizontal scrollbar entirely, per the user's own follow-up ask). Verified, not just reasoned about: measured `scrollWidth`/`clientWidth`/button bounding rects before and after in a live browser tab — confirmed the original CSS overflows (6th button's right edge 3px past the container's own edge) and the fix doesn't (comfortably inside). `scrollbar-gutter: stable` from the first attempt is kept (still correct for the vertical scrollbar itself, just wasn't the actual bug).
- [x] Icon picker's search box only ever filtered built-in icons, never a diagram's own uploaded custom icons — found live right after testing the scrollbar fix above. `IconPicker.tsx`'s `customIcons` list was rendered unfiltered regardless of `query`. Fixed with a `filteredCustomIcons` memo using the exact same substring-on-lowercased-query convention `searchBuiltinIconIds` (`builtinIcons.ts`) already uses, matching on the icon's relative path (which includes its filename) — the "This diagram's custom icons" section/label now also disappears when nothing matches, same as it already did when there are zero custom icons at all.
- [x] Allow zooming out further than today's limit — and make it a real Setting, not a hardcoded value. Confirmed this app never set `minZoom`/`maxZoom` on `<ReactFlow>` at all — the `0.5`/`2` limits were purely React Flow's own unconfigured library defaults. Went through two rounds of user feedback: first pass hardcoded `minZoom={0.1}`, then made it a proper Setting (two new `AppSettings` fields, `src/shared/settings.ts`, defaults `0.1`/`2`), initially as two separate full-width `NumberField` rows — then the user asked for one compact row instead (`"Zoom limit: in [0.1] out[2.0]"`). Final shape: `ZoomLimitField` (new local component, `SettingsPanel.tsx`) — one `FieldRow` holding two small inline number inputs (own minimal draft-until-blur state, not `fields.tsx`'s `useDraft` since it isn't exported and this file's `react-refresh/only-export-components` rule means it should stay component-only). `Canvas.tsx`'s `<ReactFlow>` reads both from `settings`. No migration needed — `readAppSettings` already merges any missing field onto `DEFAULT_SETTINGS` for old settings files.
