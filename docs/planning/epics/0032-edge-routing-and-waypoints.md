# 0032: Edge routing style and manual bend points

## Status
Done (2026-08-24) — implemented, `typecheck`/`lint` clean (same 4 pre-existing lint errors as baseline). Not yet live-tested by the user.

## Goal
Let an edge be routed differently than today's one hardcoded bezier curve: React Flow's own built-in straight/step/smoothstep path shapes, or a catmull-rom curve (reusing epic 0064's freeform-line math) with manually-placed bend points — a way to steer an edge around something it would otherwise cross straight through, the original ask this epic opened with. A per-edge `style.routingStyle` field, plus an app-wide default setting for what a newly-created edge starts with.

## Decided
**No schema unification with `'line'` nodes.** See Notes below for the full account — a real, multi-round attempt to unify edges and decorative lines into one connector type (bound-or-free endpoints) was built, live-tested, found to still read as a disguised placeholder-node system no matter how it was restyled, and discarded entirely. `'line'` stays exactly what it already was (its own `DiagramNode` type, epic 0064/ADR 0050), completely untouched by this epic. What *is* shared: the curve math (`bendablePath.ts`) and the point-editing interaction (right-click add, drag, gravity-preset menu, remove) — both epic 0064's own building blocks, now used by an ordinary edge too, not just a line.

**`EdgeStyle.routingStyle?: 'straight' | 'step' | 'smoothstep' | 'catmullRom'`**, absent means today's only historical behavior (a plain bezier, still the default). The first three are React Flow's own built-in path functions (`getStraightPath`/`getSmoothStepPath`), wired straight through with no custom math. `'catmullRom'` builds the path via `bendablePath.ts`, extended (`PathPoint`'s new optional `direction`) so each of the edge's two real endpoints gets a fixed outward-direction tangent (leaves its shape's side perpendicular) while any interior bend point uses the existing neighbor/gravity tangent — the same distinction a discarded design (see Notes) needed for bound-vs-free endpoints, reused here for bound-endpoint-vs-interior-point instead.

**`DiagramEdge.points?: LinePoint[]`**, absolute canvas coordinates, only meaningful under `'catmullRom'` routing — purely additive to the schema, no version bump (unlike the discarded design, nothing about `source`/`target`'s own meaning changes this time).

**Right-click "Add point here" on any edge auto-switches it to catmull-rom routing.** No prior trip to the property panel to change the routing dropdown first — matches the original ask (route an edge around an obstacle) as a single, direct gesture. Once in catmull-rom mode, a point's own right-click menu offers the diagram's gravity presets (same catalog/menu `'line'` points already use) plus Remove.

**Settings gains a "Default edge routing" field** (`SettingsPanel.tsx`, writing to `settings.defaultEdgeStyle.routingStyle`), same "seeds new edges, each edge can still override its own" pattern every other default-style field in this app already follows.

## Notes

**2026-08-23/24: a full edge/line unification was built, live-tested twice, and discarded.** The original plan (see this file's git history and [ADR 0057](../../decisions/0057-edge-line-unification.md), both now only reachable via `origin/epic/0032-edge-line-unification` — the branch was deleted locally after being pushed for safekeeping, never merged) was more ambitious: `DiagramEdge.source`/`target` as a bound-or-free union, `'anchor'` and `'line'` both retiring into it, a synthetic React Flow node standing in for any free endpoint. Two live-testing rounds with the user found real problems, not just bugs:

1. First pass: a free endpoint rendered as a permanently-visible, unselectable, undeletable dot with no edge attached at all — traced to React Flow requiring a real `<Handle>` to resolve an edge's own coordinates, which then forced a fixed "direction" onto the free endpoint that fed into the curve shape.
2. Second pass, after fixing that: still, in the user's own words, "just an anchor" — restyling the dot and fixing the curve math didn't change the fact that a free endpoint was structurally a disguised placeholder node. Independent research (the user's own, checking React Flow's official "Temporary Edges" example) confirmed this wasn't a bug in the implementation: React Flow's own recommended pattern for an edge with a loose end (`useIncompleteEdge`/`GhostNode`) is structurally identical — a real node standing in for the free end is inherent to how React Flow's edge system works, not something a better implementation could avoid.

The only way to avoid a stand-in node entirely would have meant abandoning React Flow's native `<Edge>` for anything with a free endpoint — a fully custom-rendered overlay (own selection, own drag, own undo integration, own delete handling) reusing only the point-handle pattern already built for bend points. The user's call, given that cost: "if it becomes such a big codebase to maintain, then using RF loses its meaning." Branch discarded, this epic re-scoped to the much smaller, still-useful piece that was actually salvageable — routing style choice and manual bend points on an ordinary, always-bound-to-bound edge, where no free-endpoint problem exists at all. The curve math and point-editing UI from the discarded attempt were pulled back in almost verbatim (`git show` against the pushed-but-locally-deleted branch, not retyped) once the scope no longer needed the free-endpoint machinery around them.

**History before that, for context on the original scope:** opened during epic 0014 testing (2026-08-19) as "route an edge around an obstacle it crosses." Stayed unscoped through several rounds of related-but-distinct ideas logged against it (epic 0047's forced straight lead-in segment, still separate and untouched by this epic; epic 0044's possible shared "transform mode" trigger, never picked up). Epic 0064 (2026-08-22) built the freeform line and its curve math as their own thing, deliberately without unifying, specifically so this math would be reusable "if edges ever gained the same capability later" — see [ADR 0050](../../decisions/0050-freeform-line-as-node-type.md). That reuse is exactly what this epic ended up delivering, just not by the route originally planned.
