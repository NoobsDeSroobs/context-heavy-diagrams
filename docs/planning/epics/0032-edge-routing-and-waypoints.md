# 0032: Edge routing and waypoints

## Status
Not Started — not yet scoped, needs a real design conversation before implementing

## Goal
A way to control how an edge routes between its two ends, so it can be steered around other shapes/containers it would otherwise cross straight through. Raised during epic 0014 (drag-edge-to-create-shape) testing — unrelated to that epic's own scope (creating a new shape from a drag), just surfaced by the same session of poking at edges.

Currently every edge is a single path computed straight from source handle to target handle (`LabeledEdge.tsx`) — no way to add a bend, and no way to avoid overlapping a node that happens to sit between two connected shapes.

## Open questions (not resolved here)
- **Interaction model.** The user's own leaning going in: mid-edge points the edge is forced to pass through, with "vector controls" (i.e. draggable waypoint handles on the edge itself, maybe with direction/tangent handles too, not just a plain point) — closer to a vector-path-editing feel than, say, orthogonal auto-routing. Worth comparing against how other diagramming tools (Visio, draw.io, Miro) handle this before settling on a specific interaction, since "waypoints with vector controls" could mean several different things in practice (plain draggable points that just bend a straight/curved line through them, vs. full Bezier handles per point).
  - **Refined 2026-08-20, still not decided**: leaning away from a hard pass-through point and toward an *invisible bias offset* instead — think Bezier control points, not points the path is forced to touch. Dragging the middle of an edge would pull/bias the curve toward the drag without the edge being forced through that exact spot. The user flagged their own uncertainty here: this framing assumes curved (Bezier) edges, which is what `getBezierPath` already renders today — but if edges ever gained a right-angled/orthogonal routing style (a real alternative some diagramming tools default to), a bias-offset control wouldn't obviously translate to that rendering model at all. Whichever interaction model this epic lands on needs to either commit to Bezier-only routing or answer this before building bias controls.
- **Manual placement vs. auto-avoidance.** Does the user place waypoints by hand only, or does the tool ever suggest/auto-route around an obstacle? The framing above ("route them around other objects") suggests manual control is the actual ask, not automatic obstacle avoidance — but worth confirming explicitly rather than assuming, since automatic routing is a substantially bigger feature.
- **Data model.** Waypoints need to live somewhere in `DiagramEdge` (`src/shared/diagram.ts`) — likely an ordered array of points (canvas coordinates, or relative to the source/target the way `ConnectionPoint.offset` is relative to its side) — and `docs/file-format.md` needs to document whatever shape is chosen. Whether a waypoint is a plain `{x, y}` or carries its own tangent/control-point data depends on the interaction model question above.
- **Rendering.** `LabeledEdge.tsx` currently uses one of React Flow's built-in path helpers end-to-end; routing through waypoints means building the path manually (piecewise, one segment per waypoint) instead.
- **Relationship to epic 0014's AnchorNode.** Epic 0014 added a small placeholder node type (`AnchorNode`, see [epic 0014](0014-drag-edge-to-create-shape.md)) as the "leave the edge in space" outcome of a drag that isn't resolved into a real shape yet. That's a real *node* in the graph (draggable, its own id, persisted like any other node) — conceptually adjacent to "a point an edge passes through" but not the same thing (a waypoint doesn't need its own connection handles, icons, or the option to later become a Shape/Container). Worth deciding explicitly whether waypoints reuse/extend that concept or are a fully separate mechanism, rather than accidentally ending up with two unrelated ways to put a point on the canvas.

## Notes

**2026-08-20: [epic 0047](0047-edge-forced-straight-segment.md), a related but distinct idea, also just logged.** A forced straight lead-in segment at each endpoint (default automatic behavior, one configurable pixel length) rather than manual waypoint placement — kept as a separate epic since this one is explicitly about manual, per-edge control. If this epic ever gets a real design pass, worth checking whether a shared piecewise-path-building mechanism could serve both instead of two separate implementations in `LabeledEdge.tsx`.

**2026-08-20: possible shared interaction trigger with [epic 0044](0044-larger-resize-hit-targets.md).** That epic's "dedicated transform mode" idea (a button/keyboard modifier that turns a selected shape's edges/corners into large, easy-to-hit resize zones) was floated by the user as a mechanism that could *also* be reused here — the same "transform" key putting an edge into a state where its bias-offset handles become draggable, rather than two unrelated modes for two unrelated object types. Not decided, not designed; if either epic gets a real design pass first, worth checking whether unifying the trigger actually holds up once one of them is concrete, rather than assuming it will.

**2026-08-23: scope decided — full line/edge unification, not just added waypoint controls.** ADR 0050's "Unifying edges and lines into one connector type" alternative (`source`/`target` as a bound-or-free union, rather than always a required node id) is now the actual direction for this epic, not just the "likely eventual answer" it was framed as when deferred. The user's rationale, three concrete wants:
1. A line should be able to connect to a shape directly (blurs the line/edge distinction from the connecting end, rather than lines and edges staying two parallel mechanisms forever).
2. An edge's endpoint should be able to detach and live free in space, independent of any shape — the same freedom a line already has, and the same role `AnchorNode` (epic 0014) currently plays as a placeholder for a not-yet-resolved edge end. Full unification likely replaces `AnchorNode` outright rather than living alongside it.
3. Deleting a shape shouldn't cascade-delete edges attached to it — an edge can carry real information (a label, a linked-diagram-worthy relationship) that shouldn't vanish just because one endpoint's shape got deleted. Instead, that endpoint should fall back to a free, undetached point roughly where the shape used to be.

This settles the *direction*, not the *design* — the "real design conversation before implementing" this epic's Status line already calls for is still needed, and now has a concretely larger scope to work through: the bound-or-free union on `DiagramEdge.source`/`target`, the resulting `.chd` schema version bump and migration path for existing files, what happens to `AnchorNode` (retired vs. kept for some other purpose), and a new question raised specifically by want (3) — whether shape deletion should *ever* cascade-delete an edge, or whether "fall back to a free point" is the answer in every case, not just a fallback when nothing else is decided.

**2026-08-22: [epic 0064](0064-simple-curved-freeform-line.md) built the likely-reusable curve math.** That epic needed a bendable line independent of any node and deliberately built it as its own thing (a new node type) rather than unifying with edges right away — see [ADR 0050](../../decisions/0050-freeform-line-as-node-type.md) for the full reasoning, including why unification was the "right eventual answer" but premature to commit to before the mechanism itself was proven. The part worth knowing about here: the point-list-plus-per-point-"gravity" → piecewise-bezier math lives in its own dependency-free module (`bendablePath.ts`, no notion of "node" or "edge"), specifically so this epic can consume it directly if/when it gets picked up — turning "waypoints with vector controls" into "reuse 0064's gravity model on an edge's own point list" rather than a second design-and-build pass. Still not started; this is a pointer for whenever it is.

**2026-08-21: reusable groundwork from [epic 0045](0045-edge-label-position-slider.md).** That epic needed "the point at an arbitrary fraction of an edge's rendered path" (for positioning the label anywhere along it, not just the midpoint) and solved it in `LabeledEdge.tsx`'s `pointAtRatio()` — a throwaway SVG `<path>` fed the same path string BaseEdge renders, read via `getPointAtLength()`. Whatever interaction model this epic lands on (waypoints, bias offsets) will likely need the same kind of point-on-path math, possibly the same helper directly. The user flagged this connection while epic 0045 was being scoped, worth checking `pointAtRatio` before reimplementing similar geometry here.
