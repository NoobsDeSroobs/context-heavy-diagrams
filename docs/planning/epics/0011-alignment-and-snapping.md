# 0011: Alignment and snapping

## Status
Done — merged to `master` (#14). See Implementation notes; the interactive drag/snap feel itself was never independently re-confirmed after merge (see Verification gap below), but nothing's been reported wrong since.

## Goal
Accurately align shapes vertically/horizontally while dragging, with snapping — requested during epic 0002 design discussion, not part of the original brief. Numeric position/size fields already exist on every node; this epic is about mouse-driven precision on top of that, since direct mouse interaction is the primary way shapes actually get positioned.

## Scope, decided when this epic started
See [ADR 0019](../../decisions/0019-snap-to-shape-not-grid.md) for the full write-up of this decision and its alternatives — summarized here as it was originally scoped:

Two items from the original task list were genuinely open and resolved with the user before implementing:
- **No snap-to-grid.** Proximity-based snap-to-shape only — a 5px (screen-pixel) threshold, not requiring edges to touch, so e.g. two shapes with a gap between them can still snap into a matching column/row.
- **Connection-aware alignment (positioning a node relative to what it's connected to) is deferred** to its own epic — see [epic 0031](0031-connection-aware-alignment.md). It was flagged in this epic's original task list as a real fork (lightweight snap extension vs. full graph auto-layout) not a small addition, so it's being kept out of this epic entirely rather than guessed at.

## Implementation notes (2026-08-19)
- **Geometry is pure and framework-free**: `src/renderer/src/alignment.ts` exports `boundsFrom` (x/y/width/height → left/right/top/bottom/centerX/centerY) and `computeSnap(dragged, others, threshold)`. Each of the dragged node's three X-values (left/center/right) is checked against each other node's three X-values, independently of the same 3×3 check on Y — a drag can snap horizontally to one shape and vertically to a completely different one at the same time. Only the single closest match per axis actually moves the node; ties at that same closest distance are kept as additional guide lines (e.g. three shapes already sharing a left edge all light up together). Verified correct by hand-tracing several cases (edge-to-edge, center-to-center, exact-zero-distance, multi-way ties) — see this epic's implementation session.
- **Threshold is in real screen pixels, not flow/canvas units** (`SNAP_THRESHOLD_PX = 5`, converted via `/ zoom` before comparing in flow coordinates) — a fixed canvas-unit threshold would feel wrong at different zoom levels (too loose zoomed in, nearly unreachable zoomed out); the user's own framing ("5 px") was explicitly screen-pixel, not canvas-unit.
- **Snap correction happens by re-nudging position after React Flow's own drag update**, inside `onNodeDrag` (fires every drag tick): read the live (pre-snap) position RF already applied, compute the snap delta, and if nonzero, call `setNodes` to shift by that delta — which wins as the tick's final state. This works because React Flow recomputes each tick's raw position from the drag's *start* position plus total pointer movement (not incrementally from the previous tick's rendered position), so the correction doesn't get fought — it just holds the snapped position for as long as the pointer stays within the threshold band, matching Figma/Illustrator-style smart-guide behavior.
- **A dragged node's own descendants are excluded from comparison** (a container always geometrically "contains" its own contents, which isn't meaningful alignment signal and would produce distracting guide lines) — same `parentId`-chain-walking approach `onNodeDragStop`'s existing reparenting logic already uses, just a fresh local instance rather than a shared helper.
- **Multi-node drag**: snap is computed from the lead dragged node only (the one under the cursor); the resulting delta is applied uniformly to every node in the drag group, preserving their relative offsets to each other.
- **Guides render as a screen-space overlay**, not inside React Flow's own pan/zoom-transformed viewport (no supported way to inject arbitrary content into that internal group) — `components/AlignmentGuides.tsx` converts flow-space guide positions to screen pixels via `useViewport()` (which re-renders the overlay on pan/zoom too), as a sibling `<div>` next to `<ReactFlow>` inside `.canvas-view-flow`. `pointer-events: none` throughout so it never intercepts the drag it's illustrating.
- **Not extended to resizing** — this epic is specifically about drag/position, per its own goal statement ("direct mouse interaction is the primary way shapes actually get positioned"). Snap-while-resizing would be a natural, separate follow-up if wanted.
- **Fixed: snap held while dragging but reverted the instant the mouse was released.** User-reported after a manual try. Root cause confirmed by reading `@xyflow/system`'s `XYDrag` source: on drag-end, React Flow calls its own internal `updateNodePositions(dragItems, false)` — committing the raw pointer-derived position straight from its internal drag state — *before* invoking `onNodeDragStop`, silently overwriting whatever `onNodeDrag`'s per-tick corrections had already applied. `onNodeDrag` alone was never going to be enough; the snap correction now also runs inside `onNodeDragStop` (recomputed fresh via a new shared `computeGroupSnap`, not reused from the last tick, since the pointer can move slightly between the last `onNodeDrag` call and release), which runs *after* React Flow's internal commit and so wins. The reparenting logic already in `onNodeDragStop` now operates on the corrected position too, not the raw one.

**Verification gap**: this session's browser-automation tooling couldn't drive React Flow's node-drag interaction (same class of limitation as epic 0003's connect-by-drag gap — synthetic pointer events aren't recognized by React Flow's D3-drag-based interaction handling, and screenshot capture wasn't available as a coordinate-based fallback). The pure geometry (`computeSnap`) was verified correct by hand-tracing test cases directly, and the release-time root cause was confirmed by reading React Flow's own source rather than guessing, but the actual live drag-and-release experience still hasn't been verified in-browser by this session. Worth another manual pass — drag a shape near another, confirm guides appear, and confirm the snapped position now holds after release.
