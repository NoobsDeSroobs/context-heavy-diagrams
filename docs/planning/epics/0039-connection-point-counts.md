# 0039: Per-side connection point counts

## Status
Done (2026-08-21). Raised by the user (2026-08-20), the same day epic 0013's "Add connection point here" bug was found and fixed during epic 0022's gallery testing — trying that flow with the fix in place surfaced a real usability problem (see Decided) that prompted this.

## Decided
**Augments, doesn't replace, the existing click-to-add flow — both capabilities stay.** Confirmed by the user after trying click-to-add in practice: it isn't very accurate, since the point lands wherever the mouse happened to be rather than anywhere precise. That's exactly the case a count-per-side generator is meant to help with (fast, evenly-spaced, no fiddly clicking), but click-to-add still has real value for placing an individual point exactly where one specific edge needs to land — no reason to lose that. Whether click-to-add's own accuracy is worth separately improving (e.g. some kind of snapping or a numeric offset input) is a smaller, related idea, not scoped here.

## Goal
Alongside the existing right-click "Add connection point here" (which places one point near the click position), let the user configure a *count* of connection points per side — e.g. 4 on the right, 2 on the bottom, 1 on the top, 0 on the left — evenly spread along each side automatically, rather than placed one at a time by hand.

## Relevant existing behavior
Epic 0013's current model: `connectionPoints: [{ id, side, offset }]` per node (`docs/file-format.md`). Points are added one at a time via right-click → "Add connection point here" (nearest-side/offset computed from click position, `nearestConnectionPoint` in `src/renderer/src/nodes/connectionPoints.ts`), removed one at a time via right-click on the point itself. **No file-format change is required just to support a count-based generator** — an even-spread count-per-side UI would still only ever produce ordinary `ConnectionPoint` entries with computed offsets. That changes if the design later wants to persist "N evenly spaced on this side" as its own declarative concept rather than baking out the resulting offsets at generation time — see the open questions below.

## Initial reaction (for the design discussion, not a decision)
The current model's strength is *precision* — a point can be placed exactly where a specific edge needs to land (three points at three specific, unevenly-spaced heights matching three specific incoming connections, say). A pure count-per-side, evenly-spread model trades that away for speed of setup. A hybrid — count-per-side as a bulk-generate convenience, existing click-to-add/remove still available afterward to fine-tune individual points — could get both: fast for "I just want 4 on the right," no loss of precision for the exceptional case. If points stay draggable/removable after being generated, "evenly spread" only needs to be true *at generation time*, not an invariant the app continuously enforces afterward — worth being explicit about which of those two this is, since they're different amounts of work (compute once vs. maintain a constraint).

## Real open questions (deliberately not resolved here)
- **Where does the setting live?** Per-node, surfaced how — right-click menu, a property-panel field, a small form with one number input per side?
- **Regenerate behavior** — if a count changes after points already have edges attached, what happens to points that would be removed? Epic 0013 already blocks removing a single point with an edge attached; a bulk regenerate needs its own answer, likely more disruptive since one count change could conflict with several existing edges at once.
- **Evenly spread — exact spacing convention?** Points at the corners (offset 0 and 1) or inset from them? Does count=1 match the default 4 fixed points' own behavior (centered on the side, offset 0.5) as a special case?
- **Interaction with resize** — already handled for individual points today (percentage-based offset, not pixels, epic 0013) — a generated set should inherit that for free, worth confirming once built rather than assuming.

## What was built
Design worked through with the user in conversation (2026-08-21) — see [ADR 0036](../../decisions/0036-connection-point-count-and-transfer.md) for the full reasoning. Answers to the real open questions above:
- **Where the setting lives**: a new "Connection points" section in the property panel (`PropertyPanel.tsx`), single-node selection only — four number fields, Top/Right/Bottom/Left, showing a total that includes the always-present default point.
- **Regenerate behavior**: not blocked, not a partial-preserve merge either — the user proposed a fully deterministic edge-transfer model instead (clockwise ordering per side; growing keeps every existing point's id/edges and appends new ones at the clockwise end; shrinking removes clockwise-most points one at a time, each transferring its edges to the new clockwise-most survivor, then re-spaces the survivors evenly). This also replaces epic 0013's original "block removal if an edge is attached" rule for the existing manual right-click remove, which now transfers instead (to the counter-clockwise neighbor, or forward if removing the first point on a side) — and, per [ADR 0036](../../decisions/0036-connection-point-count-and-transfer.md)'s Revision 3, also re-spaces the survivors evenly, same as the bulk path. Manual right-click "add point here" got the same treatment: the click position only picks *where in order* the new point goes, its and every existing point's actual offset comes from the same even-spacing pass.
- **Spacing convention**: `offset_i = (i+1)/(N+1)` over the side's *whole* point count N — evenly spread, inset from both corners, genuinely symmetric for every N. The point that happens to carry the side's fixed id (`"top"` etc.) is not exempt from this — it moves with everything else. (Two earlier, narrower attempts — spacing only the custom points, then spacing around a permanently-fixed default — both turned out wrong; see [ADR 0036](../../decisions/0036-connection-point-count-and-transfer.md)'s Revision 2.)
- **Interaction with resize**: unaffected — offsets stay percentage-based throughout, no change needed.
- **Upper limit**: new `maxConnectionPointsPerSide` global setting (default 12) in the settings panel added by epic 0047, per the user's own ask.
- **The default point is no longer special-cased at all** — every side always has ≥1 point; one is synthesized on demand (fixed id, offset 0.5) only for a side nothing has ever touched, and becomes an ordinary, freely-movable, freely-removable point the instant the side is regenerated.

Implementation: pure algorithm functions (`setSideCustomPointCount`, `removeCustomPointWithTransfer`, `insertConnectionPointAt`, `respaceClockwise`, `reassignConnectionPointHandles`, `effectivePointsForSide`/`effectiveConnectionPoints`/`connectionPointCountForSide`) in `connectionPoints.ts`; `Canvas.tsx`'s `setConnectionPointCount` as the property panel's entry point; `ConnectionPointFields` in `PropertyPanel.tsx` applies on blur/Enter rather than per-keystroke, since a mid-typing commit could transfer edges destructively before the user finishes entering a number. `ConnectionHandles.tsx` renders every point (synthesized or stored) from one unified list, replacing the original 4-hardcoded-handles-plus-a-map structure. File format: no schema change, but a real semantics change — `docs/file-format.md` updated to describe the "≥1 point per side, synthesized when absent" contract in place of "4 fixed, un-removable defaults."

## Verification
Clean typecheck and lint on all changed files (one pre-existing, unrelated lint error elsewhere in `Canvas.tsx`, already tracked under epic 0028). Manual algorithm trace against all four of the user's own scenarios (grow 3→4, shrink 3→2, right-click wedge-insert, right-click remove with transfer) confirms the logic. **Not visually verified in-session** — the dev server was already running under the user's own session (left running, not restarted), and the Browser pane's screenshot compositing wasn't available this session (timed out even after a resize), which also broke coordinate-based clicks and drags; synthetic pointer events don't reliably trigger React Flow's own pointer-capture-based selection either, same limitation noted on epics 0042/0045/0046. Worth a real click-through, in particular: the property panel's count fields on a shape with existing wired edges (grow and shrink both directions), and right-click add/remove on a shape with several points.

**Spacing bug caught by the user (2026-08-21, same day, before merge):** the lack of visual verification above meant the initial spacing formula shipped with a real defect — every even total count overlapped a custom point exactly onto the default point (making "1" and "2" indistinguishable), and odd totals visually clustered around the default. First fix attempt (space around the fixed default, drop the nearest slot) was itself rejected by the user as insufficient — "That will not work unless you manage to change the position of the default point" — and they separately caught a second bug, reconnecting an edge between two points on a 3-point side sometimes landing on the wrong point, which they correctly traced to the same root cause: the default point lived entirely outside the array the app's own ordering/transfer logic reasoned about. **Real fix (see [ADR 0036](../../decisions/0036-connection-point-count-and-transfer.md)'s Revision 2): the default is no longer a fixed, separate case at all** — every side always has ≥1 point, synthesized on demand (using the side's own name as a stable id) only while untouched, and materialized as an ordinary, freely-movable, freely-removable point the moment a side is regenerated. This is a genuine file-format semantics change (documented in `docs/file-format.md`), though the schema shape doesn't change. Verified numerically (a standalone script tracing grow/shrink sequences and their edge-reassignment maps, not just hand-traced) rather than relying on manual reasoning alone, given the first two passes' manual/partial reasoning both missed real issues. Underscores that the "not visually verified" gap is real risk, not boilerplate — a live click-through is now overdue on this epic specifically.

**Round 2 (2026-08-22): manual add/remove not re-spacing, caught by the user actually clicking through it.** The unification fix above resolved the reported symmetry/reconnect bugs, confirmed by the user directly ("Hey, you did it!"), but manual right-click add/remove were both still using their original "leave everything else untouched" design — deliberate at the time (see ADR 0036's original Decision), but the user found the result looked broken rather than precise. Fixed per [ADR 0036](../../decisions/0036-connection-point-count-and-transfer.md)'s Revision 3: every structural operation now re-spaces the whole side afterward; only *which* point moves/gets removed still differs between the bulk and manual tools. Again verified numerically (insert-then-remove trace), not live — the pattern across all three rounds this epic has gone through is real bugs surviving numeric-only verification, so a live click-through matters more here than the "worth checking" framing on other epics.

**Round 3 (2026-08-22): bottom/left mirrored, also caught live.** `respaceClockwise` (Revision 3's new shared helper) always zipped `evenOffsets`'s ascending values onto the clockwise-sorted points array by plain index — correct on top/right, where clockwise order happens to be ascending raw offset, wrong on bottom/left, where it's descending. The property panel's growth direction looked reversed on those two sides; right-click add/remove placed the new point on the visually opposite side of the click. Same root cause in both, not two separate bugs — the user's own diagnosis, confirmed. Fixed per [ADR 0036](../../decisions/0036-connection-point-count-and-transfer.md)'s Revision 4: `respaceClockwise` now reverses the offsets array for bottom/left before zipping. Verified numerically on both sides this time (growth sequences and click-near-an-edge insertion, checked against expected raw-offset direction by hand for each).

**Round 4 (2026-08-22): manual add ignored `maxConnectionPointsPerSide`.** Set to 5, grown to 5 via the panel (correctly capped by the field's own `max`), then right-click "Add connection point here" added a 6th anyway — the setting only ever reached the property panel's `NumberField`, never `insertConnectionPointAt` or the context-menu hook that calls it. Fixed per [ADR 0036](../../decisions/0036-connection-point-count-and-transfer.md)'s Revision 5: the setting is now threaded through `DiagramContext` (same pattern as `edgeStraightSegmentLength`) so node components can enforce it directly; `insertConnectionPointAt` refuses past the limit and the hook shows an alert.
