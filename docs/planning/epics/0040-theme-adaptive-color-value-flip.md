# 0040: Theme-adaptive color value flip

## Status
Done, pending PR/merge. Implemented and confirmed working in the running app by the user (2026-08-21) on `epic/0040-theme-adaptive-color-value-flip`, including the same-day Oklab revision (see [ADR 0034](../../decisions/0034-theme-adaptive-color-value-flip.md)) after the user's own testing caught the HSV version's contrast problem. Raised by the user (2026-08-20), following up on what first looked like a theming bug (epic 0022's gallery testing) but turned out to be expected behavior — explicit diagram colors correctly don't follow the app's light/dark theme, and the specific case that prompted the report was the user's own manual color override for readability. This epic is the actual, better answer to that readability problem: keep colors static in the *values that matter* (hue, saturation, opacity) while letting them adapt automatically across themes.

## Goal
When the app's theme changes, an explicitly-set color (`fill`, `stroke`, `fontColor` on a Node or Edge) should stay recognizably "the same color" but adapt its lightness so it stays legible against the new background — not stay bit-for-bit identical (today's behavior), and not lose its identity by falling back to a generic default either.

## Decided
See [ADR 0034](../../decisions/0034-theme-adaptive-color-value-flip.md) for full reasoning, including a contrast-driven alternative that was seriously considered and rejected, and a same-day revision explaining the mechanism change below. Summary:
- **Mechanism: mirror Oklab Lightness around its midpoint, hold the chroma/hue axes fixed.** `flip(L) = 1 - L`. Originally specified as an HSV Value mirror (`V' = 100 - V`) — shipped, then superseded same day once the user's own testing showed HSV's V doesn't preserve contrast reliably (it's hue-blind: red looks darker than its V suggests). Oklab's L tracks actual perceived brightness across every hue, which is what the mirror needs to actually preserve readability, not just numeric symmetry.
- **Opacity is unaffected** — this is about the color's own lightness, not `fillOpacity`/`strokeOpacity`/`fontOpacity` (already separate fields, per-channel, in `docs/file-format.md`'s Node/Edge style). Nothing about how opacity works today needs to change.
- **Dark theme is the stored baseline.** The value in the file always means "this color's lightness as rendered in dark theme," regardless of which theme was active when it was set. Render time: `displayed = theme === 'dark' ? stored : flip(stored)`. Edit time (color picker): converts the other direction — picking/typing a color while in light theme stores `flip(picked)`, so what's stored is always the dark-theme-equivalent value, and the picker itself is WYSIWYG for whichever theme you're actually looking at. This makes the transform a pure function of (stored value, current theme) — lossless and idempotent no matter how many times the app theme gets flipped, and tweakable from either theme without needing to "know" which theme a color was originally authored in.
- **No file-format change needed.** The stored `fill`/`stroke`/`fontColor` stays exactly what it is today — a literal CSS color (`docs/file-format.md` is unaffected). The dark-baseline convention is purely an in-app rendering/editing behavior layered on top: a reader that doesn't know about it (a third-party tool, or an older version of this app) still renders a perfectly valid, coherent diagram — just always in its dark-theme coloring, never live-adapted for light — which is a reasonable and harmless degradation, consistent with how this format already treats other purely-presentational state (e.g. highlight enabled/disabled isn't persisted either, per the Highlights section of that doc).
- **Always-on, blanket, no opt-in/opt-out in v1.** Every explicit `fill`/`stroke`/`fontColor` gets the flip unconditionally — deliberately simple ("translate the picked colour at runtime, no analysis of contrast"), not a contrast-driven targeted adjustment. If a real need for an exemption shows up later, the landing spot is a global toggle in the existing Settings panel, not a per-field/per-diagram flag.
- **Not a real question yet**: epic 0030 (custom style palettes) doesn't exist yet — nothing to decide until it's scoped.
- **Every existing file is affected on first load, explicitly accepted.** No stored marker distinguishes old colors from new ones; every `.chd` file's light-mode rendering changes the moment this ships (dark mode is unaffected for diagrams authored while looking at dark theme). Confirmed as intended, not a migration concern to solve around.
