# 0040: Theme-adaptive color value flip

## Status
Not Started — not yet scoped. Raised by the user (2026-08-20), following up on what first looked like a theming bug (epic 0022's gallery testing) but turned out to be expected behavior — explicit diagram colors correctly don't follow the app's light/dark theme, and the specific case that prompted the report was the user's own manual color override for readability. This epic is the actual, better answer to that readability problem: keep colors static in the *values that matter* (hue, saturation, opacity) while letting them adapt automatically across themes. Deliberately not designed here, just captured so it isn't lost, same as epics 0024/0026/0030/0037/0038/0039.

## Goal
When the app's theme changes, an explicitly-set color (`fill`, `stroke`, `fontColor` on a Node or Edge) should stay recognizably "the same color" but adapt its lightness so it stays legible against the new background — not stay bit-for-bit identical (today's behavior), and not lose its identity by falling back to a generic default either.

## Decided
- **Mechanism: flip HSV *Value*, hold Hue/Saturation fixed.** The user's own worked example: a color at a given hue, full saturation, 50% opacity, and 10% value should render at the same hue, same saturation, same 50% opacity, but 90% value once the theme flips — i.e. `V' = 100 - V`, everything else untouched.
- **Opacity is unaffected** — this is about the color's own HSV Value component, not `fillOpacity`/`strokeOpacity`/`fontOpacity` (already separate fields, per-channel, in `docs/file-format.md`'s Node/Edge style). Nothing about how opacity works today needs to change.
- **HSV specifically, not HSL** — the user named "hue, saturation, opacity, and value" explicitly; this is the HSV/HSB model's V (Value/Brightness), not HSL's L (Lightness). The two behave differently at the extremes, so this distinction matters once it's actually implemented.
- **Dark theme is the stored baseline.** The value in the file always means "this color's Value component as rendered in dark theme," regardless of which theme was active when it was set. Render time: `displayedV = theme === 'dark' ? storedV : 100 - storedV`. Edit time (color picker): converts the other direction — picking/typing a value while in light theme stores `100 - pickedV`, so what's stored is always the dark-theme-equivalent value, and the picker itself is WYSIWYG for whichever theme you're actually looking at. The user's own worked example: setting 40% while in dark mode stores 40%; setting 40% while in light mode stores 60%. This makes the transform a pure function of (stored value, current theme) — lossless and idempotent no matter how many times the app theme gets flipped, and tweakable from either theme without needing to "know" which theme a color was originally authored in.
- **No file-format change needed.** The stored `fill`/`stroke`/`fontColor` stays exactly what it is today — a literal CSS color (`docs/file-format.md` is unaffected). The dark-baseline convention is purely an in-app rendering/editing behavior layered on top: a reader that doesn't know about it (a third-party tool, or an older version of this app) still renders a perfectly valid, coherent diagram — just always in its dark-theme coloring, never live-adapted for light — which is a reasonable and harmless degradation, consistent with how this format already treats other purely-presentational state (e.g. highlight enabled/disabled isn't persisted either, per the Highlights section of that doc).

## Real open questions (deliberately not resolved here)
- **Always-on vs. opt-in.** Does every explicit color automatically get this treatment, or is it a per-field or per-diagram choice — since sometimes an exact literal color really is wanted identically in both themes (matching a brand color, say) and a forced flip would be wrong there?
- **Interaction with epic 0030** (custom style palettes/defaults, also unscoped) — if/when named palette entries exist, does a palette color also get this treatment, or only ad hoc per-element colors?
- **What happens to files that predate this feature** (including every `.chd` this gallery has produced so far) — do their existing literal colors get reinterpreted as dark-baseline values the first time this ships (potentially changing how they look in whichever theme wasn't used to author them), or does something distinguish "old, theme-naive color" from "new, dark-baseline color"? Worth a real answer rather than an implicit one, since it affects every existing file's appearance, not just new ones.
