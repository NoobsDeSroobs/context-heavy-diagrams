# 0014: Dragging an edge into empty space creates a shape

## Status
Done, merged to `master` (#16, alongside epic 0033). Never explicitly re-confirmed as its own item after merge, but the drag-to-empty-space → anchor → resolve-to-shape/container flow has been exercised constantly through dozens of subsequent epics with no issue ever reported against it. See Implementation notes.

## Goal
Dragging a connection from a shape's handle and releasing it over empty canvas (instead of onto another node) offers to create a new shape at the drop point and connects the edge to it. Familiar pattern from Miro/Figma-style tools. Raised during epic 0012 testing, not part of that epic's scope.

**Revised after first-pass user testing** (2026-08-19): the original task list assumed the new node is always a `ShapeNode`. Actual user feedback: (1) a real bug — connecting two *existing* shapes could still spawn a spurious extra shape; (2) don't assume the type — pop up a small choice (Shape / Container / more later) at the drop point, and if the user dismisses it without picking, leave the edge attached to a plain draggable placeholder instead of forcing a decision. See Implementation notes below for both.

## Tasks
- [x] `onConnectStart`/`onConnectEnd` on `<ReactFlow>`: track which node/handle a connection drag started from
- [x] On drop, detect whether the release point was the pane background (`event.target` has the `react-flow__pane` class) rather than a valid handle
- [x] If so: create a placeholder node at the drop position (via `screenToFlowPosition`), add an edge from the drag's origin handle to it
- [x] Decide which handle on the new node the edge attaches to (simplest default: a fixed side, e.g. `left`; revisit if it looks wrong in practice)
- [x] Popup at the drop point offering Shape / Container; picking one resolves the placeholder into that type; dismissing leaves it as a draggable placeholder
- [x] Fix: a drag that completes a real connection to an existing handle must never also spawn a placeholder (see Implementation notes — `connectionRadius` false positive)
- [x] Connection handles hidden until the node is hovered, then all of them appear together — previously always visible on every node, which made hovering near a shape to start a drag ambiguous with just moving past it

## Notes
Only meaningful for `ShapeNode` drags — `TextNode` has no connection handles, so this can never start from a text node. (`ContainerNode` also renders the same handles via the shared `ConnectionHandles` component, so a drag can start from a container too — the implementation doesn't special-case node type, it works from whichever node/handle `onConnectStart` reports.)

## Implementation notes (2026-08-19)
- **`connectStartRef` (a plain ref, not state)** holds `{ nodeId, handleId }` from `onConnectStart` to `onConnectEnd` — a drag gesture's transient origin, not something any render needs to react to, so a ref avoids pointless re-renders on every drag start. Cleared unconditionally at the top of `onConnectEnd` regardless of whether anything ends up spawned.
- **Pane detection**: `event.target instanceof Element && target.classList.contains('react-flow__pane')`, matching both the epic's own task wording and React Flow's own documented pattern for this exact interaction (their "Add Node On Edge Drop" example). Dropping on an existing node, a UI panel, or anywhere else that isn't the bare pane is a no-op — React Flow's own `onConnect` already handles the valid-handle case.
- **Bug fix (round 2): pane-target alone is not sufficient.** User testing found that dragging between two *existing* shapes could still spawn a spurious extra shape. Root cause: React Flow completes a connection to any handle within `connectionRadius` of the release point (default 20px, not overridden here) — a release a few pixels off the actual handle dot still forms a valid connection via `onConnect`, but the raw DOM element under the cursor at that exact pixel can still be the pane. `onConnectEnd`'s second argument (`FinalConnectionState`) carries `isValid`, which reflects React Flow's real radius-aware match rather than naive point-in-element hit-testing — the fix adds `if (connectionState.isValid) return` as the first check, before the pane check, so a real connection (exact or radius-snapped) never also spawns a placeholder.
- **Target handle is hardcoded to `'left'`**, per the epic's own suggested default — not revisited, since nothing so far suggests it looks wrong in practice.
- **`screenToFlowPosition` takes raw `clientX`/`clientY` directly**, no manual subtraction of the pane's bounding-rect offset — consistent with the existing `spawnPosition` helper in this same file, since React Flow's v12 `screenToFlowPosition` already accounts for the pane's own offset internally.
- **Scope revision: `AnchorNode` placeholder + Shape/Container picker, instead of assuming Shape.** A new minimal node type (`src/renderer/src/nodes/AnchorNode.tsx`, registered as `'anchor'` in `nodeTypes`) is what actually gets spawned at the drop point — a small (14px) draggable dot, using the same shared `ConnectionHandles` component as `ShapeNode`/`ContainerNode` (so it exposes the same `'top'/'right'/'bottom'/'left'` handle ids — the edge's `targetHandle: 'left'` stays valid whatever this placeholder becomes later, no separate edge update needed). Immediately after creating it, the existing generic `ContextMenu` (already used for right-click menus everywhere else in this file) opens at the drop point with two items, "Shape" and "Container" (not "Text" — `TextNode` has no connection handles at all, so it can never be a valid resolution of a dangling edge). Picking one calls `resolveAnchorNode(nodeId, type)`, which mutates the placeholder node in place (same id, recentered on its own center point, resized/defaulted to that type's normal new-node values — same literals `addShapeNode`/`addContainerNode` already use). Dismissing the menu (click elsewhere, Escape — both already handled generically by `ContextMenu`/the global Escape handler) leaves the placeholder exactly as it is: just another node, draggable like any other, with no special-cased behavior needed to support "drag it around later." Each resolution is its own `pushSnapshot()`, separate from the anchor+edge creation's own snapshot — same granularity as every other discrete edit in this file.
- **`'anchor'` is a real, persisted node type** — plain string, same as every other `DiagramNode.type` (see `src/shared/diagram.ts`), so a placeholder left unresolved survives a save/reload like any other node. Documented in [docs/file-format.md](../../file-format.md)'s Node `type` field, and in [ADR 0015](../../decisions/0015-anchor-placeholder-node.md), which records the alternatives considered (a genuinely free-floating edge endpoint; reusing `ShapeNode` with an "unresolved" flag) and why a small dedicated node type won out. A lenient third-party reader that doesn't recognize `"anchor"` falls back to treating it as `"shape"`, per that field's existing fallback rule — visually different (no label/icons) but not broken.
- **Connection handles now hidden until hover**, per user feedback after this round of testing — previously every `Handle` (default 4 + any custom connection points) was always visible on every `ShapeNode`/`ContainerNode`/`AnchorNode`, all the time. Pure CSS: `.shape-node .react-flow__handle` (and the `container-node`/`anchor-node` equivalents) get `opacity: 0`, with `:hover` on the node wrapper flipping it to `1` — see `main.css`. Hovering reveals *all* handles on that node together (default sides + any custom points), not just the one nearest the cursor, since the CSS rule doesn't key off cursor position at all, just "is any part of this node hovered." No JS/proximity-radius logic needed: a default handle sits a few px outside its node's own box (React Flow's own offset), but `:hover` still holds while pointing at it because hover state cascades to ancestors of whatever's actually under the cursor, not by visual bounding-box containment — so there's no dead zone between the node edge and the handle itself.
- **Not implemented: a way to resolve an already-dangling anchor later** (e.g. right-click → pick a type after the initial popup was dismissed). Not asked for — the user's own framing was "leave the edge in space, I can drag it around later," not "let me convert it after the fact." Worth revisiting if it turns out to matter in practice.
- **Conceptual overlap flagged, not resolved, with [epic 0032](0032-edge-routing-and-waypoints.md)** (edge routing/waypoints, opened alongside this revision): `AnchorNode` is "a point in space an edge connects to," which is adjacent to but not the same as "a point an edge routes *through*." Left as two separate mechanisms for now — 0032's own Notes flag this explicitly as something to decide intentionally when that epic gets scoped, rather than something to guess at here.
