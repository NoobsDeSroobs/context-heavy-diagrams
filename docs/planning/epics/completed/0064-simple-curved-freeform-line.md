# 0064: Simple curved freeform line (bezier)

## Status
Done (2026-08-23) — implemented, live-tested by the user across two passes (hit-testing, then the Layers panel), no further bugs or problems found. Ready to merge.

## Goal
A simple curved freeform line as a new top-level item category, distinct from edges (which always connect two node endpoints). Deliberately scoped down from 0051's original "freeform, bendable lines" idea: an ordered list of points, each with a "gravity" value controlling how much the curve bends at that point, rather than a full bezier-handle editor. The immediate driver is drawing trust-boundary lines in threat-model-style diagrams — a curve that can be placed and shaped independently of any node, not anchored to two connection points the way an edge is.

## Decided (2026-08-22, real design conversation before building)

**Separate entity from edges, for now.** Originally explored unifying the line with edges into one underlying connector type (a source/target that's either bound to a node or a free point in space), which would also subsume `AnchorNode`'s dangling-edge-end placeholder. The user liked the unification in principle but explicitly chose to defer it: build the line as its own thing first, reusing only the pure geometry, so the bend-point mechanism can be built and tweaked without any risk to the currently-working edge code (`LabeledEdge.tsx`). See [epic 0032](0032-edge-routing-and-waypoints.md)'s Notes for how this connects back to edges gaining the same capability later.

**Modeled as a new `DiagramNode` type (`'line'`), not a new top-level array.** Reuses the existing node envelope — selection, dragging (moves the whole line), locking, z-order, the layer panel — for free, the same way `shape`/`container`/`text`/`anchor` already work. `position`/`size` are kept as the bounding box of the line's points (with a small padding for the point handles/stroke), recomputed whenever a point moves. Points themselves live in `data.points`, node-local coordinates (relative to `position`, like a container's children), each `{ x, y, gravity? }` — order is the only thing that identifies a point (no separate id), confirmed by the user as the only property of the array that matters.

**Curve math: per-point-gravity Catmull-Rom, converted to piecewise cubic bezier.** Tangent at each point `Pi` is `(P[i+1] - P[i-1]) * gravity_i` (endpoints use their single neighbor). `gravity` absent means the default `0.5` (the standard uniform Catmull-Rom tension) — a smooth pass-through curve with no manual handle-dragging required. `gravity = 0` gives a sharp corner (zero tangent, straight in/out — a polyline vertex); higher values bend/bulge more. Two points with no interior points always renders as a dead-straight line regardless of gravity (the math degenerates to it — no special-casing needed), which is exactly what a freshly-spawned line should look like. Implemented as a pure, dependency-free function (`bendablePath.ts`) taking only a point list and returning an SVG path string — deliberately kept ignorant of "node" vs "edge" so it's the one piece a future bendable-edge type can reuse verbatim, per the duplication-risk conversation with the user.

**Styling reuses the existing style vocabulary**, not a new system: `stroke`/`strokeOpacity`/`strokeWidth`/`lineStyle`/`startMarker`/`endMarker` — the same fields `EdgeStyle` already has, added onto `NodeStyle` instead (same pattern `LegendEntry` already uses for its own `'line'` kind). No fill, no font — a line has no label in this pass.

**Placement: a 4th `ItemPalette` button**, next to Shape/Container/Text. Spawns a 2-point horizontal line at the viewport center, same `spawnPosition` convention as the other three.

**Point editing UI, kept deliberately simple for v1**: right-click on the line's path adds a point at that location (no explicit gravity — falls back to the documented default); each point renders as a small draggable handle; right-click an existing point opens a context menu with a set of named gravity presets, a divider, then Remove — discrete presets rather than a continuous drag-to-adjust gesture or per-point numeric field, enough to deliver "how much this point is allowed to bend" without building a bespoke in-canvas slider. Worth revisiting after live testing if the presets feel too coarse.

**Gravity presets are a diagram-level catalog, not a hardcoded app constant** (added 2026-08-22, before first live test — see [ADR 0050](../../../decisions/0050-freeform-line-as-node-type.md)'s addendum). A specific diagram's layout may need its own bend values, and reliably reproducing that diagram for any reader means those named values need to live in the file. New `DiagramFile.gravityPresets`, editable via a new `GravityPresetsPanel` (View → "Line bend presets"), absent/empty resolves to this app's own built-in four: Sharp (`0`), Acute (`0.2`, added the same day — "a fairly tight turn"), Smooth (`0.5`), Curvy (`1`).

**Hit-testing tracks the curve, not the bounding box** (same day, also before first live test — see [ADR 0050](../../../decisions/0050-freeform-line-as-node-type.md)'s second addendum). A concave shape (the user's example: a U-bend) made the *whole* rectangular bounding box clickable, including its own empty interior — unlike an edge, which only responds near its actual path. Fixed via `pointerEvents: 'none'` on the RF node wrapper for `line`-typed nodes, with the curve's own invisible hit-stroke and point handles each explicitly opting back in. **Confirmed working by the user.**

**2026-08-23: two Layers panel gaps fixed** (see [ADR 0050](../../../decisions/0050-freeform-line-as-node-type.md)'s third addendum) — a fresh line showed as "(unlabeled)" (now seeded `data.label: 'Line'`, matching Shape/Container/Text's own default-label convention), and clicking its row to "point at" it did nothing (`LineNode.tsx` never rendered the `entityHighlightNodeId` treatment the other three have — added as a dashed halo traced along the curve itself, not a box outline, for the same concave-bounding-box reason as the hit-testing fix). Also logged from the same conversation, not acted on: a line has its own `zIndex`/Layers row, an edge has neither (derived from its endpoints instead) — a real structural consequence of this epic's node-not-edge decision, worth weighing if the line/edge unification question (ADR 0050's Alternatives, epic 0032) ever gets revisited.

## Deliberately not done here (would need its own epic)
- Unifying with edges (bound-or-free endpoints on one connector type) — see epic 0032.
- A dedicated "place a brand-new line with both ends already free" isn't a separate concern from the above — moot for now since the line's endpoints are always free by construction in this scoped-down version.
- A palette-driven default style for lines (`settings.defaultStyles.line`, epic 0030's mechanism) — starts with a hardcoded default only, matching how shape/container/text originally shipped before that setting existed.
- Continuous/numeric gravity control — discrete presets only (four built-in: Sharp/Acute/Smooth/Curvy), though the catalog itself is now diagram-editable.
