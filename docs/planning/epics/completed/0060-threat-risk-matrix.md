# 0060: Threat/risk matrix (security view) — mode-switch, prototype phase done

## Status
**Done as a prototype, mechanism decided: both, at different layers** (2026-08-24/25, corrected same day — see thirteenth round). Both open questions this epic was really about are now resolved: the feature belongs in this app (eleventh round — "the tool is all about HIGH CONTEXT diagrams, and security is one such important context"), and the mode-switch view versus per-shape-facet question wasn't actually an either/or — the mode-switch (toolbar persona swap, full-canvas replacement) is the *view*, and the per-shape facet (threat data as a `data.details`/`data.linkedDiagram`-style attachment) is the *data model* that view reads from. See [ADR 0055](../../../decisions/0055-security-data-lives-on-diagram-elements.md) for the full decision. [ADR 0054](../../../decisions/0054-progressive-disclosure-for-advanced-features.md) still governs how it's built from here — a diagram that never touches this feature must be completely unaffected by its existence.

**What actually shipped is still a prototype, not a finished feature**: everything lives in `src/renderer/src/security/`, entirely in-memory, backed by hardcoded test data (`threatMatrixTestData.ts`) — no `.chd`/file-format persistence at all. Closing this epic here means "the mechanism and the value proposition are validated and worth keeping in the codebase," not "threat data survives a save/reload." Real persistence ([epic 0079](../0079-security-data-as-diagram-element-property.md)), a mode-aware menu bar ([epic 0080](../0080-mode-aware-menu-bar.md)), and the recursive/automation vision captured in rounds 7–10 below ([epic 0081](../0081-recursive-matrix-population-and-automation.md)) are follow-up epics, not remaining work on this one.

## Goal
A threat/risk matrix: services or components (whichever granularity, hierarchical the way this app's own diagrams already are) listed along one axis, relevant threats listed along the other. Each cell holds two values — probability and consequence — for that specific threat against that specific component/service. Row and column edges show aggregate scores (a vulnerability score per service, a threat score per threat), and the bottom-right corner shows one total security score for the whole matrix.

## The open question this epic is really about
**Is this even part of this application?** The user's own framing, explicitly unresolved: it could be a new view type inside this tool (a lot of the underlying machinery already exists — see below), or it could be a deliberately separate program entirely, specifically to avoid bloating this app with a feature that's substantially different in kind from diagramming. Nothing about scope, architecture, or even *whether to build this here* should be assumed from this doc — this is a placeholder for the idea, not a commitment to build it as part of this project.

## Relevant existing behavior, if it ever does end up here
- This is a much more fully-developed version of an entry already sitting in [epic 0022](../0022-example-diagram-gallery.md)'s own backlog: "Risk register / risk heat map — same caveats as the RACI matrix" (a flagged cross-cutting limits-test — this app is a canvas, not a spreadsheet, and grid/tabular content has no row/column primitive to lean on).
- Hierarchy: services/components nested to whatever granularity is wanted maps naturally onto this app's existing containers (epic 0004) and/or linked-diagram drill-down (epic 0009) — same structural pattern the C4 chain already demonstrates.
- Per-cell values (probability/consequence) and aggregate scores are conceptually close to this app's tag/metadata system (epic 0034/ADR 0022) and highlight-based visual overlays (epic 0026/0036) — a threat matrix's "color the cell by risk level" instinct is exactly what highlights already do for ordinary diagram elements.
- The aggregation (row/column edge totals, one grand total) is the same *shape* of idea as [epic 0059](../later/0059-aggregate-tags-up-to-parent-diagram.md) (rolling values up a hierarchy), just for numeric scores instead of categorical tag values.

**Second round, 2026-08-22: a concrete mechanism for keeping this inside the app, raised mid-session while working on an unrelated epic.** The user's own framing: this would push the app from a pure diagramming tool toward more of a "toolkit" — flagged explicitly as a real consequence, not a free win. The mechanism itself, still "food for thought," not designed or decided:
- **A mode/persona switch in the top toolbar**, alongside (not replacing) today's single diagram-canvas-first view — swaps the whole main view between "diagram mode" and a new "security mode," rather than splitting the screen. The user's own reasoning: you'd never need to see the diagram canvas and the security matrix at the same time, so there's no real cost to making them mutually exclusive full-view modes instead of a split or an overlay.
- **The security view is its own file**, stored in the same colocation folder as the diagram it belongs to — same convention already established for linked "daughter" diagrams (epic 0009, `docs/file-format.md`'s colocation-folder default). Not embedded inside the `.chd` file itself.
- **Limited, deliberate data flow between the two**, not full integration: the security view exposes a threat list (each threat carrying probability/consequence, matching this epic's original per-cell shape above) that can be defined and attached *per shape*, addressable from the diagram side — so a diagram element can carry/reference its own threat landscape without the diagram view needing to render the full matrix.
- Worth weighing against the alternative already on record above (a fully separate program) before committing either way: this mechanism meaningfully lowers the "does this even belong here" bar by reusing two patterns the app already has (colocated sibling files, a toolbar-level mode concept doesn't exist yet but toolbar-level view toggles do) — but "toolkit, not diagramming tool" is a real scope/identity shift for the project worth being deliberate about, not just a technical detail to fold in quietly.

**Third round, 2026-08-23, surfaced while naming a Phase 1 packaging build (epic 0053).** The user's own framing moved from "food for thought" to an actual stated intention: "we are planning on maybe introducing the security tool into this as well, so it is not just a diagram tool anymore." Still not decided or scoped, but now a real factor blocking the app's actual product name (epic 0027) — a name built purely around "diagram" doesn't obviously fit a tool that might also do threat/risk work, which is part of why Phase 1's packaging build used an explicitly temporary placeholder name rather than trying to land on a real one. Worth revisiting this epic's own "does this even belong here" question together with the naming conversation whenever both are picked up for real, rather than deciding either in isolation.

**Fourth round, same day, mid-naming-brainstorm — a real reframe of the mechanism question above, not just a naming idea.** Candidate name floated and left unresolved: "High-context projections" (distilling one representation of a system/story's essence down into another — a mathematical-projection analogy, the user's own). More substantively: the user suggested the security/threat aspect could be framed not as a toolkit-mode expansion (the "second round" mechanism above — a separate mutually-exclusive view) but as **just one more facet of the context a diagram element already carries** — parallel to how `data.details` (free-form Markdown notes) and a linked "daughter" diagram (`data.linkedDiagram`) already let a node hold richer context than fits on the canvas itself, without becoming a separate mode or a different kind of object. Under this framing, a per-shape threat/risk attachment would be a third member of that same family (details / linked diagram / threat data) rather than a competing "security mode" — a meaningfully different shape for the "does this even belong here, and how" question than the second round's mode-switch idea. Neither mechanism is decided; both are now on record as real alternatives to weigh against each other.

**Fifth round, 2026-08-23 — a throwaway render-only prototype, step by step, explicitly not a commitment to either mechanism above.** The user wants to "validate fit ASAP" and chose to explore concretely rather than settle the architecture question first: assume for now that the matrix *does* replace the canvas via a persona-switch mode (the second round's mechanism, picked purely to have something to prototype against — not a decision between it and the "facet" reframe above). Built so far, all in `src/renderer/src/security/`, entirely in-memory, no `.chd`/file-format involvement at all:
- A toolbar `<select>` (Diagram / Security Matrix) swapping the entire main view — `ThreatMatrixView` replaces `canvas-view-body` outright, diagram state untouched underneath.
- The matrix itself: hardcoded test threats/services (`threatMatrixTestData.ts`), a single `combine()` rule (multiplication — the standard probability × impact formula) applied identically to a cell, a row/column aggregate, and the grand-total cell (`threatMatrixMath.ts`).
- Cells are now clickable (interior grid only, never the derived aggregates) — opens a small popup (`ThreatMatrixCellEditor`) to set probability/consequence from a defined scale, updating that cell's score live.
- A probability/consequence scale reference panel to the right of the table (`ThreatMatrixScaleReference`, `threatMatrixScale.ts`) — hardcoded placeholder ranges ("you can just make up some ranges for now"); the user was explicit this needs to become configurable eventually, not that it's decided to stay hardcoded.

**Explicitly deferred, raised in the same round:** a mode-aware top menu bar — items like default edge style, Layers, and Required tags "make no sense" while in matrix mode. Not built; the menu bar (`MenuBar`/`Canvas.tsx`'s `menus` array) still shows the same File/Edit/View/Help regardless of persona. Worth revisiting once/if this prototype's fate is decided, not before.

**Sixth round, 2026-08-24 — remove capability, and a management panel replacing inline table controls.** Threats and services can now be removed as well as added, both from a new floating `ThreatMatrixManagePanel` (reuses `LegendPanel`'s own dock-shell classes/idiom) rather than the inline "+ Threat"/"+ Service" corner buttons the previous round put directly in the table — those are gone from the table now, this panel is the one place to manage the matrix. **Explicitly deferred, the user's own call**: wiring any of this into the top menu bar (`Canvas.tsx`'s `MenuBar`) — "we can modify the main menu bar later once things start to solidify."

**Seventh round, same day — a real design vision for the "service" (column) dimension, not built, deliberately captured before it's lost.** The user's own framing, raised while thinking about recursion:
- The non-threat dimension doesn't have to be manually typed names forever — it "could be anything." Two concrete ways it might eventually be *populated from the diagram itself*: linking each column to a sub-graph (a linked "daughter" diagram, epic 0009's existing mechanism), or deriving columns directly from the shapes already present in a diagram view and their links.
- If the matrix becomes recursive this way (each service/column potentially backed by its own child matrix, one level down), then **a parent view should aggregate the union of every child's own threat list** as candidate rows, rather than each level needing its own hand-maintained threat list.
- For a given parent cell (a threat × a service that has a child matrix), **the child's own already-computed threat score for that threat gets copied into the corresponding parent cell** — not re-entered by hand, and not re-derived by some different formula; whatever the child matrix already computed for that threat (via its own `threatScore()`) becomes the parent cell's value directly.
- **If a given threat has no corresponding entry in a service's child matrix at all, the parent cell should render grey and empty** — a real "not applicable/not assessed for this one" state, distinct from a low-but-real numeric score (which the current 1/1 "not yet reviewed" default for a freshly added cell doesn't actually distinguish from a genuinely assessed low-risk cell — worth reconciling if/when this gets built).

None of this is designed or built — no child-matrix concept exists yet (there's exactly one, flat, in-memory matrix instance today), no linking mechanism, no copy-up logic, no grey/empty cell state. Recorded here so the shape of the idea survives until it's actually picked up.

**Eighth round, 2026-08-24 — how the previous round's recursion vision would actually decide what's in scope, plus real risks of automating it.** Prompted by the user's own experience: they previously did this by hand in Excel, and only estimate directly at leaf diagrams — every level above extrapolates from what's underneath. Two things need distinguishing to make that automatic: which shapes are **leaf** (no linked sub-diagram, so they need a human-entered estimate) vs. **not** (extrapolated from a child), and which are **in scope** (internal) vs. **out of scope** (external — presumably third parties/vendors that don't get their own matrix at all). The user's own proposal for the second half: a required tag marking internal vs. external; walk the internal shapes, and any with no linked sub-diagram is a leaf.

Two real questions raised, not resolved:
- **What if that tag isn't defined as a required tag on a given diagram?** Discussed and settled in direction, not built: don't add a system-mandated/hardcoded tag — that would be the first exception to this app's deliberately schema-free required-tags design (every diagram author decides what tags exist for *their* diagram; epic 0034/ADR 0022 onward). Instead the *mapping* (which tag key/value means "external") should be the matrix's own configuration, pointing at whatever convention a given diagram already uses — different orgs likely already have their own ("Vendor," "Third-party," whatever). A diagram with no such tag at all should be treated as **unclassified**, not silently assumed internal; the matrix's own manage panel could offer to create the tag on a target diagram, but that's a real, consequential write to someone else's diagram and deserves its own confirmation step, not a quiet default.
- **Other automation risks**, roughly in order of concern:
  1. **Staleness** — copying a child's score into a parent cell is a snapshot, not a live reference. A child re-assessed after the copy leaves the parent silently outdated, and for a security tool specifically, false confidence is worse than visibly-incomplete data. Needs some "this parent value is stale, a child changed" signal eventually.
  2. **Shared sub-diagrams double-count.** If the same leaf diagram is linked from two parents, its score rolls into both aggregates — needs either a strict-tree assumption with violation detection, or a real decision to allow sharing and reconcile it.
  3. **Cycles** in the link graph would hang a naive "walk down to leaves."
  4. **Scale** — auto-listing every internal leaf shape on a real landscape (the 70-node Meridian Rail example) could produce dozens of columns instantly; probably needs a shape-type filter (real components only, not text/lines/containers) at minimum.
  5. **Partial completion is invisible.** Today's 1/1 "not yet reviewed" default for a new cell looks identical to a genuinely-assessed low score — sharper once aggregates start rolling up through several unfinished levels at once.
  6. **"No link yet" isn't necessarily "genuinely a leaf"** — could just mean the diagram's incomplete. Probably fine to treat the same way either way (someone needs to assess it regardless), but worth naming as an ambiguity rather than a clean signal.

**Also raised, not built: a reserved "Security score" metadata field.** Once a shape has a linked sub-diagram with its own matrix, that child's grand-total (the bottom-right total-security-score cell) could surface back onto the parent shape itself as a fixed/system-defined metadata field (visible in the Property Panel's metadata section, alongside a shape's regular tags) — not a user-defined tag, a reserved one the app populates. Ties into the same staleness question above: this field would need the same "is this still current" treatment as a copied-up cell value, not just a one-time write.

**Ninth round, 2026-08-24 — resolutions to most of the eighth round's automation risks.** Still none of this designed or built — a direction-setting conversation, not implementation:
- **Staleness (risk 1):** an explicit recursive-refresh button, plus the same refresh firing automatically on switching into the matrix persona. The user's own flagged hard part: making the refresh actually write updated values back into every affected file, not just recompute in memory. Two real shapes for this were weighed, not decided: cache the rollup and refresh on demand (what the user proposed — fast, but a real cache-invalidation surface), vs. never persist a derived score at all and always recompute live by walking to the leaves on open (slower on deep trees, but structurally can't go stale). Leaning toward the latter given this is a security tool and "confidently wrong" is worse than "slow," but not decided.
- **Sharing/double-counting (risk 2):** the user's own argument for why a strict tree is probably fine in practice, not just assumed for convenience — internal/external is inherently scoped to a perspective (team/domain/level), so the same component genuinely being "internal" to two different parents at the same level doesn't make sense; a real share would mean the scope tagging itself is wrong, not that the matrix has a bug. Still worth a lightweight safety net: detecting a file linked from more than one place, and/or labeling a score with its lineage (which parent path it was computed under) for traceability.
- **Cycles (risk 3):** solved by construction — a visited-set during traversal, which has to be depth-first anyway since a parent's values are only computable once every descendant is resolved (bottom-up dependency order, not top-down).
- **Scale (risk 4):** only Shape-type nodes count as candidates (not Container/Text/Line/Anchor), with a metadata tag letting a user opt a specific shape *out*. Explicitly **not** a curated-subset-by-default model — "scale should be everything... it makes no sense in security that you only assess half your components." Naturally scoped to one diagram's own direct shapes at a time, not the whole tree flattened into one view.
- **Invisible partial completion (risk 5):** a dedicated sentinel value for "not yet assessed" (distinct from any real 1–5 score), surfaced as a standing advisory in the Diagnostics panel — reusing the exact mechanism [epic 0075](0075-legend-empty-diagnostic.md) just built for the legend-empty warning.
- **"No link yet" ambiguity (risk 6):** left to the user's own judgment, deliberately not auto-disambiguated — "the user would know if it is a proper leaf or if it is just not linked yet."

**Tenth round, 2026-08-24 — refresh strategy clarified as a hybrid, and the aggregation-scope question settled.**
- **Staleness/refresh (risk 1), clarified:** not purely "always recompute live" — the user meant a genuine hybrid. While actively working within a matrix, scores stay cached in memory (no re-crawl on every small edit, so the view stays responsive). A full automatic crawl fires specifically on *switching into* the matrix persona, throttled behind a cooldown timer so rapidly flipping back and forth doesn't repeatedly re-crawl (the user's own question: once per 5 min? 10 min?). Not decided, but leaning shorter (2–5 min) rather than 10 — the cost being throttled is disk I/O across linked files, likely cheap unless a tree is unusually large, so there's little reason to tolerate a longer staleness window just to save it. One detail worth keeping when this is built: the throttle should only gate the *automatic* on-swap crawl — the explicit manual "recursively update" button should always force a real crawl regardless of the cooldown, since a user who clicks refresh expects it to actually happen.
- **Aggregation scope (risk 2 discussion), settled as a principle:** the union-of-children's-threats rollup isn't a special cross-cutting exception to this app's existing "a diagram only cares about itself" scoping convention — a threat that can affect a child can, by definition, also affect the parent, so listing every child's threats as candidate parent rows is just what ordinary local, bottom-up aggregation looks like here, not global reasoning about the whole tree.

**Separately, the same day: a naming observation about the core diagramming model, unrelated to this epic.** The user thinks "Shape" may be the wrong name for that node type — a Shape and a Container remain conceptually different things even with every style property set identically, so "Shape" (which reads as purely geometric/visual) undersells that it's really a distinct semantic category, something like "Concept." Real and worth pursuing, but a large, cross-cutting rename (`'shape'` is a literal stored string in `DiagramNode.type` in every `.chd` file, touching ADR 0029's backward-compatible-loading rule, `ShapeNode.tsx`, and pervasive UI/doc references) — logged as its own idea, [epic 0076](../0076-rename-shape-to-concept.md), not folded into this one.

**Eleventh round, 2026-08-24 — the core "does this belong here" question shifts from open to a real leaning toward yes.** After stepping away from the prototype for a bit, the user's own words: "there is actually real value to be gotten from having this security angle baked in. The tool is all about HIGH CONTEXT diagrams, and security is one such important context." This is the first time this epic's central question has moved past "completely unresolved" — not a final decision on *which* mechanism (mode-switch vs. per-shape facet is still open), and not a commitment to build the full thing, but a real, citable argument for keeping it in this app rather than spinning it out separately, on record for whenever the mechanism question is actually settled.

Directly alongside that shift, the user raised a standing concern that applies regardless of which mechanism wins: this app "should not force you to use its advanced options" — the base case (shapes, edges, containers) must stay exactly as simple as it's always been for someone who never touches Details, linked diagrams, highlights, or a security matrix. Formalized as [ADR 0054](../../../decisions/0054-progressive-disclosure-for-advanced-features.md) (its own thing, not folded into this epic, since it's a standing rule for every feature this app has or will have) — and now a hard constraint on however epic 0060 itself eventually gets built, not just a nice-to-have.

**Still true, unchanged by any of this:** no decision on *which* of the two mechanisms (mode-switch vs. per-shape facet) is right, and no decision on how data would actually flow between the diagram and matrix sides. This prototype exists purely to make that conversation concrete, not to preempt it — the shift above is about *whether*, not *how*.

**Twelfth round, 2026-08-25 — mechanism decided, epic closed.** The branch was brought up to date with `master` (which had moved ahead by epics 0075/0076 since this branch was cut) and merged cleanly — `typecheck` clean, no unresolved conflicts. Merging `epic/0060-threat-risk-matrix` into `master` itself is the user's own action, not done by Claude.

**Thirteenth round, same day — the mode-switch/per-shape-facet question wasn't actually either/or.** Corrects this round's own first pass (which had framed mode-switch as beating per-shape facet outright). The user's own synthesis, prompted by reflecting on why the persistence problem existed at all: "if the data is fundamentally a part of the shapes, and the matrix is just a visualization of that, then it is persisted." Per-shape facet is the *data model* (threat/risk entries live on nodes — and possibly edges, still open, see below); the mode-switch is the *view* that reads and aggregates that data — never a second, separately-persisted store of its own. This also directly delivers the user's other stated want: a "Security" section wherever a single shape's own info is shown, so looking at one service doesn't require scanning a potentially long matrix for its row. Diagram-level configuration (the threat catalog, the probability/consequence scales, the calculation modes) stays a small diagram-level area, not per-element — the matrix's row/column structure and math are shared, only the scores themselves are per-element. Formalized as [ADR 0055](../../../decisions/0055-security-data-lives-on-diagram-elements.md). [ADR 0054](../../../decisions/0054-progressive-disclosure-for-advanced-features.md) (progressive disclosure, referenced since the eleventh round but never actually written down) was also formalized this round, since it was found to be missing as an actual file — the eleventh round's note claimed it existed.

The user also restated a standing principle while making this call, worth keeping on record verbatim in spirit: **the diagram remains the core and centre of the application — the security matrix and everything like it exists to supplement and enhance understanding of the diagram, not to become a parallel thing the diagram is subordinate to.** This is the same instinct ADR 0054 already codifies (advanced features must not encroach on the base experience), stated here from the other direction — a reason *for* keeping security data anchored to diagram elements rather than a reason to keep it out of view.
