# 0035: Propagate required tags to linked children

## Status
Done, merged to `master` (#19, alongside epic 0024). User confirmed after testing: "verified, merged."

## Goal
A "Copy to children" button on the Required Tags panel that pushes the current diagram's `requiredTags` template down its entire link subtree, so a complex view built from many linked sub-diagrams doesn't need the same required tags redefined by hand in every one. Raised directly by the user while testing epic 0024 (multi-window) — depends on epic 0034 (required tags themselves) and the linked-diagram model from epic 0009.

Design resolved in [ADR 0024](../../../decisions/0024-propagate-required-tags-to-children.md): merge (parent wins on key collision, child's own extra tags survive), recurse the whole subtree with a pre-write preview/confirmation, and never cross outside the root diagram's own directory tree — a link can legitimately point at an externally-owned diagram (ADR 0005), and propagation must not reach into one just because something in the chain links to it.

## Tasks
- [x] `src/main/requiredTags.ts` (new): recursive directory-bounded link-tree walk, shared by a read-only preview and the actual merge+write, with cycle protection (visited-path set) and a boundary check (`isUnderRoot`) that skips — and does not recurse past — anything outside the root diagram's own **colocation folder** (`<dir>/<basename>/`, not just its containing directory — a plain sibling `.chd` is external too; see the bug note below).
- [x] `requiredTags:previewChildren` IPC (dry run: walk only, no writes) and `requiredTags:copyToChildren` IPC (walk + merge + write each reachable file, skipping a no-op write when the merge doesn't actually change anything), both returning `{ reached, external, unreadable }` absolute-path lists so the caller can show a clear summary — never a silent partial success.
- [x] Preload: `previewRequiredTagsChildren(diagramPath, directChildRelativePaths)`, `copyRequiredTagsToChildren(diagramPath, requiredTags, directChildRelativePaths)`.
- [x] `Canvas.tsx`: `copyRequiredTagsToChildren` gathers the current diagram's *direct* linked-node relative paths from live `nodes` state (deeper levels come from disk during the walk — see ADR 0024), calls preview, confirms with the user, then calls copy and reports the result. Both the confirmation and the result list the actual relative paths involved, not just a count — the user asked for this directly, on the reasoning that a count alone doesn't let you verify *which* diagrams are about to be touched before committing. `requiredTags.ts`'s `WalkResult` returns display-relative paths (relative to the root diagram's own directory, e.g. `main/internal.chd`) rather than absolute ones, computed via a new `toDisplayPath` helper.
- [x] `RequiredTagsPanel.tsx`: new "Copy to children" toolbar button (same placement pattern as `DiagnosticsPanel`'s "Recheck"), disabled when there are no required tags to copy. Guards against no `currentPath` (links can't be resolved from an unsaved diagram) with an alert, same pattern as `handleLinkClick`.
- [ ] **Your manual click-through pass**: a parent with a nested subtree of linked children (including one child with its own extra required tag, and one link pointing outside the parent's folder) → Copy to children merges correctly into every internal descendant, leaves the child's own extra tag intact, and never touches the external link's target. `npm run typecheck`/`lint` both clean (lint's 4 remaining errors are the pre-existing epic 0028 baseline, confirmed by file/line match — one new React-Compiler "existing memoization could not be preserved" diagnostic came up on the first pass of `copyRequiredTagsToChildren` and was resolved by restructuring away from `let`-reassignment-across-`await` toward `.catch()`-returning-`null`, not suppressed).

## Notes
Deliberately not built: per-key conflict resolution UI (silent parent-wins merge instead), and any live update of already-open windows showing an affected child — those windows won't reflect the change until reloaded, same accepted limitation as everywhere else in the app without dirty-tracking (epic 0020).

**A real bug caught during the user's own testing, not during design**: the external-link boundary was anchored at the root diagram's containing *directory*, not its colocation folder — so a plain sibling `.chd` sitting right next to the root diagram (not nested inside `<basename>/`) was wrongly treated as internal and got written to. The user caught this directly with a concrete repro tree (`root/main`, `root/external`, `root/main/internal`) and correctly diagnosed the likely cause before it was even confirmed. Fixed by anchoring the boundary at `colocationDirFor(rootPath)` instead of `dirname(rootPath)` — see [ADR 0024](../../../decisions/0024-propagate-required-tags-to-children.md)'s Consequences.

**A second, unrelated bug caught in the same testing pass**: linking to a diagram via the node right-click menu ("Link to diagram…") silently did nothing, while Ctrl/Cmd+click worked. Root cause was in `ContextMenu.tsx`, pre-dating this epic entirely (confirmed via `git diff` — this epic and epic 0024 never touched that file): its item-click handler called `item.onSelect()` then unconditionally `onClose()`. When `onSelect` itself opens a *new* context menu (exactly what "Link to diagram…" does, via `handleLinkClick`'s create-new/link-existing chooser), both go through the same `setContextMenu` state — the subsequent `onClose()` call nulled the just-opened chooser out in the same synchronous batch before it ever rendered. Ctrl/Cmd+click bypasses the outer menu entirely, so it never hit this. Fixed by swapping the order (close, then select) in `ContextMenu.tsx`, which is generic enough that this fix isn't specific to linking — any future menu item that opens another menu benefits too.
