## Goal
Two purposes under one epic:

1. **Dogfood the tool on itself.** Document this tool's own architecture and design using nothing but its own features — a **technical view** and a **functional view**, built as real `.chd` files that ship as examples.
2. **Build a broad gallery of generic example diagrams** — one attempt per standard architecture/IT diagram type an architect might reach for — to find out concretely where this tool's flexibility holds up and where it breaks down. These are illustrative/fictional content, not about this tool.

Per [ADR 0008](../../decisions/0008-tool-scope-includes-ea-adjacent-diagrams.md), the gallery explicitly includes enterprise-architecture-adjacent diagram types (business capability maps, motivation/goals views, application portfolios), not just software/technical diagrams — the tool is meant to take an architect most of the way toward proper EA tooling, not just software-architecture diagramming.

**Coverage target: every architect discipline, not just technical ones.** Data architect, business architect, enterprise architect, solution/technical architect, integration architect, security architect, infrastructure/cloud architect — the gallery below is organized by discipline specifically so gaps are visible per-persona. Nothing gets excluded just because it's awkward; an entry only gets dropped if it turns out to impose real, undue complexity or usability cost on the *other* use cases (e.g. a feature that would make simple diagrams harder to build in service of a niche notation). That's a judgment call for whoever's reviewing progress here, not something to pre-empt by leaving a discipline thin.

This runs **continuously alongside normal development epics**, not as a single bounded deliverable — see Notes.

- **Tenth round, 2026-08-22: #1 built at real scale, expanded scope for the required-tags template.** The user's own framing for #1 went well beyond the original candidate description — "a large organisation with hundreds of services," each service tagged with 5 required tags (GDPR data-sensitivity, NIS2 regulatory scope, owning team, business domain, lifecycle state) and a highlight defined for every possible value of every tag. Design conversation before building: employees are represented only via the "Owning team" tag, not as separate shapes (keeps the diagram to one coherent node kind); scale target settled at ~70 services rather than the literal "hundreds" first suggested, to sanity-check the approach at a size this tool has never actually been exercised at before going further; tag values proposed by Claude against the existing Meridian Rail lore and confirmed/adjusted by the user (GDPR became a 4-level sensitivity scale — No PII / Pseudonymized / PII / Sensitive PII — rather than a binary; Service state became a 7-stage lifecycle — Planned / In Development / Released / Maintenance / Phasing Out / Replaced / Retired — synthesized from the user's own example terms, which had some redundant near-synonyms). Built via a one-off generator script (not committed — hundreds of tagged, positioned nodes aren't practical to hand-write the way the C4 chain was), producing 70 services across 10 business-domain `container` nodes in a grid, each service carrying all 5 tags via a seeded weighted-random assignment biased per domain (e.g. Customer Experience skews PII-heavy and NIS2 Essential; Data & Analytics skews Pseudonymized and In Development, matching the modernization narrative). 36 highlights (one per tag value across all 5 tags), every one confirmed to match at least one service in the generated data — two lifecycle states initially landed on zero services by chance and were forced onto two narratively-fitting legacy services rather than re-tuning weights against the fixed seed. No inter-service edges — the ask was tags/highlights/organization, not a dependency map; can be added later if wanted.
