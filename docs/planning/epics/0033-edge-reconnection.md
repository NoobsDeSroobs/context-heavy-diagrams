# 0033: Edge reconnection

## Status
Done, merged to `master` (#16, alongside epic 0014). Revised twice on 2026-08-19 after user testing caught two real bugs (see Implementation notes), both fixed. The post-fix void-drop path was never explicitly re-confirmed as its own item after merge, but edge reconnection has been exercised constantly through dozens of subsequent epics with no issue ever reported against it.

Implemented on the epic 0014 branch rather than a fresh one, deliberately: it directly reuses that epic's `AnchorNode`, and starting a second unmerged branch while 0014 is still in flight would violate this project's own one-epic-at-a-time discipline. Kept as its own epic doc anyway (not folded into 0014's) since it's a genuinely distinct, separately-nameable capability — grabbing an *existing* edge's endpoint, not creating a brand-new edge.

## Goal
Grab either end of an existing edge and drag it to a different attachment point, while the other end stays put — so a connection that made sense on one side of a shape (e.g. "left") can be moved to a better-fitting side (e.g. "top") after the diagram gets rearranged, without deleting and redrawing the whole edge. Raised directly by the user, motivated by exactly that scenario. Explicit requirement: dropping the grabbed end on empty canvas (instead of another handle) must not just cancel — it should spawn a placeholder the same way epic 0014's brand-new-edge-into-empty-space already does.

## Tasks
- [x] Enable React Flow's native edge-reconnection (`edgesReconnectable` + `onReconnect`, using its `reconnectEdge` utility) — this interaction is a built-in React Flow feature, not something built from scratch
- [x] `onReconnectEnd`: detect a drop on empty canvas the same way `onConnectEnd` already does (see `isVoidDrop`), and if so, spawn an `AnchorNode` and re-point the dragged end at it, offering the same Shape/Container popup
- [x] Reuse, don't duplicate, epic 0014's anchor-spawn + popup logic

## Implementation notes (2026-08-19)
- **Native React Flow feature, not a custom build.** `edgesReconnectable` (defaults to `true` once `onReconnect` is provided, set explicitly here for clarity) plus `onReconnect={onReconnect}` on `<ReactFlow>` is the entire "grab an edge's end and redrop it on a different handle" interaction — React Flow handles the drag, the hit-testing (including the same `connectionRadius` proximity as new connections), and hands back `(oldEdge, newConnection)`. `onReconnect` just calls `reconnectEdge(oldEdge, newConnection, eds)` (React Flow's own utility, same shape as `addEdge`) inside `setEdges`, after a `pushSnapshot()` — identical pattern to `onConnect`. This covers the user's motivating example directly: dragging an edge's end from one handle to a different handle on the *same* node (e.g. `'left'` → `'top'`) works exactly the same as dragging it to a different node entirely, no special-casing needed.
- **`onReconnectEnd` mirrors `onConnectEnd`, refactored to share code rather than duplicate it.** Two small helpers extracted to module scope: `isVoidDrop(event, connectionState)` (the same `!connectionState.isValid` + `react-flow__pane`-target check `onConnectEnd` already used, now shared instead of copy-pasted) and `pointFromEvent(event)` (mouse vs. touch coordinate access). A new `spawnAnchorAt(clientX, clientY, wireEdge)` callback holds the actual "create the anchor, let the caller wire whichever edge end needs it, open the Shape/Container popup" logic — `onConnectEnd` and `onReconnectEnd` each just do their own `isVoidDrop` check and pass a different `wireEdge` closure (`addEdge` a brand-new edge vs. `setEdges` patching whichever of the existing edge's `source`/`sourceHandle` or `target`/`targetHandle` was actually dragged loose — see the second bug below for what that determination actually requires, which is less obvious than it looks).
- **No ref needed to bridge start→end** for `onReconnectEnd` itself, unlike the epic-0014 connect-from-a-node case: React Flow's `onReconnectEnd(event, edge, handleType, connectionState)` hands over the edge and which end directly, so there's nothing to track across the gesture. (A ref *was* needed for a different reason — see the bug fix below.)

- **Bug (found by user testing): dropping a reconnected end in the void created *two* edges into the anchor, not one.** Root cause, confirmed by reading `@xyflow/react`'s source directly rather than guessing: React Flow's own `EdgeUpdateAnchors` implementation fires **both** the generic `onConnectStart`/`onConnectEnd` **and** the specific `onReconnectStart`/`onReconnectEnd` for the same drag-an-existing-edge's-endpoint gesture — its internal `_onConnectStart` composite literally calls `onReconnectStart?.(...)` immediately before `onConnectStart?.(...)`, every time, with the *opposite* (fixed) end's node/handle as the params. So on a void drop, `onConnectEnd` (epic 0014's logic, thinking a brand-new connection started from the fixed end) and `onReconnectEnd` (epic 0033's logic, correctly re-pointing the existing edge) both ran independently, each spawning its own anchor+edge landing at the same drop position — two anchors stacked on top of each other, each with one edge, read by the user as "two edges connected to the anchor."

  Fixed with a new `isReconnectingRef`: `onReconnectStart` (now wired, previously wasn't) sets it `true` — since React Flow calls it before `onConnectStart` within the same synchronous composite, `onConnectStart` can check it and skip arming `connectStartRef` (leaving it `null`) whenever the "connect start" it's seeing is actually the side-effect of a reconnect drag, not a genuine new connection. With `connectStartRef` never armed, `onConnectEnd`'s existing `if (!origin ...) return` guard already handles the rest — no change needed there. `onReconnectEnd` resets the flag back to `false` once the gesture is fully over. `onConnectEnd`'s own logic and `spawnAnchorAt`/`isVoidDrop` were correct throughout; the bug was purely "which handler should even run," not the anchor-creation logic itself.

- **Second bug (found by user testing, after the first fix): the end that ended up attached to the anchor was the *opposite* end from the one actually dragged.** Root cause: `onReconnectEnd`'s `handleType` argument was misread as "which end is being dragged." It's actually the opposite — React Flow's `EdgeUpdateAnchors` source shows the mousedown handler for grabbing the *source* anchor calls through with the *target*'s type (`{ nodeId: edge.target, id: edge.targetHandle, type: 'target' }`), and vice versa for grabbing the target anchor — because internally, a reconnect drag is implemented as "start a normal connection drag *from the fixed/opposite end*," so `handleType` naturally describes that fixed end, not the one actually moving. The original code branched `handleType === 'source' ? patch source : patch target`, which patches the *fixed* end instead of the dragged one — exactly backwards. Fixed by inverting the branch to `handleType === 'target' ? patch source : patch target` (target fixed ⇒ source was dragged, and vice versa), with a comment on-site quoting the source behavior directly rather than leaving it as a fact someone has to rediscover by testing.
- **Considered writing a separate ADR for "reuse `AnchorNode` on a reconnect void-drop" — decided against it.** The interesting decision (a placeholder node as the answer to "an edge needs *some* valid endpoint, even before the user picks one") is already [ADR 0015](../../decisions/0015-anchor-placeholder-node.md)'s; this epic just applies that same, already-settled answer to a second trigger path. There wasn't a real fork of alternatives debated here — using React Flow's native reconnect API over hand-rolling one wasn't a close call, per the bar in [docs/decisions/README.md](../../decisions/README.md) ("if we seriously debated alternatives, write it down"). Flagging this judgment call explicitly rather than silently skipping it, given how much ADR coverage was found to be missing earlier this same session — if it turns out to feel wrong in retrospect, it's cheap to write one up after the fact.

**Verification**: the user manually tested the drag/reconnect mechanics directly (this environment's own browser-automation tooling still can't drive React Flow's drag interactions, so this was entirely the user's own testing, not this session's). Confirmed working: reconnecting to a different handle, both same-node and different-node. Two bugs found in the void-drop path specifically (see above, both now fixed) — neither re-verified live yet, since both fixes landed after that testing pass. `tsc --noEmit` and `eslint` are clean (no new errors beyond the same pre-existing baseline). Worth a follow-up manual check specifically: drop a reconnected end in empty canvas and confirm (1) exactly one anchor with exactly one edge results, not two, and (2) the anchor ends up on the end that was actually dragged, with the other end of the edge unchanged.
