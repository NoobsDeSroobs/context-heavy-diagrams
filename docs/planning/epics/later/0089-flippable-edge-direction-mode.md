# 0089: Flippable edge direction — data flow vs. invoker/trigger direction

## Status
Not Started — idea only, not yet scoped, but has a leaning direction from a design conversation with the user (2026-08-24)

## Goal
Sometimes an edge's arrow should show the direction data actually flows; sometimes it should show who authenticates/triggers the interaction (which is often the *opposite* direction — e.g. a client polling a server is data flowing server-to-client but triggered client-to-server). Let a diagram show either, switchably, rather than being locked to whichever one was drawn.

## Leaning design (not committed — refined once, not a spec)
- **Named, user-managed "arrow sets"** — a dropdown somewhere lets the user create/rename/copy a named set (e.g. "Data flow," "Trigger direction"), the same general shape as the not-yet-built active-palette selector in [epic 0074](../completed/0074-multiple-named-style-palettes.md). Every diagram starts with one default set.
- **Every edge stores a connection-point pair per set, not just markers.** An edge already has a source connection point and a target connection point (`sourceHandle`/`targetHandle`, plus the `source`/`target` node ids). The user's proposed shape: a dictionary keyed by set name, each value a `{source: {nodeId, connectionPointId}, target: {nodeId, connectionPointId}}` tuple. **This resolves the open question the first pass of this doc raised** (see below) — direction doesn't need a separate cosmetic-vs-structural concept at all: switching the active set is just "read this set's tuple, write it into the edge's real `source`/`sourceHandle`/`target`/`targetHandle`." Since a marker's start/end is already derived from which end is currently source vs. target at render time (`LabeledEdge`), start/end markers automatically follow the swap for free — no separate per-set marker storage needed.
- **The dropdown picks which set is *active* diagram-wide** — switching it reads every edge's tuple for the newly active set and applies it. Not destructive: the other sets' tuples stay stored, untouched. ("Mass selecting them based on the diagram level dropdown," the user's own framing.)
- **"Flip direction" only touches the currently-active set** — flipping while "Data flow" is active swaps that set's own stored tuple (and applies it immediately, since it's active) without touching "Trigger direction"'s separately-stored tuple.
- **Renaming/deleting a set is a plain rename/delete, not a demotion.** The user's own correction to this doc's first pass: unlike Required Tags (where a value might be real, manually-entered element data worth preserving even after its key stops being required — ADR 0022's "don't destroy data" rule), an arrow set's per-edge tuple is fully app-managed, derived-from-the-diagram data, not something a human directly typed in that could be lost. Deleting a set just deletes its key from every edge's dictionary and the registry; renaming just migrates the key in both places atomically. No leftover/orphan-preservation step needed, unlike the [required-tag rename bug logged earlier today](../../../known-issues.md#adding-a-new-required-tag-immediately-stamps-its-placeholder-key-onto-every-element-then-demotes-it-to-a-stray-free-tag-on-rename) — that bug's specific failure mode (demote-not-delete leaving a stray copy behind) doesn't apply here, precisely because there's nothing here worth demoting-to-preserve.

## Superseded: the `included`-flag/filtering approach
A prior revision of this doc settled on one canonical edge per logical connection, with a per-(edge, set) `included` boolean, filtered at render time. **Superseded by the Derived/Independent model below** — not wrong exactly, but the user found a real problem with the layer underneath it (see "The identity-key problem" below) while designing further, and the fix that resolves it also makes a cleaner mechanism for exclusion than a per-edge boolean. Kept here for the record, not as the current design.

## Current leaning design: Derived vs. Independent sets, grouped by `groupId`
Two explicit kinds of set, chosen by the user at creation time — this directly matches "generic tool, can't assume symmetry" better than a single global storage strategy, by making the symmetric/asymmetric choice per set-family rather than per edge:

- **Derived set**: locked to showing exactly the same edges as every other set in its family — no independent inclusion/exclusion — but shares style/label/metadata/bend-points with them, differing only in direction (which connection points each end uses). This is the technical-documentation case: "Data flow" and "Trigger direction" as two derived sets of one family are guaranteed 1:1 by construction, not by convention.
- **Independent set**: an entirely separate pool of edges, full customization, nothing shared with any other family. This is the business-mapping case: "Responsibility" and "Cost flow" can legitimately have different edges, because they're different families entirely.
- **`groupId`, an integer, marks which family a set belongs to.** Creating a new *derived* set gives it the same `groupId` as whichever set is currently active (it derives from that one). Creating a new *independent* set mints a fresh, never-before-used `groupId`, starting its own family. Simple, sequential, no special-casing needed to answer "which sets share edges with which."

## The identity-key problem this design had to solve, and how
The user's own mid-design catch, before landing on the model above: if a shared edge's identity were keyed by *which connection points it touches* (an earlier framing — "one master set... using the connection points as the key"), then dragging that edge's endpoint to a different connection point in one set breaks its own key. The two options that leaves are both bad: silently re-key it (so the *other* sets sharing it now can't find it anymore under its old key) or "extract and simulate adding another" (create a second entry under the new key) — which risks unbounded bloat over time and, worse, means the old-key and new-key entries no longer share properties at all, defeating the entire point of a shared edge.

**Resolution: don't key shared identity by connection points at all — keep using the edge's own stable `id`**, exactly like everything else in this schema already does (required tags, style, metadata are all keyed by an element's `id`, never by its structural position). Within a derived family, the per-set data that can legitimately differ is a `{sourceHandle, targetHandle}` override tuple keyed by set name, layered on top of one canonical edge identified by its own unchanging `id`. Dragging an edge's endpoint while "Data flow" is active just updates the `(edgeId, "Data flow")` tuple — the edge's `id`, and everything else about it, never changes, so there's nothing to re-key and nothing that can bloat from being dragged around.

## Edge-creation-time dedup — the user's original ask this session
"Check on edge creation if the new edge already exists and is simply hidden in this set." With the model above: within a *derived* family, this mostly resolves itself — since membership is locked identical across the family by construction, there's no "hidden, not deleted" state to check for at all; a new edge drawn while any family member is active is added to the family's one shared pool and every sibling set shows it immediately (each starting with some default direction). The dedup check that *does* still matter: before creating a brand-new edge object from a drag gesture, check whether an edge already connects the same two connection points (in the active set's family) — if so, this should be treated as adjusting that existing edge's direction/tuple for the active set, not spawning a duplicate parallel edge. **Not yet resolved**: this app already allows genuinely-intentional parallel edges between the same two nodes elsewhere (not itself a bug) — a naive "same node pair already connected" check would incorrectly collapse two deliberately-distinct edges into one. The dedup check likely needs to key on the *exact* connection-point pair, not just the node pair, to avoid that false-positive.

## Real open questions this leaning design still doesn't resolve
- **Is "no partial exclusion within a derived family" really intended, including the 95%-symmetric case?** E.g. two sets that should share 9 of 10 edges, differing only in direction, but genuinely need a 10th edge in just one of them. Today's model forces that into becoming a fully independent family instead — losing shared properties for *all ten* edges, not just the one exception. Worth confirming this is an acceptable trade rather than something that'll turn out to be a real recurring annoyance.
- **What happens to a family's edge when the underlying connection points themselves change** — e.g. a shape's connection point count/spacing changes (epic 0039), or a point is deleted? A `(edgeId, setName)` tuple pointing at a now-nonexistent `connectionPointId` needs a defined fallback.
- **Does a brand-new edge need a real tuple seeded for every set in its family immediately**, so no set is ever caught relying on a "missing, falls back to the family's default set" safety net in normal operation (the user's own framing from an earlier pass — that fallback should structurally never actually fire)?
- **Where does the set-management UI (dropdown, New Derived/New Independent, rename, copy) physically live?** Same open question epic 0074 already has for its not-yet-built palette selector — worth resolving both together, same UI pattern.
- Copying a set within a derived family: same tuples as the set it was copied from, or blank/default?
- Diagram-level data, not a Setting — per [ADR 0052](../../../decisions/0052-settings-ownership-tiers.md)'s ownership-tier glossary, the set registry (including `groupId`s) and the active-set pointer are per-diagram, not per-user.
- Is a set's scope *only* direction (the connection-point tuple), or does the user also want per-set marker/line style (e.g. "Trigger direction" always dashed)? The tuple-swap approach makes marker *direction* free (start/end follows source/target), but a deliberately different visual *style* per set is a separate question this hasn't touched yet.

## Notes
Raised by the user 2026-08-24, refined across five passes the same day. (1) Named sets stored per-edge, active set chosen diagram-wide via dropdown, flip scoped to the active set only. (2) Storage shape is a source/target connection-point tuple per set, not per-set markers. (3) Surfaced that React Flow can't cleanly represent "this edge is disabled under the current set." (4) Settled — temporarily — on one canonical edge with a per-set `included` flag, filtered at render time, over a full independent edge list per set. (5, this revision): while designing further, the user caught a real problem with keying shared identity by connection points (dragging breaks the key, forces a bloat-or-lose-properties choice) — resolved by keeping the edge's own `id` as identity and layering a `{sourceHandle, targetHandle}` tuple on top, and reframed exclusion as a property of the *set kind* (Derived vs. Independent, grouped by `groupId`) rather than a per-edge boolean, which cleanly supersedes pass (4)'s `included` flag. Still explicitly not committed to as a full spec — needs a real design pass before any schema/implementation work starts, but the identity model and the derived/independent split are now reasonably settled.
