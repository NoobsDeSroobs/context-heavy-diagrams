# 0004: Containers

## Status
In Progress

## Goal
Container shapes that group nodes using React Flow's parent/child relationships, so child nodes move together with their container automatically — without becoming a separate "grouping" mechanism that's hard to edit individual elements within.

## Design
See [ADR 0012](../../decisions/0012-container-node-design.md) for the full reasoning. Summary:
- **Connectable, not rotatable** — same category as `ShapeNode`, confirmed against a brief conflict (brief says containers should rotate; rejected for now since rotatable+connectable requires solving rotated-handle-position math that ADR 0004 already deferred once).
- **Deleting a container promotes its children** (reparented to the container's own parent, or top-level) rather than cascading the delete to them.
- **Nesting containers is allowed**, not restricted — cheaper to allow than to add validation blocking it.
- New `parentId?: string` field on `DiagramNode`, mapping to React Flow's native `Node.parentId`. **No `extent: 'parent'`** — tried initially (to clamp a child's position to its container's bounds), reverted after user testing found it made dragging a node back *out* of a container impossible: `extent: 'parent'` hard-clamps a node's position during any drag, so a child could never actually be moved past its container's edge, meaning the un-parent-on-drag-out logic never got a real "outside" position to detect. Consequence: a container's children aren't visually clamped when the container is resized smaller — a child can end up poking outside its (now-shrunk) container. Accepted as v1 behavior, not a bug: predictable drag-out beats resize-clamping given the two are currently mutually exclusive with this library's API.
- **"Attach contained shapes"** (added after initial implementation, from real user testing — see Notes): a container's right-click menu item that bulk-reparents every currently-top-level node fully inside its bounds, instead of requiring one drag per node. Deliberately scoped to top-level (unparented) nodes only — a node already inside a different container is left alone, not silently moved out of it.

## Notes
Implemented 2026-08-19. Verification done:
- `npm run typecheck` and `npm run lint` clean on all touched/new files.
- Smoke-tested in the browser via the Vite dev server (`http://localhost:5173`, renderer only — no Electron shell/`window.api`, so this doesn't exercise save/load): added a container, shape, and text node with no console errors; container resize handles render; connection point right-click menu present (shared code path with `ShapeNode`, already exercised by epic 0013).
- The trickiest part — coordinate math for nested reparenting and the parent-before-child array ordering invariant, including a container-inside-a-container delete case and a cycle-safety check — verified with a standalone script (10/10 assertions passing, not committed to the repo — this project has no test runner set up, see below).
- Right-click context menus (on both `ShapeNode` and `ContainerNode`) turned out to be scriptable via synthetic `dispatchEvent` after all, once the event was dispatched on the actual inner element with the listener (not the outer React Flow node wrapper) and the DOM was re-queried in a separate call after the dispatch (React's own update commit happens asynchronously relative to the dispatch call returning). Used this to confirm `attachContainedNodes`'s candidate-detection found exactly the expected node.

**User-reported bug, fixed same session**: dragging a *multi-selected* group of nodes into a container only reparented the single node under the cursor, not the rest of the selection. Root cause: `onNodeDragStop`'s original implementation only read its second callback argument (the grabbed node), ignoring React Flow's third argument — the full list of every node that moved as part of that drag. Fixed by iterating all of them, each checked against its own geometry independently (an important detail: a container being drag-selected alongside other nodes must be checked against *its own* intersecting containers, not the grabbed node's).

**Also added, from the same feedback**: an explicit "Attach contained shapes" menu item on the container, for bulk-encapsulating a lot of already-positioned free-floating shapes at once instead of one drag per shape. Deliberately scoped to top-level (unparented) nodes fully inside the container's bounds — reaching into other containers isn't in scope for this action.

**Second round of user testing (same day) found three more bugs, all fixed:**
1. **Opening an existing diagram and clicking "Add container"/"Add shape" deleted the already-placed nodes and replaced them with new ones.** Root cause: the in-memory id counter (`nextId`, module-scope, starts at 1 every session) had no awareness of ids already used in a *loaded* file. A diagram saved by an earlier session already has nodes like `container-1`/`shape-2`; opening it in a fresh session and clicking "Add shape" regenerated `shape-2` again — same id, so React Flow's id-keyed internal store treated it as an update to the existing node, not a new one, silently overwriting it. Fixed with `syncNextIdPastLoadedIds()`, called once per load from the single `loadDiagramIntoCanvas` choke point (also covers link-navigation and breadcrumb back-nav, not just Open).
2. **Dragging a shape out of a container didn't work — it stayed stuck inside the container's bounds.** Root cause: `extent: 'parent'`, added on children specifically so they'd stay visually inside their container, is a hard clamp React Flow applies to *every* position update for that node, including a drag meant to pull it back out — the node could never actually reach a position outside the container in the first place, so the un-parent-on-drag-out logic never saw anything to detect. Removed `extent: 'parent'` entirely; see Design for the resulting resize-clamping tradeoff.
3. **New shapes/containers/text spawned at a fixed canvas-coordinate origin**, invisible off-screen on a large, panned/zoomed diagram. Now computed from the current viewport's visual center via `rfInstance.screenToFlowPosition`, confirmed in-browser to land exactly at the window's center point.

**User pushback on fix #1's approach**: after landing the sync-on-load patch for the id collision, the user asked why bother with a sequential counter at all rather than a real globally-unique id — correctly identifying that the patch fixes the *known* collision path (opening a file) but not the underlying fragility (any future path that generates ids independently — e.g. epic 0025 copy/paste between diagrams, or two people editing separately — would need its own patch too). Replaced `nextId`/`syncNextIdPastLoadedIds` entirely with `crypto.randomUUID()`-suffixed ids (`shape-<uuid>`), removing both the counter and the sync call — simpler code than the patch it replaced, not just a different bug fix. Kept the readable type prefix rather than a bare UUID, consistent with this project's git-diff-friendly/human-debuggable file format goals.

**Not independently verified — still needs your interactive check**, same category as epic 0006/0013/0018's leftover items: dragging a node back out of a container now that `extent: 'parent'` is gone, and nested containers in the actual UI. Drag-based interactions (unlike right-click menus, and unlike toolbar-button clicks) still can't be driven by browser automation here — React Flow's custom pointer-capture drag/selection system doesn't respond to synthetic `PointerEvent` dispatch, only real input. This is a tooling limitation, not a sign of a code problem.

**Container deletion actually promoting a real child — the one item in the list above that WAS eventually tried and turned out to be genuinely broken**, not just unverified. Reported by the user after merging epics 0003 and 0011: "Deleting a container deletes all contained shapes." Root cause confirmed by reading `@xyflow/system`'s source directly (not guessed at): React Flow's `deleteElements`/`getElementsToRemove` cascades a `remove` `NodeChange` to every descendant automatically whenever a parent is deleted — even though only the container itself was selected. This epic's original `onNodesChange` guard (`containerRemovalIds`) only ever stripped the *container's own* remove-change from what reaches `onNodesChangeBase`; the cascade-included children's remove-changes were never stripped, so they got deleted via the normal path before `removeContainerReparenting` ever ran — by the time it did, there was nothing left to promote. This bug predates epics 0003/0011; it was simply never exercised with a real nested child until now (see the "not yet interactively confirmed" note this task item originally carried). Fixed on branch `fix/container-delete-cascade`: the guard now also walks the `parentId` chain to catch transitive descendants (not just direct children) of any container being removed, stripping all of their remove-changes too, so `removeContainerReparenting` has the full, unmodified node list to work with. Verified the filtering logic directly (including a 2-level-nested-container case and a case where an unrelated, independently-selected node is deleted alongside the container) — the live in-app behavior still needs your check, same browser-automation limitation as everything drag-related in this epic.

**No test runner exists in this project yet** — the standalone verification script lived in the scratchpad, not the repo, and is gone. If container/hierarchy logic like this keeps growing (epic 0011 alignment/snapping and epic 0024 tabs will likely touch similar coordinate math), a real unit test setup (e.g. Vitest, already a natural fit for a Vite-based project) might be worth its own small epic at some point — not scoped now, just flagging the gap since this session leaned on a throwaway script to get any non-visual confidence at all.

**Icon slots, details, and linked-diagram were deliberately left off `ContainerNode`** in this first pass — the schema (`DiagramNode.data`) already supports them uniformly across node types, so adding that UI later needs no schema change, just JSX. Not in the original task list; skipped to keep this epic scoped to grouping/resize/connect.
