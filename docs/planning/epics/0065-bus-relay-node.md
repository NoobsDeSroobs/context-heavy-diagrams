# 0065: Bus/relay node — a pass-through connector with scalable point count

## Status
Not Started — not yet scoped. Raised by the user (2026-08-22), explicitly as a far-out idea to research later, not to be designed or built now: "I will leave it here as this is too far out from my comfort zone to be able to say anything without research and testing."

## Goal
Upgrade the existing placeholder `AnchorNode` (epic 0014 — the small draggable dot spawned when a connection drag is dropped on empty canvas, today only ever resolved into a real Shape or Container) into an optional real node type of its own: a **bus/relay** — modeled on an electromechanical bus (the user's own reference: a memory bus's lanes). Concretely:

1. **Scalable point count.** A configurable number, the node scales in size to fit — not a fixed small circle like today's anchor.
2. **Pass-through pairing, not a hub.** Left and right sides linked to each other; top and bottom sides linked to each other — the relay doesn't terminate a connection so much as let it continue through, visually joining what would otherwise be two separate edges into one continuous line at the relay's own boundary.
3. **Shared properties across the relay.** Style and tags should propagate through the connection when two edges are joined via a relay — the two segments read as one logical connection, not two independently-styled edges that happen to touch.
4. **A hard constraint on the connecting end**: whatever attaches to a relay can only use a plain line end — no arrowheads or other markers — presumably because a pass-through joint shouldn't visually imply directionality or termination the way a normal edge endpoint does.
5. **Stretch goal, explicitly the "if it's possible" version**: not two edges glued at a relay node at all, but **one single edge with multiple required waypoints** it traverses — the relay would then be more like a visual marker on one edge's path than a separate node two edges connect to. The user flagged this as the ideal outcome but is unsure it's achievable, and deliberately didn't want to speculate further without research.

## Relevant existing concepts, not resolved here
- **`AnchorNode` (epic 0014)** is the nearest existing precedent — same "drop a connection on empty space, get a placeholder" mechanism, but today's anchor always resolves into an ordinary Shape or Container, never stays as its own persistent node type. This epic asks whether a relay is a *third* resolution option for that same anchor-drop flow, or a wholly separate item-palette entry.
- **[Epic 0032](completed/0032-edge-routing-and-waypoints.md)** (manual edge waypoints/bias offsets, deliberately deferred) is conceptually close to this epic's stretch goal — a single edge with intermediate points it passes through. Whoever picks either epic up should check the other first; they may turn out to be the same underlying mechanism (waypoints) with two different visual treatments (an invisible bend point vs. a visible, styled relay glyph), or genuinely different.
- **React Flow's edge model is fundamentally two-endpoint** (one `source`/`target` pair per edge) — this codebase's entire edge machinery (`onConnect`, `reconnectEdge`, `LabeledEdge.tsx`'s path building) assumes exactly two ends throughout. The stretch goal (one real edge spanning multiple relay points) is a genuine open technical question, not just a UI design question — whether React Flow supports this natively, or whether it would need to be simulated as several chained edges rendered/selected/edited as if they were one, is unresearched. This is likely the single biggest unknown blocking this epic, more than the visual/interaction design.
- **Style/tag sharing "through" a connection** would be a real departure from this app's established philosophy elsewhere: [ADR 0010](../../decisions/0010-named-searchable-style-presets.md) deliberately rejected remembering *any* relationship between a style choice and where it came from ("nothing 'remembers' that an edge was created via the 'Dependency' preset... raw properties are the only truth") specifically because a remembered link going stale (one side edited, the other not) is misleading. Whoever designs this needs to decide whether "shared through the relay" means a one-time copy at connection time (consistent with existing philosophy) or a live, enforced link between the two segments (a new kind of relationship this app doesn't have anywhere else) — worth being deliberate about which, not assuming the more ambitious one by default.
