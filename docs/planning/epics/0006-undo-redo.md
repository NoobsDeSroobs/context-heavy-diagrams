# 0006: Undo / redo

## Status
Done — continuous-gesture grouping (drag/resize/rotate) was never explicitly re-confirmed as its own item after this epic merged, but undo/redo has been exercised constantly through dozens of subsequent epics with no issue ever reported against it. See Notes.

## Goal
Undo/redo over a reasonable number of steps (not unlimited/branching for v1). Primarily aimed at three real scenarios: accidental/mistaken deletion, mistaken transformations (move/resize/rotate, and later style/container changes), and "the previous text was better."

## Tasks
- [x] Full state-snapshot stack over `{nodes, edges}` (`HistorySnapshot`, `past`/`future` state in `Canvas.tsx`) — generic, not per-field tracking, so it doesn't need revisiting when epics 0003/0004 add new mutable fields. `MAX_HISTORY = 50`.
- [x] Snapshot per completed action, not per pixel-drag/resize/rotate-tick.
- [x] Text edits: snapshot on `EditableLabel`'s `onCommit`, one step per commit.
- [x] Undo stack scope: per-diagram, reset in `loadDiagramIntoCanvas`.
- [x] Keyboard shortcuts: Ctrl/Cmd+Z (undo), Ctrl/Cmd+Shift+Z (redo, Figma-style, resolved during epic 0018). Toolbar Undo/Redo buttons added too (disabled when their stack is empty), matching the discoverability pattern already established for New/Open/Save.

## Implementation notes (the real substance of this epic)

**Architecture: explicit `pushSnapshot()` calls at each mutation site, not a `useEffect` reacting to `nodes`/`edges` changing.** A first attempt used the effect approach — react to the *result* of a mutation rather than intercept every call site, appealing since most real edits (`updateNodeData`, used throughout `ShapeNode`/`TextNode`/`Canvas.tsx` for label/icon/link/connection-point edits, plus direct `setNodes` calls for add/duplicate/save) bypass `onNodesChange`/`onEdgesChange` entirely — React Flow's `updateNodeData` calls its own internal store's `setNodes` directly, not the app's `onNodesChange` prop. But the effect approach broke under React StrictMode's dev-mode double-invoke: the effect's only real "output" was a ref mutation (`lastSettledRef`), and an effect whose side effect isn't safe to run twice is exactly what StrictMode's double-invoke exists to catch — confirmed via manual testing (one `Ctrl+Z` press after two "Add shape" clicks did nothing visible). A cleanup-based fix was tried and rejected too: reversing the ref mutation in the effect's cleanup fixes the StrictMode double-invoke case, but cleanup *also* runs before every genuine subsequent effect execution (standard React lifecycle), which broke real multi-edit sequences by having each new edit's cleanup incorrectly undo the previous edit's push.

Switched to explicit calls instead: `pushSnapshot()` (captures current `{nodes, edges}` onto `past`, clears `future`) is called directly, immediately before the mutation, at every real mutation site — `addShapeNode`, `addTextNode`, `duplicateSelected`, `onConnect`, the `onNodesChange`/`onEdgesChange` wrappers (for canvas-driven drag/resize/delete), and via a new `pushSnapshot` exposed through `DiagramContext` for `ShapeNode`/`TextNode`'s `updateNodeData` call sites (label commit, remove link — connection points once epic 0013 merges). Regular callbacks aren't double-invoked by StrictMode (only render bodies and effects are), so this has no equivalent hazard.

**Continuous-gesture grouping** (drag/resize/rotate → one undo step, not one per tick): `onNodesChange`'s wrapper snapshots once at the *start* of a position/dimension change carrying `dragging`/`resizing: true` (via `beginContinuousEdit`, which no-ops on subsequent mid-gesture calls) and clears the flag on `dragging`/`resizing: false`. Rotation has no such flag from React Flow (`TextNode`'s rotate handler is just repeated `updateNodeData` calls in a `mousemove` loop), so it calls `beginContinuousEdit`/`endContinuousEdit` itself, now exposed via `DiagramContext` for exactly this. A position/dimension change with **no** dragging/resizing flag at all (e.g. React Flow's own keyboard-triggered arrow-key nudge, epic 0018) is treated as discrete — each nudge is its own undo step, deliberately not grouped (matches how keyboard-repeat wasn't grouped for the arrow-key feature itself either).

**Verified interactively** (fixed the StrictMode bug in the process, not just assumed correct): two "Add shape" clicks → `Ctrl+Z` → exactly one node remains (was silently a no-op before the redesign) → `Ctrl+Z` again → zero nodes, Undo correctly disabled → `Ctrl+Shift+Z` ×2 → back to two nodes, Redo correctly disabled. Separately: select a node → Delete key → one node remains → `Ctrl+Z` → the deleted node is restored (confirms the `onNodesChange`-driven `'remove'` path works, not just the direct-`setNodes` `add` path). **Not independently verified**: actual drag/resize/rotate gesture grouping (genuinely needs mouse-drag simulation, which is exactly the category of interaction the user asked to handle themselves after epic 0018) — please confirm dragging a shape across the canvas and rotating a text node each produce exactly one undo step, not many.
