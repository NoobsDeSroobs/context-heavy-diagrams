# 0026: Tagging and overlay visualization

## Status
Implemented — awaiting your manual click-through pass (see last task below) before calling it Done. Depended on [epic 0034](0034-unified-tag-and-metadata-system.md) (tag storage) — done and merged. Remaining open questions from the Notes below resolved via direct design discussion; see [ADR 0025](../../decisions/0025-tagging-and-overlay-visualization.md).

## Goal
Tag nodes and edges with freeform labels, then visualize the diagram *by* tag via a set of user-defined, individually-toggleable **highlights** — each one a tag + a color. Two motivating use cases: tracing a specific data path through a system (which shapes and edges does customer PII actually flow through?), and showing which parts of a large macro/landscape diagram participate in a given business capability, without needing a separate diagram file per concern.

## Design (as scoped in discussion)

**Depends on [epic 0034](0034-unified-tag-and-metadata-system.md)**, which superseded this epic's original tag-storage plan. Tags are `data.metadata` entries (see ADR 0022) — key-value pairs (`GDPR: Sensitive`, not just a flat `gdpr-sensitive` string), either free/human-added or diagram-required, all in one mechanism rather than a separate `data.tags: string[]` field as originally sketched here. This also resolves what was an open question below: a highlight keys off a specific `key`+`value` match (`GDPR = Sensitive`), not mere tag presence. Tagging an element (the "needs its own UI surface, not yet designed" gap noted below) is also resolved by 0034 — it's the same Properties Panel "Metadata" section every Shape/Container/Edge gets, not a separate mechanism to design here.

**Two related concepts, not one:**
- **Tags** — `data.metadata` entries, per epic 0034/ADR 0022.
- **Highlights** — a separate `{ key, value, color }` catalog, managed independently of individual elements (which of them are currently *enabled* is separate session-only state, not part of the catalog itself — see Design below). A highlight doesn't tag anything itself; it's a saved *visualization* of an existing key/value pair.

**Highlights panel** (a new in-app view — see open question below on "panel vs. window"):
- "Add new highlight" reveals a searchable list of every tag currently used somewhere in the diagram, inline in the panel — same searchable-list *concept* already established for icons (`builtinIcons.ts`)/line-style presets (ADR 0010), but as an inline expansion rather than `IconPicker`'s floating anchored popup: this panel already has a fixed dock's worth of space, so no anchor-rect plumbing is needed.
- Pick a tag, and a color is assigned automatically from a small rotating default palette (other properties left open/extensible — "maybe some other things," not specified further yet); the color swatch is editable afterward from the panel row.
- Once added, the panel lists each highlight as: color swatch, tag name, and an on/off toggle. Multiple highlights can be enabled simultaneously — this isn't "pick one active view," it's a set of independently-toggleable overlays.
- Enabling a highlight renders on every matching node/edge — **match-count-dependent** (resolved, ADR 0025): exactly one enabled highlight matching an element → its color applied to the element's border/stroke, drawn slightly thicker (a live rendering override, the actually-stored `style` untouched). Two or more matching → small color chips instead, one per match, no color blending or priority — exact chip placement is an implementation detail, watching for collision with Shape's existing icon-slot corners (epic 0007).
- **No dimming of non-matching elements in v1** (resolved, ADR 0025) — plain default appearance elsewhere.
- **In-app panel** (resolved, ADR 0025), not a second window — same `UtilityDock` shell as `RequiredTagsPanel`/`DiagnosticsPanel`.
- **Split persistence** (resolved, ADR 0025): the highlight *catalog* (`{key, value, color}[]`) is saved to the `.chd` file as `DiagramFile.highlights`; which highlights are currently *enabled* is volatile, session-only, in-memory state — reset to none-enabled on every load, never written back.

## Tasks
- [x] `src/shared/diagram.ts`: `HighlightDefinition = { key: string; value: JsonValue; color: string }`, `highlights?: HighlightDefinition[]` on `DiagramFile`. `serializeDiagram` carries it through (array order preserved, no sorting — same as `requiredTags`); `parseDiagram` needs no change, per its existing no-per-field-validation stance.
- [x] `docs/file-format.md`: new "Highlights" section, plus the top-level structure table/example and the Versioning field-history line, per this project's living-spec convention.
- [x] `Canvas.tsx`: `highlights` state (persisted — loaded in `loadDiagramIntoCanvas`, included in `persistDiagram`'s `toDiagramFile` payload) and a separate `enabledHighlightIds` state (session-only `Set<string>`, reset — never loaded from the file — on every `loadDiagramIntoCanvas`). `addHighlight`/`updateHighlightColor`/`removeHighlight`/`toggleHighlightEnabled` handlers, plus a `usedTags` memo scanning every node/edge's metadata for the picker. A single `matchHighlights(metadata)` closure (not raw `highlights`/`enabledHighlightIds`) is exposed via `DiagramContext`, so node/edge components only need an element's own metadata to get its current matches.
- [x] `src/renderer/src/highlights.ts` (new): `highlightId` (stable key+value identity, used for both the enabled-set and catalog de-duplication) and `matchingHighlights` (pure, shared by `Canvas.tsx`'s `matchHighlights` and reusable elsewhere).
- [x] `HighlightsPanel.tsx` (new, `UtilityDock` surface, same shell/toggle pattern as `RequiredTagsPanel`/`DiagnosticsPanel`, added to the same mutual-exclusion group as the other three dock panels): lists each highlight (checkbox, color swatch, `key = value` label, remove). "Add highlight" is an inline searchable list of tag key/value pairs currently used somewhere in the diagram, not a floating anchored popup like `IconPicker` — this panel already has a fixed dock's worth of space, no anchor-rect plumbing needed. Color editing is a plain native `<input type="color">` per row, not `ColorPickerPopup` (that component is tied to `beginContinuousEdit`/`endContinuousEdit` undo-session semantics that don't apply here — highlight edits aren't part of node/edge undo history, same as `requiredTags` edits already aren't).
- [x] `HighlightChips.tsx` (new): the small color-dot row shown for a 2+-match element — pure content, positioning is each caller's job (`.highlight-chips-anchor` for nodes, an inline-styled translate wrapper for edges, mirroring `EdgeLabelRenderer`'s own label-positioning convention).
- [x] Rendering: `ShapeNode`/`ContainerNode` layer a border-color/width override (`HIGHLIGHT_BORDER_WIDTH = 3`, vs. the default 1.5px) after `nodeContainerCss`, plus chips anchored just above the shape (outside the icon-slot corners, no collision) for 2+ matches. `LabeledEdge` does the equivalent for `stroke`/`strokeWidth`, with chips offset above the label point.

## Notes
**[Epic 0036](0036-grouped-highlights.md)**, logged separately: originally a key-level "macro filter" highlight idea, raised while designing this epic and deliberately left undesigned. The user came back with a simpler "Add group" proposal that fully supersedes it — see ADR 0026. Not this epic's problem to solve either way.

Deliberately not this epic's scope, carried over from the original scoping discussion, not re-litigated:
- **Tag autocomplete while tagging an element** (not just while building a highlight) — natural follow-on once the highlight picker's autocomplete exists, not required for this epic's core scope.
- **What "tracing a data path" means mechanically**: still manual (the user selects and tags the relevant nodes/edges themselves; the tool only visualizes), not automatic graph traversal/path-finding — consistent with [ADR 0008](../../decisions/0008-tool-scope-includes-ea-adjacent-diagrams.md)'s flexible-primitives-over-automation stance.
- **Cross-diagram tag scope stays local/per-diagram.** No shared/global tag catalog across linked diagrams — there's no visibility into a linked child's content from the parent anyway (ADR 0005's downward-only, independently-scoped model), so a shared catalog wouldn't make practical sense on top of how the tool already works.

**Nice-to-have, explicitly for later, not this epic's core scope:**
- A "search children" setting — when searching tags (e.g. in the highlight picker), optionally also search within linked child diagrams, not just the current one. Bridges some of the "local only" limitation without needing a persisted shared catalog — would read child files on demand (the app already has the IPC plumbing for this from epic 0009: `resolveLinkedDiagram`/`openDiagramAtPath`), not a new indexing mechanism.
- A "copy to children" operation — propagate a highlight definition down a diagram's link tree, for consistent highlight catalogs across a complex view without a shared catalog file. [Epic 0035](0035-propagate-required-tags-to-children.md) built exactly this shape of operation for `requiredTags` (merge semantics, full-subtree recursion, bounded to the diagram's own colocation folder — [ADR 0024](../../decisions/0024-propagate-required-tags-to-children.md)); a highlights version would very likely reuse the same `src/main/requiredTags.ts` walk logic rather than reinvent it. Not this epic's scope.

Likely relevant once scoped: epic 0022's gallery (application-to-capability heat maps, data flow/lineage diagrams, security zones would all benefit substantially), and epic 0003/ADR 0010's color/styling infrastructure, which highlight rendering will likely want to build on rather than invent separately.
