# 0183: Installable icon packs

## Status
Not Started. Logged 2026-11-07; replaces the closed epics 0019 (vendor icon packs), 0098 (configurable asset folders) and 0104 (central custom-icon library). The main choices below are made; the design pass settles what is under "To settle", then an ADR, before code.

## Goal
Let a person install icon sets (AWS, Azure, a company's own) once per machine, pick from them in any diagram, and be told when a diagram needs a pack this machine lacks. The app ships no vendor icons: the person supplies the files, so redistribution terms are not the app's question. The built-in Tabler set becomes a pack of the same kind.

## Decided
- **Where:** a folder in the per-user data folder next to the saved preferences, one folder per pack: `icon-packs/<Pack>/<Subset>/<icon>.svg`. Not the install folder: it is read-only on a machine-wide Windows install and in a Linux AppImage, and an update replaces it. Packs are copied in whole.
- **One install manager** handles install, removal and export of packs, as its own step: a window over the canvas that blocks until the work is done or cancelled. The menu item opens it. Making the folders by hand still works, but the manager is the way, so a scattered set of folders is not what people end up with.
- **Install:** the person picks a folder; each subfolder becomes a subset in the picker. Files are written to a staging folder and moved into place only when everything is copied, so cancelling or failing leaves nothing half-installed.
- **Metadata:** a file in the pack folder and one in each subset folder: a name (the folder name if absent), a description, and a text saying what to do when the pack is missing. If a pack has none, install writes a default listing the icon names. Per-icon meanings (user, person, human) are an optional addition to try; roll it back if it strains search, file size or the work of keeping it.
- **A pack is known by its name.** Two packs with the same name are the same pack; a renamed folder with a metadata name keeps working.
- **Used packs in the diagram:** when an icon from a pack is used, the pack's name and its "if missing" text are copied into a list in the `.chd`; the entry goes when no icon from that pack is left. Written from the icons actually in the diagram each time it is saved, so it cannot go stale.
- **Missing pack:** one diagnostics error naming the pack and showing that text. An app that does not know installed icons shows no icon, and the newer-file warning applies ([ADR 0118](../../decisions/0118-saved-with-version-marker.md)). An app that knows them but lacks the pack behaves as any other machine without it.
- **Icons stay SVG until exported as pixels**, drawn in the page and not as images, so they follow the light and dark theme. They follow the text colour as the built-in icons do today; colours a pack's author fixed in an icon are kept. Recolouring by the person (line and fill) is an idea for later, not part of this.
- **The built-in Tabler set is installed by the same code,** as a full copy, and is a pack like any other: the same folders, the same metadata, an example for people who make packs. The installer does not install it: on the first start the app asks "Install the default icon pack(s)?", and Yes opens the manager and starts the install. No is remembered and not asked again; the manager installs it later by hand. A diagram that needs a pack that is not installed says so in diagnostics, with a button to open the manager.
- **Removal moves the pack to the system trash,** or to a hidden folder in the packs folder where the system has none.
- **Picker:** collapsible sections per pack and subset, built for thousands of icons.
- **Not in scope:** the extension; the CLI beyond what is under "To settle".

## To settle
- **Reference form.** `{source: 'installed', pack, path}`; the path is untrusted and stays inside the pack ([ADR 0115](../../decisions/0115-paths-stored-in-diagrams-are-untrusted.md)). Additive: `docs/file-format.md`, the validator and the skill's field reference. An existing `{source: 'builtin', id}` must keep working ([ADR 0029](../../decisions/0029-backward-compatible-loading-is-a-standing-rule.md)): the skill teaches it and assistants write it, so it is best read as an alias for the Tabler pack, not migrated away.
- **The cleaner is now the safety boundary.** An inline SVG can run a script, load a resource and restyle the page, which an image never could. So every icon is cleaned on every read, not once at install (a hand-placed file never went through install): an allowlist of elements and attributes, with scripts, event attributes, `foreignObject`, external references (the app is offline, [ADR 0113](../../decisions/0113-enforced-offline-behaviour.md)), `@import` and animation removed. A vetted library (DOMPurify's SVG profile) over our own parser: it is an npm package bundled into the renderer, so the same version runs on every platform; it needs a DOM, which the renderer has and the command line does not (the command line draws no installed icons, see below). A new dependency, so `npm run notices`. Gradients, clip paths, masks and strokes stay: vendor icons need them.
- **Icons must not touch each other.** Inline SVGs share one document: two icons that both use `id="a"` for a gradient or the class `cls-1` (most exported packs do) paint each other. The prefix has to be per icon, not per pack, as two icons in one pack collide just the same. Form: `pack-subset-icon-existingid`, made from the icon's place in the pack, with characters an id cannot hold replaced and a short hash added where two places would give the same text (`EC2` and `ec2`). It is applied when the icon is read for use, not written into the installed file, so a hand-placed icon is covered too and an exported pack holds the files as supplied. It rewrites every reference to an id (`url(#…)`, `href`, `xlink:href`, selectors and `url()` inside `<style>` and `style` attributes) and class names, or turns `<style>` rules into attributes. The same goes for an SVG export that embeds several icons. One gap the name alone leaves: the same icon drawn twice (on the canvas and in the picker) repeats its ids, and a gradient or clip path defined inside a hidden element (`display: none`) does not work from another place in the page. Add a per-use counter to the id, or never hide a drawn icon; the design pass picks.
- **Fallback if inline SVG proves slow** on very large diagrams: draw an icon inline only when it uses the text colour, and draw fixed-colour icons as `<img>` from a data URL, which is isolated and cheap. Measure before building it.
- **Cost.** The picker is a window onto the list: with sections collapsed and only the rows in view drawn, a few tens to a few hundred icons are in the page at once, and search runs on names, not on the SVGs. That holds only if the picker is built that way; a plain list inside a scroll box draws all 5,000. The canvas draws what a diagram uses, parsed once and cached.
- **One-off and existing custom icons.** A single icon the person adds goes into a default pack of its own (`Misc icons`), separate from Tabler, installed by the same manager. The `assets/` folder stops being where new icons go, but a diagram's existing `{source: 'custom', path}` icons must keep opening and drawing ([ADR 0029](../../decisions/0029-backward-compatible-loading-is-a-standing-rule.md)), and the command-line export still reads them. Two costs to settle: a diagram that carried its own icons beside it no longer does, so a colleague sees a missing-pack error for `Misc icons`; and everyone's `Misc icons` has the same name and different contents, so the same path can be a different icon on another machine. A short content hash kept with the reference would let diagnostics say "this icon differs", and an action in the manager could move a diagram's old custom icons into `Misc icons`.
- **Export.** Export writes a pack as a zip a colleague installs through the same manager; a zip reader is a new dependency, or the manager takes folders only at first. Removal says that diagrams using the pack will show a diagnostics error; the app cannot know which diagrams, as they are separate files. `shell.trashItem` can fail on a Linux desktop without a trash, hence the hidden-folder fallback.
- **First start.** The question comes after a diagram opened from the file manager has loaded, not before it. A new Tabler version in an update is offered by the manager as an update and never overwrites an installed pack, whose metadata may have been edited. The payload is one archive, not 5,000 loose files, to keep the installer small and the unpacking fast.
- **The command-line export** draws built-in icons from a bundled folder today and has no per-user folder to read. It keeps reading the bundled Tabler copy; an installed icon it cannot find is drawn as a neutral placeholder with a warning, not a failure.
- **Tests and fixtures** that open diagrams with built-in icons need the pack present in the test environment.
- **File names.** Two icons that differ only by case are one file on Windows and two on Linux; install reports a clash instead of overwriting.
- **Reinstalling** over an existing pack adds new icons and keeps an edited metadata file.
