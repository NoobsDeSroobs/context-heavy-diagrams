# 0080: Behaviours are the tool's own flow vocabulary, and their symbols are semantic, not symmetric

## Status
Accepted. Merges 0080 (BPMN as a vocabulary, not a metamodel), 0180 (behaviours are light elements for events and verbs), 0193 (behaviour symbols: one colour per family, marks of our own, an end that says how it ended) and 0198 (parallel paths are closed by a wait, decisions by a decision) into one decision, reworded 2026-11-26. It keeps the lowest number of the group. It sits under [0008](0008-tool-scope-includes-ea-adjacent-diagrams.md) (flexibility over formal notation) and builds on [0175](0175-assistants-make-what-a-person-can-make.md).

## Context
A flow needs elements that are not entities: a step, a decision, a start, an end. BPMN showed the value of a fixed set of visual symbols for them: a business analyst and a developer read the same diagram the same way. But its precision comes from a metamodel of about a hundred elements, a rigid grammar, validation rules and token semantics, which is the rigidity 0008 rejects. And BPMN draws the split and the join of a gateway with one symbol, so a flow can be miswired in a way the drawing hides: a split into three paths closed by a join with four arrows in, one of them from a decision's second way, looks balanced by eye and waits for an arrow that is never sent.

## Decision
**Flow elements are the tool's own vocabulary, and their symbols are semantic and not symmetric:** a symbol says what it does in the position it is in, even where BPMN would use one symbol for both ends. What is left of BPMN is the general idea of representing the concepts of a flow with visual symbols.

- **Our own vocabulary, with BPMN as its inspiration.** The list goes beyond BPMN (a human action, Wait for first, an end that says how it finished, an event that says whether it begins a flow) and changes some of what it took (decisions and parallel paths are closed differently, the marks and colours are ours, "human" replaces "user"). The product says "inspired by BPMN", never "based on" or "compliant"; the notices credit OMG. Nothing is enforced and there is no execution model, and process modelling is in scope without the tool becoming a process tool. Labels are neutral ("Decision", not "Exclusive Gateway"); the BPMN terms are search keywords only, so someone who knows BPMN still finds things by the name they expect.
- **Entities are nouns, behaviours are verbs.** A behaviour is a node of type `stencil` with a `kind` from a closed list built into the app: nobody defines or installs kinds, which would let nouns creep in. Things and concepts stay entities and carry context (notes, tags, metadata, links, security). A behaviour is deliberately light: a label, its kind, a style, a size and place, a parent, connection points and one link, and no notes, tags, icons, metadata or security data. A lane is a container and a behaviour in it is its child, the only other context it has. The frame is always a rectangle (a circle for events, a square for choices, a band for a step) so resizing, containment and connection points work as for any node, and non-rectangular outlines are not used.
- **A kind is a base shape with an optional mark, and its id says what it is:** the base word first and the subtype after (`step-human`, `event-timer`); an id is permanent once released, and a renamed one stays as an alias. Its default colour is built into the app and not stored, so it is the same on every machine, and a fill on the element wins.
- **One colour per family; the kind is told by name and mark.** Families (steps, decisions, parallel, events) differ in colour and lightness, so they differ in grayscale too, and nothing varies inside a family. There is no red. Marks are our own, one meaning each.
- **Decisions and parallel paths are closed differently.** A decision is closed by a decision symbol: its ways go into one, then on. Parallel ways are opened by Run in parallel and closed by a wait, Wait for all (the flow goes on when every path has arrived) or Wait for first (when the first has). A gateway is still a split or a join by its arrows and not by its symbol, so the symmetric style, one symbol that closes what it opened, also works: it is accepted and not advised, since a name says what a symbol does in one position and in the other the reader has to know the convention.
- **State is named, stored only when not the default, and read leniently.** An end says how it finished (`outcome`: success, warnings, failed, aborted) and how far it reaches (`reach`: this path, or the whole flow), separate because every outcome can have either reach. An event says whether it begins a flow or sits in one (`flowPosition`), stored and not derived from its edges, so it survives a filtered view and states the intent. A value an app does not know is drawn as the default. The person a flow waits for is a human step or action, not a "user", since that person is often part of the system.
- **The only check is one warning:** two ways of one decision meeting at a join that waits for all its arrows, with nothing between them that gathers them into one. It only warns; a drawing is never refused, and a flow the validator cannot see (through a loop) is not judged.
- **Legend, search and review.** The legend shows the kinds the diagram uses, one row for each way an end finishes, derived and never stored, with a switch to hide it for the session. A behaviour is found by id, label, kind name and BPMN terms, and in a review its kind and link are changes in meaning. An assistant can make and change a behaviour as a person can.

## Alternatives considered
- **BPMN as the notation, with its grammar and validation.** It is the rigidity 0008 exists to avoid; the goal is not a BPMN tool.
- **A rectangular entity with an icon and a preset, or a role facet on nodes.** A behaviour could not be told from an entity, would carry all the context, and conformance and required tags could not leave it alone.
- **Non-rectangular outlines** (a diamond for a gateway). Resizing, connection points and containment all assume a rectangular frame.
- **Changeable icons, tags, per-person colours or stored legend rows on behaviours.** A behaviour is context-light, a legend row that is stored goes stale, and the same file would look different on another machine.
- **One symbol that closes what it opened, for every gateway (pure BPMN).** The mistake above cannot be made by accident, but a closing symbol looks like the opening one, so a person must trace the arrows to know whether paths are waited for or merged.
- **Parallel paths and decisions both closed by waits.** A join waits for every arrow into it, so a decision's unused way is waited for forever.
- **One colour for all gateways, colour inside a family, or a red or green family.** The first let decision and parallel be confused, the second says in colour what the mark already says, and red reads as an error.
- **ArchiMate as the vocabulary source.** A heavier metamodel and less recognised for flow work; the same verdict would apply.

## Consequences
- The file format gains a node type, an additive change in `docs/file-format.md`; every place that lists node types (conformance, the exports, the review, search, the assistant tools) needs it.
- The list of kinds can grow, so the picker groups and filters it and the legend shows only the kinds in use. A later kind follows the same rules: its own mark, the family colour, no red.
- A behaviour cannot be coloured by tag; what needs explaining is an entity or a text box beside it.
- Both closing conventions are valid, so a diagram may mix them; the legend, the file format and the assistant instructions name each kind's role in both positions.
- A file that uses an outcome, a reach or the human action shows a plain end or step in an older app, and the changelog says so.
