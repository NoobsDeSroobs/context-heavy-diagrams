# 0139: Releases are built by CI from a version tag, and each build says how far it has been tried

## Status
Accepted. Merges 0139 (releases are built by CI from a version tag, unsigned), 0162 (the installer can put `chd` on the PATH), 0165 (the release installs its own installer and ships the licence) and 0166 (Linux and macOS builds are published, labelled by how far they have been tried) into one decision, reworded 2026-11-26. It keeps the lowest number of the group. It builds on [0113](0113-enforced-offline-behaviour.md) (the app stays offline) and [0106](0106-chd-command-line-tool.md).

## Context
The Windows installer was first built by hand, so a person without Node, git and a build could not get the app. The app has no auto-update and makes no network requests, so each version is downloaded by hand and its provenance has to be checkable. There is no code-signing certificate. Nobody on the project had a Mac, and Linux had not been tried on real hardware, and holding those builds back means nobody on those systems can try the tool, and so nobody can report that it works or does not.

## Decision
- **A release is a tag.** A GitHub Actions workflow builds and publishes when a tag `vMAJOR.MINOR.PATCH` is pushed; the maintainer creates and pushes the tag, and the workflow only reacts. It refuses unless the tag equals `v` plus the `package.json` version and the tagged commit is on `master`, and it runs lint and the tests first. It publishes the installer, a `SHA256SUMS` file and release notes taken from the matching changelog section, and marks a version below 1.0.0 a pre-release.
- **electron-builder never publishes, and the app keeps no `publish` configuration.** The upload is a `gh` command in the workflow, so no update feed exists and no network code enters the app. The workflow has read access by default and a write token only in the release job, with two actions pinned by commit hash and no other third-party code.
- **It is unsigned for now.** The release notes and the README tell the reader to choose "More info", then "Run anyway", and to check the checksum.
- **The release installs its own installer before it publishes.** A script installs it silently into a scratch folder, checks that the program, the `chd` launchers, the licence files and the install options are there, runs `chd --version` against `package.json`, checks that the PATH was not touched, and uninstalls. A failure stops the release before anything is uploaded. A second workflow runs the same check, without publishing, on a pull request that touches the build files.
- **The licence ships beside the program.** `LICENSE.txt` and `THIRD-PARTY-NOTICES.md` are installed next to it on Windows and Linux, and inside the app's resources on macOS, where a loose file in the root of a `.app` cannot be signed. The release notes name the source: a link to the tagged tree, the licence and where the notices are installed.
- **Linux and macOS builds are published after the Windows release exists and only add files to it,** so a failure in one can never block the tested installer. Each asset's label, the release notes and the README say how far the build has been tried on real hardware, no further than it has: a build nobody has run says it is not tested, and one that has been installed and lightly used says so. CI checks only what it can without a display (the licence files, that `chd --version` runs, and on macOS that both architectures are there and the signature is valid). Linux ships an AppImage and a deb (a snap needs snapcraft and stays out of CI); macOS ships one universal DMG, ad-hoc signed and not notarised, since an unsigned arm64 build is refused as "damaged". Checksums are per platform.
- **The Windows installer can put `chd` on the user's PATH.** A checkbox on its options page, unticked by default, since the other choices change what the app does and this one changes a variable every program the person starts will read. It edits only the user's PATH, keeps its type so `%VARIABLE%` entries stay variables, and adds only `<install folder>\bin`, never the folder itself, which would make every program in it startable by name. The uninstaller removes exactly that entry, and an update does not touch it. A PATH the installer cannot read safely is left alone. The functions are tested against a scratch registry key with the NSIS that electron-builder downloads.

## Alternatives considered
- **Upload a locally built installer by hand,** or **electron-builder's own publisher,** or **a third-party release action.** The first is not reproducible, the second brings an update-feed concept and token handling for a feature the app lacks, and the third is more code holding a write token for what one command does.
- **Hold the Linux and macOS builds back until they are tested,** or **publish them from one job with the Windows installer.** Nobody can test them without them, and an untested build could stop the tested one from being published.
- **Two macOS DMGs, or arm64 only.** A question for the person downloading, or Intel Macs left out.
- **Put the install folder on the PATH, move the launcher into `bin`, use a PATH-editing plugin, or `setx`.** Respectively exposes the executable and uninstaller by name, breaks launcher paths already written into assistants' files, adds a downloaded binary to the build, and truncates the PATH and flattens its variables.
- **Tick the PATH box by default.** A person who does not read the page would have the PATH changed.
- **Run the installer check on every pull request,** or **show the licence as a page in the installer.** The first costs minutes on a Windows runner for something a path filter catches; the second makes a person click through a licence the GPL does not require them to accept to run the program.

## Consequences
- A release is a tag and nothing else; the changelog entry must exist before it, or the version gets a one-line note.
- Every download triggers a SmartScreen or Gatekeeper warning until signing exists; code signing and a build-provenance attestation are not decided here.
- The installer check writes to the user hive like a real install and removes it again, so it must run on a runner or a throwaway account, not on a machine with the app installed.
- A silent install leaves the PATH alone, and the choice can only be changed by running the installer again or editing the PATH. Linux and macOS have no PATH registration and macOS no launcher: those users call it by its full path.
- Likely first-run problems on Linux and macOS are not handled (the AppImage may need `libfuse2` or refuse Electron's sandbox), and an Intel Mac is covered only by the universal build's other half. The label moves with what has been tried, not with the signing.
