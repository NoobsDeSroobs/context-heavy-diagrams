# 0188: Icons come from installed packs, drawn as cleaned inline SVG

## Status
Accepted (2026-11-17)
Amends: [0006](0006-icon-storage-model.md) (adds the `installed` source it left open). Keeps [0029](0029-backward-compatible-loading-is-a-standing-rule.md) and [0115](0115-paths-stored-in-diagrams-are-untrusted.md) as they are.
Superseded by: none

## Context
The app draws a bundled Tabler set inline and a diagram's own custom icons as `<img>`. People want the icon sets of their own world (a cloud vendor's, a company's) without the app shipping or licensing them, and a diagram that needs a set the machine lacks should say so. The icons are third-party files, so how they are drawn is a security and a theming question at once.

## Decision
- **A pack is a folder in the per-user data folder:** `icon-packs/<Pack>/<Subset>/<icon>.svg`, next to the saved preferences, not in the install folder (read-only on a machine-wide Windows install and in an AppImage, replaced by an update). A `pack.json` in the pack and a `subset.json` in each subset hold a name (the folder name if absent) and a description; `pack.json` also holds a text saying what to do when the pack is missing and an optional version. Unknown fields are ignored and an unusable file is reported, never a reason to refuse the pack. A pack without them gets a default written at install. A pack is known by its name: two folders with the same name are one pack, and the second is reported, not used.
- **One install manager** (a window that blocks until done or cancelled) installs, removes and updates packs. Install copies into a staging folder and moves it into place when everything is there, so a cancel leaves nothing half-installed. A name that differs from another only by case is reported as a clash (one file on Windows, two on Linux). Reinstalling adds new icons and keeps edited metadata. Removal moves the pack to the system trash, or to a hidden folder in the packs folder where there is none. Sharing a pack is copying its folder.
- **The reference is `{source: 'installed', pack, path}`;** `path` is `<Subset>/<icon>.svg` (folder and file names, with `/`), resolved inside the pack's folder and kept there ([0115](0115-paths-stored-in-diagrams-are-untrusted.md)): exactly two plain names, no `..`, no other separator, no Windows device name. The folder of a pack is found by looking its name up among the installed packs, never by putting the name into a path. `{source: 'builtin', id}` stays valid and means the Tabler pack's `Outline/<id>.svg`; `{source: 'custom', path}` keeps opening and drawing as an `<img>`.
- **Icons are drawn as inline SVG, cleaned on every read,** so each icon decides for itself how it is coloured: a shape-only icon (Tabler) draws in `currentColor` and takes the text colour in both themes, and an icon with colours its author fixed (a cloud vendor's service icons) keeps them. Nothing has to say which is which. The cleaner is an allowlist from a vetted sanitiser library (its SVG profile) in the renderer: scripts, event attributes, `foreignObject`, external references (the app is offline, [0113](0113-enforced-offline-behaviour.md)), `@import` and animation are removed; gradients, clip paths, masks, strokes and `<use>` of an id in the file stay. A `<style>` element would restyle the page, so its rules are written into the style attribute of each element they match, limited to the properties that colour and draw (nothing that positions, sizes or loads), and the element and the classes go. Cleaning happens at read time, not install, because a hand-placed file never went through install. The command line draws no installed icon.
- **Icons are kept from touching each other.** Inline SVGs share one document, so ids are rewritten when an icon is read for use, not in the file: a prefix made from the icon's place (`pack-subset-icon`, characters an id cannot hold replaced, a hash of the place) plus a per-use counter, so the same icon drawn on the canvas and in the picker does not repeat ids. Every reference to an id is rewritten with it (`url(#…)` in an attribute or a style, `href`, `xlink:href`); with the classes gone there is nothing else shared. An SVG export that embeds several icons does the same.
- **Tabler is an installed pack like the others.** It is carried in the installer as one archive and offered on the first start ("Install the default icon pack(s)?", asked after a diagram opened from the file manager has loaded). Yes opens the manager and installs it; No is remembered, and the manager installs it later. A new Tabler in an update is offered as an update and never overwrites an installed pack. A `builtin` reference with no Tabler pack installed is a missing pack, not a blank. The command-line export keeps reading the bundled copy.
- **One-off icons go into a pack too.** Adding a single icon asks which pack, defaulting to `My icons`, created when first used; `assets/` stops being where new icons go. The cost is that a diagram no longer carries its icons: a colleague sees the missing-pack message of that pack.
- **A missing pack is one diagnostics error** naming the pack and showing its "if missing" text, with a button that opens the manager; a missing icon in an installed pack is handled like any other missing file ([0084](0084-diagnostics-missing-files.md)). The diagram may carry an optional list of the packs it uses (name, version and the "if missing" text), written by the app from the icons present at each save, so it cannot go stale; a file without it is valid, and diagnostics work from the references alone. An app that does not know installed icons shows none and gives the newer-file warning ([0118](0118-saved-with-version-marker.md)).
- **The picker has a collapsible section per pack and subset,** searches by name, caps the rows it draws per section and draws previews as they scroll into view, so thousands of icons are a window onto a list, not 5,000 elements.
- **Not in the first version:** exporting a pack as a zip, meanings per icon (synonyms) in search, recolouring an icon by the person, listing and writing installed icons from the extension or the command line.

## Alternatives considered
- **Draw installed icons as `<img>`, with a CSS mask for one-colour packs.** Isolated by construction: no cleaner, no id rewriting, and shape-only icons would still follow the text colour through the mask. Rejected because an `<img>` takes no colour from the page, so the app would have to know which way to draw each icon: a flag per pack or subset, or a guess from the file, and a folder that mixes shape-only and fixed-colour icons would need it per icon. Inline lets the icon say so itself. The inline form needs the cleaner and the rewriting, and is accepted with that cost. If it proves slow on very large diagrams, fixed-colour icons can move to `<img>` from a data URL, which is isolated and cheap.
- **Keep Tabler bundled and show it as a read-only pack.** One less state, no first-start question. Rejected: it keeps the built-in set a special case and the icons in two forms, while installing it through the manager teaches the way, lets a person remove what they do not use, and is the path a later central repository would use.
- **Keep `custom` as the way to add one-off icons.** Icons travel with the diagram. Rejected as the way for new icons: it repeats each icon in every diagram's folder in the repository, and a pack is easier to share.
- **Identify an icon by a content hash as well as its name.** Would tell "this icon differs" for two machines' `My icons`; left out until it is a real problem.

## Consequences
- The sanitiser becomes the safety boundary for installed icons, which [0112](0112-electron-hardening-sandbox-and-navigation.md) could so far leave to `<img>`; it is a new dependency, listed in the notices.
- A saved diagram gains an optional field and a new reference form; older apps read them as an unknown source and show no icon.
- A pack's format is public, since people write it: it needs its own page in `docs/`.
- A colleague opening a diagram needs the same packs; the diagnostics message says how to get them.
