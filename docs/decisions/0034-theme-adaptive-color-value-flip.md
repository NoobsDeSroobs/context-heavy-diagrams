# 0034: Theme-adaptive color lightness flip

## Status
Accepted, revised same day (2026-08-21) — see Revision below. The mechanism shipped is an Oklab lightness mirror, not the HSV Value mirror originally specified; everything else in this ADR (blanket application, dark-baseline convention, no file-format change, backward-compat stance) is unchanged.

## Context
This was raised (2026-08-20) after a gallery-testing session surfaced a readability problem: an explicit color chosen for legibility against one theme's canvas background (the classic case being a near-white shape, fine on dark, invisible on light) stays bit-for-bit identical when the app's theme changes, since explicit `fill`/`stroke`/`fontColor` values never followed the theme. The initial framing captured a specific mechanism up front (HSV Value mirror, dark-theme baseline) but left open whether it should be blanket or targeted, how it interacts with existing files, and where exactly it should live architecturally. Worked through with the user in conversation (2026-08-21).

## Decision
- **Blanket, not contrast-driven.** Every explicit `fill`/`stroke`/`fontColor` on a Node or Edge gets the same deterministic treatment, unconditionally — no contrast-ratio analysis against the canvas background, no per-field/per-diagram opt-out in v1. A contrast-driven alternative (only nudge a color when it would actually fail legibility, leave everything else untouched) was seriously considered — see Alternatives — but the user's explicit call was to keep this "translate the picked colour at runtime, no analysis of contrast or advanced coding," accepting that colors which weren't a problem also shift.
- **Mechanism: mirror Oklab Lightness around its midpoint, hold the `a`/`b` chroma-hue axes fixed.** `flip(L) = 1 - L` (Oklab's L is normalized 0=black to 1=white). Applied via a full sRGB→Oklab→(flip L)→Oklab→sRGB round trip — see Revision for why Oklab, not HSV. Same formula in both directions (see below), which is what makes it safe to reuse for both rendering and editing.
- **Dark theme is the stored baseline, entirely a renderer-side convention — no file-format change.** A stored `fill`/`stroke`/`fontColor` is always interpreted as "this color's lightness as it should render in dark theme," regardless of which theme was active when it was set. `docs/file-format.md` is unaffected: the stored value is still just a literal CSS color string, exactly as before.
  - **Render**: `displayed = theme === 'dark' ? stored : flip(stored)`.
  - **Edit** (color picker, in either theme): `stored = theme === 'dark' ? picked : flip(picked)`.
  - Both directions are the *same function call* — `flip` is self-inverse (mirrored around the midpoint), so `themeAdaptiveColor(color, theme)` is the one utility used everywhere a value crosses the stored/displayed boundary, in either direction. This is also what keeps it a pure rendering-layer concern rather than a "processing" step with its own separate write path: there's exactly one transform, applied at exactly the boundary between what's stored and what's shown/picked.
  - Why the mirror preserves contrast, not just individual color appearance: for any two colors with lightness `L1`/`L2`, mirroring both around the same midpoint preserves their absolute gap exactly — `|flip(L1) - flip(L2)| = |L1 - L2|`. That property held under HSV's V too, but only translates into *preserved readability* if the lightness metric is actually perceptually uniform — which HSV's V isn't (see Revision) and Oklab's L is, by design.
- **Every existing `.chd` file is affected the moment this ships — explicitly accepted, not a migration concern.** There's no stored marker distinguishing "old, theme-naive color" from "new, dark-baseline color" (deliberately — see previous point), so every existing file's **light-mode** rendering changes on first load under this code; dark mode is unaffected for diagrams authored while looking at dark theme (the OS-follows default, ADR 0027). This includes the full example gallery. The user's explicit call: yes, apply the same conversion to everything, that's the intended behavior, not a bug to route around.
- **No opt-out mechanism in v1** — if a real need for one shows up later (e.g. an exact brand color that must never shift), the user's own suggested landing spot is a global toggle in the existing Settings panel (`settings.ts`/`SettingsPanel.tsx`, ADR 0032) to disable the flip entirely, not a per-field/per-diagram flag. Not built now; noted here so it isn't re-litigated from scratch if it comes up.
- **Arbitrary CSS color input, not just hex.** The property panel's `ColorField` has both a `<input type=color>` swatch (always hex) and a free-text field (any valid CSS color — `rgb()`, `hsl()`, named colors). Rather than hand-writing a parser for every valid CSS color syntax, the conversion normalizes via the browser's own CSS engine: assign the string to a hidden element's `style.color`, read back `getComputedStyle(...).color` (always resolves to `rgb(...)`), then do the Oklab math on that. A string the engine can't resolve passes through unchanged.

## Revision: HSV Value → Oklab Lightness (same day, 2026-08-21)
Shipped and confirmed working, but the user's own follow-up testing surfaced a real problem with the original HSV-based mechanism: white text on a semi-light red background was readable, but the flipped version — black text on the mirrored red — was hard to read, even though the mirror is mathematically symmetric. Root cause: HSV's Value (`max(R,G,B)`) is hue-blind and not perceptually uniform. Pure yellow and pure blue both read `V=100%`, yet yellow looks nearly white and blue looks quite dark — red sits in an awkward middle, looking noticeably darker than its `V` suggests. Mirroring a metric that doesn't track actual perceived brightness doesn't reliably preserve actual contrast, even though it exactly preserves the *numeric* gap between two Values.

Fix: swap the mirrored channel from HSV's `V` to Oklab's `L` (Björn Ottosson, 2020 — the same conversion the CSS `oklab()`/`oklch()` spec uses), which is purpose-built to track perceived lightness uniformly across hues. The rest of the design (dark-baseline convention, self-inverse mirror applied at the stored/displayed boundary, blanket application, no file-format change) is unchanged — this only replaces the internal color-space math in `themeAdaptiveColor.ts`, not the architecture around it. No new dependency: Oklab's conversion is a published, closed-form set of matrix operations, implemented directly (same scale of code as the HSV math it replaced).

Known limitation, accepted: Oklab's L/a/b round-trip can produce an out-of-sRGB-gamut result for high-chroma colors mirrored to a very different lightness (Oklab's gamut boundary is lightness-dependent). The implementation clips channels to `[0, 255]` rather than doing full gamut mapping — a standard, well-understood simplification (the same tradeoff most `oklch()` polyfills make), not worth the added complexity for this feature.

## Alternatives considered
- **Contrast-driven, targeted adjustment**: only shift a color's Value when its actual contrast against the current theme's canvas background would fall below a legible threshold, leaving already-fine colors untouched. More precisely targeted at the real bug (and would have left most existing diagrams' appearance untouched), but requires a contrast metric, a search/clamp step to find the minimal correction, and loses the clean "pure function of (stored value, theme)" invertibility the chosen mechanism has — explicitly rejected by the user in favor of the simpler deterministic transform.
- **Per-field/per-diagram opt-out at ship time.** Rejected — there's nowhere to store an exemption flag without contradicting the "no file-format change" decision; deferred to a possible future global app setting instead (see Decision).
- **A stored marker distinguishing pre/post-feature colors**, to avoid changing how existing files look. Rejected — the user explicitly wants uniform treatment across every file, old and new, not a two-tier system.
- **Hand-written CSS color parser** covering hex/rgb/hsl/named syntax. Rejected in favor of letting the browser's own style engine resolve it (see Decision) — no new dependency, and correct by construction for anything valid CSS accepts.
- **HSV Value mirror** — the original mechanism, shipped then superseded same day. Rejected once live testing showed it doesn't reliably preserve contrast (see Revision) — HSV's V isn't perceptually uniform across hues, so mirroring it doesn't correspond to mirroring how light a color actually looks.
- **CIE Lab** (the older, more established perceptually-uniform space) instead of Oklab. Not seriously pursued once Oklab was on the table — Oklab is a newer refinement designed to fix known non-uniformities in Lab specifically for this kind of lightness-adjustment use case, and is already what the CSS color spec itself uses for `oklab()`/`oklch()`.

## Consequences
- New utility module (`src/renderer/src/styles/themeAdaptiveColor.ts`): CSS-color-string → RGB (via the DOM computed-style trick) → Oklab → flip L → Oklab → RGB → hex. One exported function, `themeAdaptiveColor(color, theme)`, used identically at every read (render, picker display) and write (picker edit) site — no separate "toDisplay"/"toStored" functions needed since the transform is self-inverse.
- `DiagramContextValue` (`DiagramContext.tsx`) gains `theme: Theme`, provided from `Canvas.tsx`'s existing `useTheme()` call — same "thread it through context so deep components don't need Canvas's own state directly" precedent already used for `matchHighlights`/`edgeStraightSegmentLength`.
- Render-side touch points: `nodeStyleCss.ts`'s `nodeContainerCss`/`nodeLabelCss` (fill/stroke/fontColor → CSS), consumed by `ShapeNode`/`ContainerNode`/`TextNode`; `LabeledEdge.tsx`'s `stroke`/`fontColor` computation. Edge markers need no separate handling — they already inherit the edge path's rendered stroke via CSS's `context-stroke`.
- Edit-side touch points: `PropertyPanel.tsx`'s `NodeStyleFields` (fill/stroke/fontColor) and `EdgeFields` (stroke/fontColor) — both the value shown in `ColorField` and the value written back via `onChange` need the same transform, applied in the same direction (self-inverse) since one is "stored → displayed" and the other is "picked → stored." Also `Canvas.tsx`'s right-click "Fill…"/"Border…" `ColorPickerPopup` flow, which reads/writes the same style fields through a separate path from the property panel.
- `docs/file-format.md` needs no changes — this is confirmed as a pure in-app rendering/editing behavior, not a schema concern.
- **Known, accepted side effect**: because the mirror is blanket and uniform (every element's lightness flips around the same midpoint), toggling themes gives the whole diagram a "negative image" feel, distinct from any single color's individual behavior. This is the direct visual cost of rejecting the contrast-driven alternative above — logged as an open point to revisit, not currently considered a problem to fix.

## Addendum: canvas background color was missing this treatment (2026-08-25)
Found while testing the DiagramContext re-render performance work: `settings.canvasBackgroundColor` (the Style Palette panel's "Canvas background" field, ADR 0048) was never included in the blanket application above — it rendered as a raw stored value with no theme adaptation, unlike every `fill`/`stroke`/`fontColor`. Not a deliberate exclusion; the "blanket, not contrast-driven" decision was scoped to Node/Edge style fields when written and this one was simply missed. Fixed the same way as every other touch point: `Canvas.tsx`'s `--xy-background-color` CSS var now applies `themeAdaptiveColor`, and `StylePalettePanel`'s `ColorField` gained a `theme` prop to flip its displayed value and round-trip picked values the same way `PropertyPanel`'s `NodeStyleFields`/`EdgeFields` already do.
