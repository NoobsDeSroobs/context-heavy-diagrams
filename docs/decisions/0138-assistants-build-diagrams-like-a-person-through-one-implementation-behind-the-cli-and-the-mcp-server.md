# 0138: An assistant builds diagrams like a person, through one implementation behind the command line and the MCP server

## Status
Accepted. Merges 0138 (the MCP server carries the guidance, the command line the checks), 0148 (building by operations that answer), 0150 (`chd edit` and `chd ask`), 0161 (the layout check judges edges as drawn), 0171 (an edit answers with the problems it touched), 0172 (a one-page build topic), 0174 and 0177 (`route_edges`), 0182 (validating text), 0187 (behaviours, label positions and crossings) and 0199 (the tool makes every id) into one decision, reworded 2026-11-26. It keeps the lowest number of the group. It builds on [0106](0106-chd-command-line-tool.md), [0109](0109-stale-edit-check-for-every-ai-write-path.md), [0110](0110-claude-desktop-extension.md), [0115](0115-paths-stored-in-diagrams-are-untrusted.md) and [0175](0175-assistants-make-what-a-person-can-make.md).

## Context
Assistants asked to draw a large diagram wrote their own generator scripts, about a thousand lines each, to get ids, parent order, connection points and positions right. A script needs a runtime the machine may not have, a chat client has no shell, and an assistant cannot look at the picture it makes: a rasteriser or a browser is not always there, and not every client shows an image to its model. A CI job has no assistant and no MCP server, only `chd`.

## Decision
- **An assistant does what a person does, one operation at a time, and each operation answers with what it made** ([0175](0175-assistants-make-what-a-person-can-make.md)). Operations are plain data from one pure core in `src/shared/edit/`: add an entity, container, text, line or behaviour; connect; move, resize, relabel, restyle, nest and remove; tags, the legend, links to other diagrams, notes; an edge's routing points; a behaviour's kind; where a label goes. A batch is all or nothing and an error names the operation. Coordinates are absolute, the core touches no disk, and anything a person can do in the editor an assistant can do here, except what has no operation yet (icons, reference images, the security matrix, gravity presets, edge direction sets: the raw file tools).
- **One implementation, two front doors.** The format rules, the validator, the metamodel check, the diff, the fingerprint and the edit core live in shared code. The command line (`chd edit`, `chd ask`, `chd validate`, `chd check`, `chd diff`) and the MCP server (`edit_diagram`, `inspect_diagram`, `room_for_label`, `validate_diagram`, ...) are thin wrappers and cannot give different answers for the same file. A test runs both over the same diagrams and compares answers and bytes, and lists each tool that has no counterpart (the reading tools, which a shell already has) with its reason. A check that exists only in the server is not allowed: every check is reachable from `chd` with exit codes, since a CI gate must never depend on what an assistant saw. A pass in a session is advice and a guard against writing a broken file, not a certificate.
- **Both are AI write paths and carry the same guards:** the stale-edit check ([0109](0109-stale-edit-check-for-every-ai-write-path.md)), confinement to the chosen folder and paths that stay inside it ([0115](0115-paths-stored-in-diagrams-are-untrusted.md)), and validation of the result before it is written.
- **The MCP server carries the guidance;** nothing of ours is written into the person's folder, so their own `CLAUDE.md` and skills never collide with ours. It gives the format rules by topic, and an assistant that builds with `edit_diagram` reads one short `build` page (what the tool does and leaves to the assistant, the numbers, recipes) and not the hand-writing rules. `chd mcp` runs the same server for any client. The folder route (a skill and `AGENTS.md`) stays for agents without MCP support.
- **The assistant decides all layout; the tool answers.** It never places an element. It reports, in text, what is wrong with the layout: overlaps, labels without room, an element sticking out of its container, an edge across an element or across another edge, a label on something. Edges are judged on the path that is drawn (the same function the canvas and the export use), so curves and bend points count. An edit answers with the problems that involve what it touched and a count of the others; `validate_diagram` stays for a whole file and also takes text, where only the checks that need a folder are skipped.
- **One thing it may do for the assistant is route edges.** `route_edges` draws edges only, right-angled through lanes between elements, and chooses each edge's connection points (the side facing the other element, in order, evenly spaced) unless told to keep them. It never moves an element, discards any route that still touches one, and is deterministic.
- **The tool makes every id.** Add operations take no `id`. A handle (`"as": "$name"`) names what an operation made for the rest of that call and is never written to the file, so an assistant can add and connect in one call without choosing ids, and a note's file name comes from an id the tool made, as a person's does.

## Alternatives considered
- **The folder route as the primary route, the server as a subset,** or **both carrying the same text.** The folder copy drifts from the app and can clash with the person's files, and an assistant that has both cannot tell which to follow.
- **The server mirrors every command, or only the server exists.** A pipeline has no server, so a check that lives only there is not enforceable.
- **A compact description the tool turns into a diagram** (like D2), or **helper functions for the assistant's own script.** The first hides the step-by-step loop and forces the tool to decide placement; the second still needs a shell.
- **Only the running app executes the operations.** Watching and undo come free, but the app must be open and the connection needs its own security design ([0169](0169-no-live-connection-between-the-mcp-server-and-the-app.md)).
- **A picture from the tool** (a bundled rasteriser or a browser): several MB, unlike the app, and not our code under the offline rule. A list works in every client.
- **An edit that only confirms, or repeats every problem in the diagram.** The first needs another call after every change; the second grows with the diagram.
- **Let the assistant choose ids, or keep handles across calls.** Both let it name things a person cannot.

## Consequences
- A second path for edits that must produce what the editor would: results are validated and written in the app's own serialisation, and the tests check both.
- A change to an operation or a check reaches both front doors at once; a change to a front door's file handling must be made in both, which the parity test catches.
- The size of the `build` page is kept to about a page by a test. It is advice for what the checks cannot judge, and moves into the checks when one can be written.
- Routed edges are right-angled, and a diagram that was curved becomes partly stepped; fewer crossings depend on the placement, which stays the assistant's.
- An assistant or script that sends `id` on an add operation is refused and must use a handle.
