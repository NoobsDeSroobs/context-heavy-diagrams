# 0039: Top menu bar — custom renderer bar, File/Edit/View split

## Status
Accepted

## Context
Epic 0049 was raised (2026-08-20), explicitly lower-urgency and unscoped, with three real open questions: native Electron menu vs. a custom renderer-built one, how multi-window Undo/Redo state would work under a native menu, and how this relates to epic 0048's left sidebar (raised in the same message, both epics implying a real information-architecture pass rather than two independent changes). Worked through with the user in conversation (2026-08-22), once the Canvas batch group finished and this became the first App-features epic.

## Decision
- **Custom in-renderer menu bar, not a native Electron menu.** I laid out the real tradeoff (native gives free accelerator handling and correct per-window state since this app is Windows/Linux only, no macOS; custom reuses every existing handler and keyboard-shortcut code unchanged, at the cost of building menu-bar keyboard navigation/hover behavior by hand) and recommended custom. The user's own reasoning matched: styling/UX flexibility later matters more than the native-menu conveniences, consistent with this app having no other native chrome anywhere.
- **Information architecture, decided for both epic 0049 and epic 0048 at once** (even though only 0049 is built now), per the user's explicit menu contents:
  - **File** (leftmost): New, Open, Save, Save As, Reload, Close. Export deferred (noted for later, not built).
  - **Edit**: Undo, Redo.
  - **View**: Required tags, Diagnostics, Layers, Settings.
  - **Highlights** — explicitly pulled out of this menu bar entirely, moved to its own floating popup next to Legend's on `fix/highlights-free-tags-and-toggle` (done first, no ADR of its own — see that branch's commit and [PROGRESS.md](../../PROGRESS.md) — so this epic didn't have to build a throwaway interim home for it).
- **No trailing "…" on View's panel-toggle items** (Required tags, Layers, Settings) — caught by the user as inconsistent leftovers from the old toolbar buttons. Ellipsis is reserved for items that open a dialog requiring further input before the action completes (Open…, Save As… correctly keep theirs); a panel toggle isn't that, matching Diagnostics, which never had one.
- **File → Close does not close the OS window.** My first implementation did (real IPC: `BrowserWindow.fromWebContents(event.sender)?.close()`, closing whichever window actually sent the request). The user corrected this directly: they want the *current window* reset to a blank diagram, not destroyed — this app's own convention (one `BrowserWindow` per diagram, ADR 0023) doesn't mean every window is disposable the way a browser tab is. Rebuilt to call `loadDiagramIntoCanvas(null, blankDiagram)` — the same full-state-reset function every other load path (initial mount, File → Open, Reload) already goes through — with the same lightweight `confirm()` guard `handleReload` already uses, skipped when the canvas is already empty (matching `handleOpen`'s existing "nothing to lose" window-reuse check). The now-unused `windows:close` IPC (main, preload, preload types) was removed rather than left as dead code.
- **A real interaction bug in the custom menu bar's hover-switch, caught by careful live testing (not the user this time — my own instrumented console logging after the Browser pane's automated clicks gave inconsistent, confusing results).** Native menu-bar convention expects hovering a sibling label to switch straight to it once one menu is open. Implemented as: `onMouseEnter` sets `openIndex` to the hovered menu whenever a *different* one is currently open. The bug: because a click gesture necessarily fires `mouseenter` before `click` (the cursor has to arrive before it can click), by the time the click handler ran, `openIndex` already reflected the hover's switch — so the click's own toggle logic ("clicking the already-open menu closes it") mistakenly closed the menu the user had just arrived at, rather than confirming it open. Fixed with a `hoverSwitchedToRef` that records *only* a genuine switch (arriving from a different index, not re-entering the same one), which the click handler checks first: if this click is landing on a menu that hover *just* switched to as part of the same gesture, keep it open instead of toggling.

## Alternatives considered
- **Native Electron menu.** See Decision — real, credible option (this app's `autoHideMenuBar: true` window config already scaffolds for one), rejected for the new bidirectional main↔renderer IPC every dynamic menu state (Undo/Redo enabled, Reload disabled, Diagnostics/Highlights counts) would need, when the custom path needed none of that.
- **Highlights staying in this menu's View section.** Rejected — moved out entirely before this epic started building, at the user's request; see `fix/highlights-free-tags-and-toggle`.
- **File → Close destroying the window** (my own first pass). Rejected by the user directly — see Decision.

## Consequences
- New `src/renderer/src/components/MenuBar.tsx` — generic `{ menus: MenuBarMenu[] }`, no knowledge of this app's specific actions; click-outside/Escape-to-close copied from `ContextMenu.tsx`'s existing pattern, including its "close before running the action" ordering.
- `Canvas.tsx`'s old `.toolbar` row loses every File/Edit/View button; keeps the saved-flash indicator, current-file-path display, and theme toggle, none of which fit the File/Edit/View split.
- `handleClose` (new) reuses `loadDiagramIntoCanvas` — no new state-reset logic to maintain separately.
- `windows:close` IPC added and then removed in the same epic — a real example of building the wrong thing first because the label ("Close") suggested a different action than the user actually wanted; worth remembering that a menu-item *label* alone doesn't fully specify behavior in an app with unusual window semantics.
- Epic 0048 (left sidebar) inherits this epic's information-architecture decision — when it's built, "what goes in the sidebar" is already answered (Highlights joins Legend there; nothing from this menu's File/Edit/View moves).
