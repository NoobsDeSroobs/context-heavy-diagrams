# 0025: Tag highlight rendering, persistence, and UI shape

## Status
Accepted

## Context
The tag-highlight work was scoped in an earlier session down to "tags are `data.metadata` entries ([ADR 0022](0022-unified-tag-and-metadata-system.md)); highlights are a separate `{key, value, color, enabled}` list", but deliberately left several technical questions open rather than guessed at: how a highlight actually renders, especially when more than one matches the same element; whether non-matching elements dim for contrast; whether the highlights UI is an in-app panel or a second window (newly a real option once multi-window landed); and whether highlight state persists in the file.

## Decision
- **Rendering is match-count-dependent, not one fixed style**: an element matching exactly **one** enabled highlight gets that highlight's color applied to its border/stroke, drawn slightly thicker — a live rendering override, never touching the element's actually-configured `style.stroke`/`style.strokeWidth`. An element matching **two or more** enabled highlights instead shows one small color chip per match (a corner/edge badge, exact placement to be settled during implementation, watching for collision with existing icon slots on Shape nodes) — no attempt at blending or picking a single "winning" border color once there's more than one match.
- **No dimming of non-matching elements in v1.** Simpler default, revisited only once there's a working highlight UI to actually judge it against.
- **In-app panel, not a second window** — same `UtilityDock` surface pattern as `RequiredTagsPanel`/`DiagnosticsPanel`. Highlights control how the diagram you're already looking at renders, so the control surface belongs alongside the canvas, not in a window you'd have to arrange next to it. (Multi-window having landed made a second window newly *possible*, but didn't make it the better fit here.)
- **Split persistence: the highlight catalog is saved, its on/off state is not.** `DiagramFile.highlights` is a new persisted array of `{ key, value, color }` definitions — "files are the database," so anyone who opens the file sees the same set of *available* highlights. Which of those happen to be toggled on right now is separate, volatile, in-memory-only state that always starts back at off when the diagram is (re)loaded — deliberately not stored anywhere in the file, so opening a diagram never surprises you with someone else's highlight overlays already active.

## Alternatives considered
- **One fixed rendering style regardless of match count** (either always-override or always-chips). Rejected in favor of the hybrid: always-override loses information the moment two highlights match the same element (which color wins?); always-chips is needlessly subtle for the overwhelmingly common single-match case, where a clean, prominent border recolor reads faster at a glance.
- **Dimming non-matching elements from the start.** Real value for the "trace a data path" use case, but adds a second rendering mode to design and maintain before there's a working highlight UI to judge it against — deferred, not rejected.
- **A second `BrowserWindow` for the highlights UI**, mirroring the multi-window model. Rejected — a highlights panel is a control surface for the diagram in front of you, not an independent document; keeping it in-app avoids the sync-with-the-focused-window problem a second window would introduce for no real benefit here.
- **Persisting enabled/disabled state too** (matching how `viewport` already persists). Considered, since it's the more literal reading of "files are the database," but the user's own call was explicit and deliberate: the *definitions* are shared/persisted, the *active view* is personal and transient, closer to "which panel is open" (session-only, like the diagnostics list) than to viewport position.

## Consequences
- Schema: `DiagramFile.highlights?: { key: string; value: JsonValue; color: string }[]` — no `enabled` field in the persisted shape at all, since that's exactly the state that's deliberately not saved. `docs/file-format.md` needs a new "Highlights" section when this lands, per this project's living-spec convention.
- Renderer-side, enabled state is a plain `Set`/array of currently-toggled highlight keys held in `Canvas.tsx` state, reset on every `loadDiagramIntoCanvas` — never written back, same treatment as `diagnostics` rather than `viewport`.
- Per-node/edge render logic needs to compute, on every relevant render, how many *enabled* highlights currently match that element's metadata — a small derived computation (not stored), most naturally alongside the existing per-node `metadata` rendering.
- The border-override rendering path reuses the same "live visual override without touching stored style" precedent this project already has for other transient rendering states (e.g. alignment guides, selection outlines) — it's not a new category of thing to reason about, just a new source of one.
- Deferred, not designed here: exact chip placement/sizing, and how an edge (not just a node) visually carries a chip when it has no "corner" the way a node does — left for implementation, to be judged against the actual running app rather than guessed at on paper.
