# 0028: Example gallery is organized as a shared landscape plus domain folders, not a flat list of independent diagrams

## Status
Accepted

## Context
The example diagram gallery was originally scoped as one independent illustrative diagram per checklist entry — a standalone GDPR data-flow diagram, a standalone business capability map, a standalone C4 context diagram, and so on, roughly 50 entries with no relationship to each other. That's a reasonable literal reading of "one example per diagram type," but it wastes the two features that make this tool's gallery worth building in the first place: linked-diagram navigation and tag-based highlight overlays. A pile of unrelated diagrams doesn't exercise either — every entry would be built from scratch with no reuse, which is also not how a real architecture practice actually produces its diagram set (the same underlying landscape gets viewed and sliced many ways, not redrawn per audience).

This was raised by the user (2026-08-20) as a refinement, noted but not yet acted on. Separately, the user asked (this session) for the gallery to be organized by logical domain (naming Compliance, Enterprise Architecture, Integrations, Business mapping as examples), which needed reconciling with the gallery's existing per-architect-discipline checklist.

## Decision
1. **A shared fictitious narrative setting (one modernization scenario, one fictional organization), not a single mechanically-derived master diagram.** Most gallery entries are full, independently-drawn diagrams that happen to be set in the same fictional organization/situation — roleplaying a specific persona in a specific moment (an enterprise architect surveying the estate, a technical architect designing the target platform, a task force presenting a rationalization view) — rather than being generated as "views" of one base file. See the 2026-08-20 amendment below; the original wording of this point was corrected the same day it was written.
2. **Compliance/regulatory dimensions are highlight overlays on an existing diagram, not standalone diagrams.** A GDPR view and an NIS2 view are tag-based highlight sets toggled on/off over a base diagram (see [docs/file-format.md](../file-format.md)'s Highlights section), matching how tag-based highlights and highlight groups already work. This wasn't possible when the gallery was first scoped — highlights didn't exist yet. This is the one place "don't build a separate flat diagram per variant" actually applies.
3. **The gallery folder (`examples/gallery/`) is organized by domain**, mirroring the gallery's per-architect-discipline structure (enterprise architecture, business, data, solution/technical, integration, security/compliance, infrastructure/cloud, process/flow) plus three folders outside that discipline list: `landscape/` (the shared spine), `limits-tests/` (deliberately poor structural fits, gathered together rather than left scattered across disciplines), `self-documentation/` (dogfooding, not fictional content), and `hello-world-tier/` (the simplest-possible tier, a companion to the complex landscape).
4. Not every discipline entry hangs off the landscape — several are genuinely standalone (Business Model Canvas, RACI matrix, the tool's own self-documentation) and stay as independent files in their domain folder.

## Alternatives considered
- **Flat `examples/gallery/` with one file per diagram type, no folders**: simplest to browse for a small set, but doesn't scale to ~50 entries and gives no signal about discipline coverage gaps, which is one of the gallery's explicit goals.
- **Keep every entry fully independent (the original gallery scoping)**: avoids any dependency ordering (nothing blocks on the landscape existing first), but wastes linked-diagram navigation and highlights — the two features most worth showcasing — and doesn't resemble how real architecture artifacts relate to each other. Rejected per the user's 2026-08-20 refinement.
- **Organize folders around collaboration mode (autonomous/AI-aided/manual) instead of domain**: would make the three-mode experiment the gallery also raised more visible, but scatters related diagram types across folders by *how* they were built rather than *what* they're about, which is the less useful axis for someone browsing the gallery. Rejected; collaboration mode is still worth tracking, just not as the folder axis — likely per-entry metadata later instead.
- **Standalone compliance diagrams (keep the original GDPR RoPA diagram as its own file, add NIS2 similarly)**: still valid as a keep-both option, and `security-compliance/`'s README keeps the RoPA-style diagram entry precisely because a standalone data-flow diagram and a landscape highlight overlay show different things. Not rejected outright — the overlay approach is additive, not a replacement for every standalone security/compliance entry.

## Consequences
- Build order now has a real dependency: the base landscape diagram needs to exist before it can be linked from or highlighted over by other entries. `landscape/README.md` calls this out.
- The domain-folder skeleton (`examples/gallery/*/README.md`) is a set of pointers only, not duplicated checklists — the gallery planning doc's task list stays the single source of truth for feasibility notes per entry, to avoid drift between two lists. The concrete Meridian Rail scenario and candidate diagram list (see amendment below) lives in **that planning doc**, not in `examples/gallery/README.md` — it's where the user reviews, comments on, and edits the list before anything is built, so it's the canonical copy.
- The gallery's open questions (collaboration mode per entry, whether to introduce a genuine "Ongoing" status) remain open; this ADR only resolves the structural question of how the gallery is organized on disk.

## Amendment (2026-08-20, same day)
The first pass at Decision point 1 read "one shared fictitious system landscape, with per-discipline views derived from it" — i.e. treat *every* discipline's entry as a mechanically-derived slice of one master diagram, the same mechanism as the compliance overlays. The user corrected this immediately: the "don't build a flat diagram per variant" instruction was specifically about compliance/regulatory dimensions (GDPR, NIS2, ...), not about discipline entries generally. Persona/scenario diagrams — an EA's view, a technical architect's C4 drill-down, a task force's rationalization deck — are still meant to be genuinely separate, deliberately roleplayed diagrams, not derived views of a single file. The corrected framing: **one shared fictional setting, many independently-real diagrams set within it**, with highlight overlays reserved for the narrower compliance-dimension case. At least ~10-15 diagrams are expected, deliberately varied in technique — flat, linked (multi-level drill-downs), single-highlight, grouped-highlight, and markdown/details-sublayer-heavy — not one shape repeated. Decision point 1 above has been edited in place to reflect this; this note exists so the correction itself isn't lost.

## Amendment 2 (2026-08-20, same day)
A second correction, on process rather than content: the candidate diagram list was first written into `examples/gallery/README.md`. The user's actual intended workflow is (1) the candidate list goes into the **gallery planning doc itself**, where they read/comment/edit it directly, (2) a subset gets agreed and built first to "cut our teeth" before attempting the rest, (3) only then does real building start. The list has been moved into that planning doc's own body (a new "Candidate diagram list" section, marked UNDER REVIEW) as the canonical copy; `examples/gallery/README.md` now just points there instead of holding its own copy.

## Amendment 3 (2026-08-20, same day)
A third correction, on scope: the 15-entry candidate list and its 12-folder skeleton were overkill for a first pass, with real duplication — an application-portfolio view isn't meaningfully different in technique from a capability heatmap; a cloud-architecture diagram isn't meaningfully different from a technical one. Separately, organizing by architect job title ("enterprise architect," "security architect") was the wrong axis — the tool aims to be useful to as many *people* as possible (a PO benefits from a business capability map without being a "business architect"), not to as many specialist *roles* as possible, so folders should be named for domains, not personas.

Both corrections applied together: folders consolidated from 12 to 5 (`landscape/`, `technical/`, `business/`, `organisation/`, `self-documentation/`); the candidate list trimmed from 15 to 10 entries. Dropped outright as redundant: application portfolio rationalization (same technique as the capability heatmap), the event-topology and cloud-deployment entries (folded into `technical/`, not meaningfully distinct from the C4 chain). Deferred, not dropped: passenger data lineage, the incident runbook, and a dedicated "limits-tests" category — a genuinely useful entry (the RACI matrix) can double as a limits-test without needing a diagram built solely to demonstrate one, which was the user's own example (a technology reference model / standards catalog "showcases by itself many aspects" rather than needing a separate thin entry).

This is expected to happen again as the list gets built out — this ADR records the amendment pattern, not a claim that round 1's scope is final.
