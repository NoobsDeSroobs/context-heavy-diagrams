# 0035: Layer order (z-index) control

## Status
Accepted

## Context
Epic 0043 was raised (2026-08-20) while reviewing the C4 gallery diagrams, wanting a way to see and control which canvas object renders on top of which — the user's own framing: "a view that lets me see each object and their z height." Primarily meant to fix container/shape stacking problems specifically. Left unscoped at capture time (persisted z-index vs. array-order, what the visibility view looks like, node/edge scope). Worked through with the user in conversation (2026-08-21).

## Decision
- **Scope: Shape/Text/Container nodes only. Edges are never independently ordered — their z-index is always derived, never stored**: `edge.z = (source.z + target.z) / 2`, computed at render time, same treatment `zIndexedNodes` already gives the container-tier/selection-tier compositing today. Edge-over-edge stacking at a shared connection point already has its own narrower fix (epic 0046); this epic doesn't touch it.
- **No hierarchy in v1** — a flat list, not a tree mirroring container nesting. A real hierarchical view (grouping shapes/containers together with locking) is explicitly future work, revisit once/if a grouping feature exists — noted here so it isn't redesigned from scratch then.
- **New persisted field: `DiagramNode.zIndex?: number` (integer).** Stored in React Flow's `data.zIndex`, deliberately not the top-level React Flow `Node.zIndex` prop — that prop is already a *computed* rendering value handed to React Flow (`zIndexedNodes` in `Canvas.tsx`). The persisted field feeds that computation directly: `renderedZ = data.zIndex + (selected ? SELECTION_BUMP : 0)`.
- **The existing "containers always render behind shapes" rule becomes a default, not a hard constraint.** Today it's an unconditional type check (`n.type === 'container' ? 0 : 2000`) with no escape hatch. Explicit user call: the *default arrangement* stays exactly as it looks today, but it's produced entirely by the **backfill's starting values**, not by any permanent type-based rule surviving into the render computation — drag a container above a shape in the panel and its `zIndex` genuinely exceeds that shape's, and it renders on top. No special-casing by node type anywhere after backfill; z-index alone decides.
- **Integers, sparse by default.** Every node absent this field (every file that predates this epic) gets one backfilled the first time it's loaded under this code — assigned with gaps (not consecutive integers), derived from current array order, so there's normally room to insert a dragged node between two neighbors without a collision. Same "seed once, reconcile on load" precedent this app already uses for required tags (ADR 0022). The backfill deliberately reproduces today's container/shape split as *starting values* (containers seeded from a low range, shapes/text from a much higher range, far enough apart that initial load can never accidentally cross them) — preserving each file's current visual stacking exactly on first open (ADR 0029), while leaving it fully overridable from that point on.
- **Reorder algorithm — average when there's room, cascade-shift when there isn't, extrapolate at a boundary.** Dragging a row to sit between two new neighbors (`low`, `high`):
  - Both neighbors exist, `high.zIndex - low.zIndex >= 2`: `newZ = low.zIndex + floor((high.zIndex - low.zIndex) / 2)`. Only the dragged node's value changes.
  - Both neighbors exist, `high.zIndex - low.zIndex <= 1` (no integer room — the user's own worked example: neighbors at 10 and 11, midpoint 11.5 rounds into an already-occupied slot): shift `high` and every node in the contiguous saturated block above it up by 1 until a gap opens, then place the dragged node in the freed slot. Bounded to the saturated block, not a full-diagram renumber.
  - Only one neighbor exists (dragging to the very front or back of the whole order): extrapolate a real gap from that single neighbor (not a bare `±1`), preserving headroom for future inserts at that new boundary.
- **UI: a flat list in the existing right-side dock** (Highlights/Required tags/Diagnostics family), sorted by z-index descending — top of list renders frontmost, matching the user's own worked example (dragging "Router" above "Server" gives it the higher value, 50 > 40). Each row: a one-letter type badge (S/C/T for Shape/Container/Text), the node's own `data.label`, and its z-index. Drag to reorder.
- **Clicking a row does *not* select the node — it's an "entity highlight," a new and different concept from the existing "property highlight."** The user's own distinction, worth keeping as the naming going forward: epic 0026/ADR 0025's existing `highlights` feature colors every entity that shares a given metadata *property* value — a **property highlight**. This epic needs the opposite shape: pointing at one specific, individual entity regardless of its properties — an **entity highlight**. Two different concepts that happen to share the English word "highlight"; kept clearly distinct in code naming (`entityHighlight...`, not reusing `highlight`/`Highlight` bare) to avoid the two being confused later. Explicitly not real React Flow selection either — the user's own reasoning: z-index "is not a property of the concept the shape encapsulates," so it shouldn't appear in the property panel at all, which selection would force.

## Alternatives considered
- **Array-order-as-layering** (reorder the underlying `nodes` array instead of a real field). Rejected — this format already has a *different*, existing array-order requirement (parent-before-children, for containers), and stacking a second, unrelated ordering concept onto the same array invites confusion for no real savings, given this format already adds fields additively.
- **Float z-index** instead of integers. Would sidestep the interpolation-collision case entirely (average of two distinct reals is always strictly between them), but the user specifically wants whole numbers in the list display and had already reasoned through the integer collision case and its fix — kept integers, added the cascade-shift fallback instead.
- **Full renumber on every drag** (reassign every node's z-index to 0,1,2,... after each reorder). Simpler code, no collision case to handle at all, but rewrites every node's z-index on every single drag — noisy for this format's git-diff-friendliness (`docs/file-format.md`'s Determinism section). Rejected in favor of the sparse/gap approach, which normally touches exactly one node per drag.
- **Reusing real node selection for the panel's click-to-locate behavior.** Rejected — see Decision; the user specifically didn't want the z-index value anywhere near the property panel.
- **A hierarchy/tree view mirroring container nesting**, prompted by a Slides.com comparison. Explicitly deferred, not rejected — revisit once/if a grouping-and-locking feature exists to hang it off of.

## Consequences
- Schema (`src/shared/diagram.ts`): `DiagramNode.zIndex?: number`, serialized alongside `position`/`size`/`rotation` — additive, no version bump (same convention as every other optional field added since v1).
- `docs/file-format.md` needs a new field entry once this lands.
- `Canvas.tsx`'s existing `zIndexedNodes` computation **loses its type-based tier check entirely** — `n.type === 'container' ? 0 : 2000` goes away, replaced by `data.zIndex + (selected ? SELECTION_BUMP : 0)` for every node regardless of type. The container/shape split becomes purely a property of the backfilled *starting values*, not of ongoing render logic. `orderedEdges`-style logic needs a matching computed z, averaged from each edge's two endpoints' effective z-index, passed into React Flow the same "computed at render time, never persisted" way.
- Load-time backfill lives alongside the other defensive reconciliation this app already does on open (`runSync` for required tags) — assigns sparse integer values from current array order, containers seeded from a low range and shapes/text from a much higher one (far enough apart to never accidentally cross on initial load), wherever `zIndex` is absent.
- New node creation (`addShapeNode`/`addTextNode`/`addContainerNode`) seeds a `zIndex` above the current maximum, so a freshly added node appears on top by default — matching today's implicit "later in the array paints on top" behavior for same-tier siblings.
- New UI: a `LayerPanel`-equivalent component in the existing `UtilityDock`, each row showing a one-letter type badge (S/C/T), label, and z-index; plus a small piece of session-only **entity-highlight** state in `Canvas.tsx`/`DiagramContext` (`entityHighlightNodeId` or similar — deliberately not sharing the `highlight`/`Highlight` name with epic 0026's unrelated *property*-highlight feature), rendered as a visual indicator on the corresponding node. Not reusing `selected` or `HighlightDefinition`.
- Deferred, not designed here: the future grouping/locking feature and the hierarchical panel view it would enable (see Decision).
