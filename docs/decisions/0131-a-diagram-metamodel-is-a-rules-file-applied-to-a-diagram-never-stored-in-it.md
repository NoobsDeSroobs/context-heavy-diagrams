# 0131: A diagram metamodel is a rules file applied to a diagram, never stored in it

## Status
Accepted. Merges 0131 (conformance profiles), 0143 (the extension writes metamodels), 0144 (a profile is called a diagram metamodel) and 0145 (a draft is checked and compared without being written) into one decision, reworded 2026-11-26. It keeps the lowest number of the group. It builds on [0109](0109-stale-edit-check-for-every-ai-write-path.md), [0110](0110-claude-desktop-extension.md) and [0138](0138-assistants-build-diagrams-like-a-person-through-one-implementation-behind-the-cli-and-the-mcp-server.md).

## Context
A diagram can claim an architectural style (hexagonal, data-flow) and break its rules without anyone noticing. The tool already knows what the rules need: tags, containers, directed edges and named edge readings. What was missing is a way to write the rules down once and check any diagram against them, in the app and in CI. An assistant that drafts a diagram also wants to judge it before it exists on disk, and to help the person write the rules.

## Decision
- **A diagram metamodel is a JSON file applied to a diagram, never stored in one.** It is `<name>.chdmeta`, the vocabulary of element and relation kinds and the constraints on combining them, which gives value only as a whole, so a check applies exactly one. It has `edges`, `roles` and `rules`; the format is in [metamodel-format.md](../metamodel-format.md), written to stand on its own so others can author metamodels or build checkers. It changes no `.chd` format: a diagram only needs tags and an edge direction set. The word is "metamodel", not "profile", which suggests a variant or a preference.
- **The arrow meaning is declared, never guessed.** `edges.meaning` is `dependsOn`, `flowsTo` or `irrelevant`, and `edges.presence` is `required`, `optional` or `forbidden`. Both start at `none` in the template, which is invalid, so a metamodel cannot be used until its author has chosen. A diagram states its meaning with an edge direction set whose name equals the meaning, spaces removed and lower-cased, and the rules are evaluated in that set's orientation. A diagram without the set, or with two that match, has a violation; it is never silently checked in the wrong reading.
- **Roles are exact matches** on type, tag and containment, not the substring matching of the search box: compared text is lower-cased and stripped of whitespace, then must be equal, so a rule about `role=port` does not catch `support`. An element that matches no role is ignored.
- **Five rule kinds** (`forbiddenEdge`, `requiredEdge`, `containment`, `requiredProperty`, `maxElements`) and three severities: `error` breaks a rule of the style and fails the check, `warning` a best practice, `info` is worth knowing. Only errors fail. A key the format does not know is an error, so a typo cannot disable a rule, and a metamodel that fails validation checks nothing.
- **The check is a pure function in `src/shared`,** used by the Diagnostics panel and by `chd check <file> --metamodel <file-or-built-in-name>`, whose exit code is non-zero on an error; `chd check` is the authority for CI. The app ships a template and two metamodels (hexagonal, data-flow). The person's own live in a metamodels folder, a preference, which can be a folder in a repository. Sharing rules that live outside every repository is left to the team, since the command line reads only local paths and stays offline ([0113](0113-enforced-offline-behaviour.md)).
- **A draft can be checked and compared without being written.** `check_diagram` takes a path or text, and `diff_diagrams` takes each version as a path or as text; on the command line `-` is standard input. A revision still compares a file on disk with git, so a text version is compared with another version. Notes are not compared when a version is text (a note is a file beside a diagram, and a text version has no folder), and the paths inside a text diagram are never read. These tools are read-only.
- **The extension can write a metamodel, and only that beyond diagrams and notes.** A name ending in `.chdmeta` can be created and updated, validated with the reader `chd check` uses before it is written and refused with the same message if invalid; the stale-edit check applies and updates stay behind the person's opt-in ([0109](0109-stale-edit-check-for-every-ai-write-path.md)). A metamodel is validated on its own by `chd validate <file>.chdmeta` and `validate_metamodel`, and `validate_diagram` stays for diagrams: a well-formed diagram and a diagram that follows a metamodel are different questions and can disagree.
- **There is no guard against an assistant fitting a metamodel to its own diagram.** The server cannot tell sessions apart; what a green check is worth is for the person to judge, who owns the rules and the result.
- **The older names are read and never written:** `.chdprofile.json` files, the `profileVersion` key (an error beside `metamodelVersion`), `--profile` and the saved `profilesFolder` setting. The `--json` key `profileName` is now `metamodelName`; a script reading it changes.

## Alternatives considered
- **Rules as test code** (ArchUnit style): flexible, but asks people to write JavaScript and shows nothing in the app. **The search query language for roles:** substring-based and cannot say "inside a container with this role".
- **Edge meaning as a default, flipped afterwards.** Many styles do not define what an arrow means, and a default gives confidently wrong results. **One combined field for meaning and presence:** "required but any meaning" and "forbidden" are about presence and would be mixed up with it.
- **The metamodel embedded in the `.chd` file.** Every diagram would carry its own copy of shared house rules, and the file format would change.
- **Other names:** archetype (suggests a template a diagram only approximates), ruleset (rules from several sources can combine, these cannot), style (clashes with the Style panel), viewpoint (an ISO 42010 compliance term the tool does not aim at).
- **Write the draft under another name first,** or a hidden temporary file: leaves files in the person's folder for a read-only question.
- **Allow every `.json` file to be written,** or **refuse diagram edits after a metamodel was written in the same session:** the first makes any configuration file writable, the second is porous because sessions are invisible to the server.

## Consequences
- A diagram's author must prepare it (tags, the named edge set) for each metamodel; the metamodel's `description` says how. An existing set called "Data flow" has to be renamed "Flows To" before the data-flow metamodel applies.
- Files, scripts and CI jobs written under the old names keep working. A `.chdmeta` gets no JSON highlighting from an editor or from GitHub unless it is associated with JSON.
- Writing a metamodel gives an assistant no more reach than writing a diagram: it is data, never run.
- A draft's own structural problems (a dangling edge, a duplicate id) are found by `validate_diagram` or the write-time validation, not by `check_diagram` and `diff_diagrams`.
- Linked diagrams, levels (C4), layer ordering, waivers and layering several metamodels are not covered.
