# 0033: Diagram legend entry model, persistence, and placement

## Status
Accepted

## Context
Epic 0037 was raised (2026-08-20) while reviewing the C4 context gallery example, which uses fill color and a dashed edge to carry meaning with nothing in the diagram explaining the convention — but deliberately left unscoped: what a legend entry actually is, how it relates to the existing highlight catalog (epic 0026/ADR 0025), where it renders, and whether its visibility persists. Worked through with the user in conversation (2026-08-21) rather than guessed at up front.

## Decision
- **Three entry kinds, one flat type**: `LegendEntry = { id, kind: 'line' | 'icon' | 'shape', label, color? }`, `kind` discriminating which extra fields apply — `line` adds `lineStyle`/`startMarker`/`endMarker` (same fields/vocabulary as `EdgeStyle`), `icon` adds an `IconRef`, `shape` adds nothing beyond `color`. One flat interface with optional fields, not a discriminated union of three interfaces — consistent with this schema's existing style (`NodeStyle`/`EdgeStyle` are also flat optional bags, not unions).
- **`color` applies to `line` and `shape` kinds only, never `icon`.** This app's icons (epic 0007) are fixed bundled/custom image assets — inline SVG or raster — not authored as single-color glyphs meant to be tinted. A colored background chip behind an icon was considered and rejected: the user's own reasoning for rejecting a colored *box* as the plain-color swatch shape (readers could assume "only red boxes are relevant" rather than "red means X" in the abstract) applies identically to a colored chip behind an icon.
- **The `shape` kind renders as a circle/dot, not a box.** A rectangle risks being read as "this convention only applies to rectangular shapes"; a plain colored circle reads as "this color means X," full stop — no shape claim attached. This is the entry kind for a color-only convention not tied to any specific line or icon (e.g. "red = GDPR-sensitive data").
- **A `line` entry reuses the existing named line-style preset picker** (`StylePicker.tsx`/`builtinLineStylePresets.ts`, ADR 0010) rather than a parallel picker — same underlying `lineStyle`/`startMarker`/`endMarker` vocabulary as edges already use, so a legend entry can describe an edge convention exactly.
- **Legend entries are manually authored, not derived from the highlights catalog.** A highlight is a metadata key/value → color mapping; a legend entry (e.g. "dashed = planned data flow") often has no backing metadata at all. Considered auto-populating from highlights or unifying the two catalogs; rejected because it would force every legend entry to be metadata-backed, which most aren't. No cross-reference between the two catalogs exists — a highlight and a legend entry that happen to describe the same convention are independent, possibly-duplicate data, same tradeoff already accepted for other independent catalogs in this file format.
- **Persistence is split, same shape as highlights (ADR 0025): the catalog is saved, the shown/hidden toggle is not.** `DiagramFile.legend?: LegendEntry[]` is new persisted diagram content — it describes how the diagram is meant to be read, so it travels with the file. Whether the legend panel is currently open is session-local UI state, default closed, reset on every load — the user's own framing: "it must be stored in the file... but the toggle itself should be session specific."
- **Placement: a `ControlButton` inside React Flow's own bottom-left `<Controls>`** (the zoom/fit/lock-interactivity widget, `Canvas.tsx`), not the existing right-side `UtilityDock` shell that Highlights/Required tags/Diagnostics/Settings all share. The panel itself is a small floating box anchored next to `<Controls>`, not a full-height dock panel — explicitly requested by the user as "a small in-canvas pane," distinct from every other panel in this app.

## Alternatives considered
- **Three separate typed catalogs** (one each for color/line-style/icon legends) instead of one flat `LegendEntry` type. Rejected — no behavior actually differs per kind beyond which optional fields are populated, so three catalogs would just be three near-identical lists to render and persist.
- **Auto-populating the legend from the highlights catalog.** Rejected (see Decision) — couples two conceptually different catalogs and can't express non-metadata conventions like line styles at all.
- **Colored box for the plain-color swatch kind.** Rejected per the user's own reasoning above; circle chosen instead.
- **Colored background chip for `icon`-kind entries.** Rejected for the same reason as the box.
- **Persisting the panel's shown/hidden state in the file.** Rejected — explicit user call, kept consistent with every other panel-open state in this app (session-local, epic 0034's diagnostics precedent, ADR 0025's highlights precedent).
- **Reusing the right-side `UtilityDock` shell** (same surface as Highlights/Required tags/Diagnostics/Settings). Rejected per explicit user direction — a legend is meant to sit near the diagram content itself, next to the corner controls, not in the side dock alongside diagram-management panels.

## Consequences
- Schema: `src/shared/diagram.ts` gains `LegendEntryKind`, `LegendEntry`, and `DiagramFile.legend?: LegendEntry[]`; `serializeDiagram` orders it directly after `highlights`. `docs/file-format.md` needs a new "Legend" section.
- Renderer-side, `legend` follows the exact same state-management shape as `highlights` in `Canvas.tsx`: a plain `useState<LegendEntry[]>([])`, loaded from `diagram.legend ?? []` on open, written back into the saved `DiagramFile` — no undo/redo integration (same as highlights, which also isn't part of the node/edge undo stack). The shown/hidden toggle is a separate `useState(false)`, never read from or written to the file.
- New UI surface: a `LegendPanel` component (new small floating-box CSS shell, not `UtilityDock`), a `ControlButton` added to `<Controls>` to toggle it, and an "add entry" flow that opens `StylePicker` for `line` kind, the existing icon picker for `icon` kind, or a plain color input for `shape` kind, plus a label text field — modeled on `HighlightsPanel`'s existing add-row pattern (button → inline picker → row appended to list, ✕ to remove).
- Row rendering needs a small swatch preview per kind: a short `<svg>` line with the picked `lineStyle`/markers and `color` (reusing `markerUrl`/`DASH_ARRAY` from `LabeledEdge.tsx`) for `line`, the icon itself (`IconSlotView`) for `icon`, a plain colored circle for `shape`.
- Deferred, not designed here: exact swatch pixel sizing/spacing, and whether a `line` entry's marker fields default to the plain-line preset or start unset — left for implementation.
