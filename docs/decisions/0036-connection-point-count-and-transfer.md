# 0036: Connection point counts and edge-transfer-on-remove

## Status
Accepted

## Context
This was raised (2026-08-20) after the gallery testing surfaced that click-to-add connection points is imprecise, but left deliberately unscoped — the real open questions were where the count control lives, what regenerating does to points that already have edges attached, and the exact spacing convention. Worked through with the user in conversation (2026-08-21).

My first pass proposed a conservative "block the whole regenerate if any point on that side has an edge attached," reusing the existing single-point-removal guard. The user pushed back with a concrete rule set instead — deterministic edge-transfer on both grow and shrink — and judged it simpler to implement and far more useful (their words: "without this smart capability then 80% of the QoL it brings is lost"). Worked through below, and it did turn out simpler: no blocking branch, no alert, no partial-failure state to explain.

## Decision
- **Clockwise ordering per side drives every rule.** Offset is left-to-right on top/bottom and top-to-bottom on left/right (existing `nearestConnectionPoint` convention); walking top → right → bottom → left clockwise means ascending offset on top/right, descending on bottom/left.
- **Growing a side's count**: existing points keep their id (and therefore their edges) and just slide to new evenly-spaced offsets; new empty points are appended at the clockwise end. `offset_i = (i+1)/(N+1)` for `i` in `0..N-1` — N=1 lands at 0.5, matching the always-present default point's own centered position. **Correction (2026-08-21, same day, caught by the user before merge):** the first implementation applied this formula to `N = customCount` alone, ignoring that the default already sits at a fixed 0.5. Every *even* total (odd `customCount`) put one custom point exactly on top of the default; every odd total visually clustered the two nearest points around it. Fixed by spacing `N = totalCount` slots (default included) and dropping whichever slot the default already covers — exact for odd totals (a true middle element at 0.5), and for even totals (which have no exact-0.5 slot — an evenly-spaced symmetric set only has a true middle element when its count is odd, a property of the geometry, not the formula) a deterministic tie-break drops the lower/earlier of the two slots straddling center. See `evenOffsetsExcludingDefault` in `connectionPoints.ts`. Even totals keep one small, unavoidable asymmetric gap next to the default as a result — a single custom point can never sit symmetrically around a fixed center it doesn't overlap.
- **Shrinking a side's count**: the clockwise-most point is removed, its edges transfer to the new clockwise-most survivor (the point "behind it," i.e. counter-clockwise), repeated one point at a time until the target count is reached; the survivors are then re-spaced evenly. If the count drops enough that no custom point remains on that side, edges transfer to that side's own always-present default handle (id `"top"`/`"right"`/`"bottom"`/`"left"`) — the natural fallback, since that handle *is* what the offset-0.5 case degenerates to anyway.
- **Manual right-click "remove connection point" now transfers instead of blocking.** This reverses the original connection-point rule (which alerted "disconnect it first" and refused to remove a wired point, [ADR 0021](0021-connection-point-removal-blocked.md)). New rule: edges transfer to the counter-clockwise neighbor, except removing the clockwise-*first* point on a side transfers forward to the point that becomes the new first instead. ~~Deliberately does not re-space the points left behind~~ — **reversed in Revision 3 below**, survivors are now re-spaced evenly too, same as the bulk regenerate.
- ~~Manual right-click "add point here" needed no change.~~ **Reversed in Revision 3 below** — it now re-spaces the whole side too.
- **The property panel's count field shows a total that includes the always-present default point**, not just the custom-point count — the user's own framing: "if I write 4 under Left, then you have to subtract one to only add 3." Internally the default stays exactly what it was before this change (fixed, non-removable, handle id equal to the side name) — the field is `customCount + 1` on read and `max(0, input - 1)` on write. Full unification of the default into the same managed pool was considered and explicitly rejected (see Alternatives) as much larger in scope than what the user was actually asking for.
- **New global setting**: `maxConnectionPointsPerSide` (default 12) in `preferences.ts`/`PreferencesPanel.tsx`, the user's own requirement ("upper limit... changeable in the settings pane") — applies to every diagram, not persisted per-file, same treatment as the edge lead-in setting.
- **Commits on blur/Enter, not per-keystroke.** Every other numeric field in the property panel applies on every keystroke since it's just a style patch; this one is structural (can delete points and transfer edges), so applying "1" then "12" while someone types "12" would be actively destructive. `ConnectionPointFields` tracks a pending value in a ref between `onChange` and `onSessionEnd`.

## Revision 2 (2026-08-21, same day, before merge): the default point is no longer a special, fixed case at all
The Revision 1 fix (dropping the nearest-to-0.5 slot from an N-way sequence) was still built on the original premise that the default point's position is permanently fixed at 0.5 — the user rejected that premise directly: "That will not work unless you manage to change the position of the default point." They were right, and for two compounding reasons, not one:

1. **Symmetry is mathematically unreachable while the default can't move.** A set of evenly-spaced points symmetric about a center has a true middle element only when the count is odd — for any even total, keeping one point permanently pinned at the exact center necessarily leaves the layout looking lopsided, no matter which formula computes the others. There is no tie-break that fixes this; the fix has to let the "default" point move.
2. **A second, independent bug**, also traced to the same root cause: reconnecting an edge's endpoint by dragging it from one point to another on a 3-point side sometimes landed on the wrong point. The user's own diagnosis: the default point was invisible to the app's own ordering — it lived entirely outside the array the clockwise-sort/transfer math reasoned about (rendered separately, hardcoded, in `ConnectionHandles.tsx`), while still being a real, clickable, connectable point on screen. Any code computing "the Nth point on this side" or "this point's clockwise neighbor" was silently working from an incomplete picture.

**New decision: the default point is now an ordinary member of the same per-side array as everything else — the only thing that survives from the old model is its fixed *id*, and only until the side is first touched.** A side with no stored `connectionPoints` entries still implicitly has exactly one point, centered, using the side's own name as its id (`"top"`/`"right"`/`"bottom"`/`"left"`) — the same id every file predating custom connection-point counts already references from its edges. That's now purely a synthesis (`effectivePointsForSide`/`effectiveConnectionPoints` in `connectionPoints.ts`), computed on demand, never assumed to be fixed at 0.5 once a side is actually regenerated. The moment a side's count changes (or a point on it is added/removed), its *entire* point set — including that synthesized entry — is written back for real and behaves like any other point from then on: freely repositioned by the same evenly-spaced formula, freely removable (down to a floor of 1 per side, the only remaining special rule), no different from a `cp-N` point except by name.

Concretely:
- `evenOffsetsExcludingDefault` (Revision 1) is gone. Plain `evenOffsets(N)` applies to the side's *entire* point count now — no more "drop the nearest slot," no more asymmetry to explain away, because there's no longer a fixed point that can't participate in the spacing.
- `setSideCustomPointCount` takes the side's whole target count directly (`targetTotalCount`) instead of a custom-only count the caller had to derive by subtracting 1.
- `removeCustomPointWithTransfer` resolves the point being removed, and its clockwise neighbors, through the same effective-points view — so a right-click removal (or a shrink) computes the correct neighbor regardless of whether that neighbor happens to be the side's originally-implicit point or an explicit `cp-N` one. It now also refuses (rather than silently succeeding) when it would leave a side with zero points — the one guarantee that used to come for free from the default being unremovable.
- `ConnectionHandles.tsx` collapses from "4 hardcoded handles + a customPoints map" to one map over `effectiveConnectionPoints` — removing the dual render path that let the inconsistency exist in the first place.
- The property panel's count field no longer needs the "+1 to show, -1 to store" conversion — the number shown is the number stored.

## Revision 3 (2026-08-22): manual add/remove also re-space the whole side
After Revision 2 landed, the user tested the manual right-click tools directly and reported both as "broken": removing a point "left the remaining points where they were" (no re-spacing), and adding one didn't re-space either. Both were deliberate design choices going in — the reasoning at the time (see the now-struck-through bullets above) was that the manual tools are a *precision* instrument, meant to stay hands-off of every point except the one being touched, distinct from the bulk regenerate's evenly-spaced convenience. In practice, that distinction didn't hold up: a side that's just had a point manually added or removed looking visibly uneven read as broken, not as "precisely preserved."

**New decision: every structural operation on a side — bulk count-field regenerate, manual add, manual remove — always re-spaces every point left on that side afterward.** The precision/convenience split survives only in *how a point's ordinal position is chosen*, not in whether the result gets evenly spaced:
- **Manual add** (`insertConnectionPointAt`): the click position is only precise enough to say *where in clockwise order* the new point belongs — before/after which existing points. That determines an insertion index; the actual offset assigned to every point on the side (the new one and all the old ones) comes from `respaceClockwise`, same formula as the bulk generator. Existing points keep their ids (and edges), they just slide to their new evenly-spaced offset, exactly like growing via the count field already did.
- **Manual remove** (`removeCustomPointWithTransfer`): unchanged in *which* point gets removed and *where* its edges transfer (counter-clockwise neighbor, or forward if it was the clockwise-first point) — only the survivors' offsets change, now re-spaced the same way a shrink via the count field already re-spaces its own survivors.

A new shared primitive, `respaceClockwise(points)`, takes a list already in the desired clockwise order (whatever was inserted or removed already reflected) and assigns each entry the matching evenly-spaced offset — the bulk generator, insert, and remove all end with a call to it now, rather than each computing offsets its own way.

## Revision 4 (2026-08-22): respaceClockwise ignored bottom/left's reversed direction
`evenOffsets(N)` always returns ascending raw-offset values. `respaceClockwise` (introduced in Revision 3) zipped those straight onto a clockwise-sorted points array by index — correct on top/right, where clockwise order *is* ascending raw offset, but wrong on bottom/left, where clockwise order is *descending* raw offset (`CLOCKWISE_ASCENDING`). The clockwise-first point on those two sides was silently getting the smallest raw offset instead of the largest, mirroring the whole side. The user caught it from two angles at once — the property panel's growth direction looked reversed on bottom/left, and right-click add/remove placed points on the visually opposite side of the click — and correctly identified it as one inconsistency, not two: "either both must treat the bottom and left sides to not work counter clockwise... or both have to properly work clockwise. Now the panel and the right-click menu use one method each." In fact both *were* going through the same `respaceClockwise` — the bug just manifested differently depending on which operation (grow vs. click-to-insert) was driving it.

**Fix**: `respaceClockwise` now takes `side` and reverses the offsets array before zipping when that side is a `CLOCKWISE_ASCENDING: false` side (bottom/left), so "array index 0" reliably means "clockwise-first" for every side, not just the two where clockwise happens to match ascending raw offset.

## Revision 5 (2026-08-22): manual add didn't respect the max-per-side setting
The user set `maxConnectionPointsPerSide` to 5, grew a side to 5 via the property panel (correctly capped — the field's own `max` prop), then used right-click "Add connection point here" and got a 6th anyway. The setting was only ever wired into the property panel's `NumberField`; `insertConnectionPointAt` (Revision 3) and the `useConnectionPointMenu` hook that calls it had no path to the setting at all and no limit check of their own.

**Fix**: `maxConnectionPointsPerSide` is now threaded through `DiagramContext` (same pattern as `edgeStraightSegmentLength`, ADR 0032 — a global setting node components need without reaching into `Canvas.tsx`'s own state). `insertConnectionPointAt` takes it as a parameter and refuses (returns `undefined`) once the target side is already at the limit; `useConnectionPointMenu` shows an alert in that case, and checks *before* calling `pushSnapshot()` so a refused add doesn't leave a spurious empty entry in undo history.

## Alternatives considered
- **Block regenerate/removal whenever a point has an edge attached** (my initial proposal, reusing the existing single-point-removal guard as-is). Simple and consistent with prior behavior, but loses most of the feature's value — the single most common case ("I have 3 wired points, I want a 4th") would require manually disconnecting first. Rejected by the user for exactly this reason.
- **Unifying the always-present default point into the same count-managed pool per side.** Originally rejected here as much larger in scope than the behavioral gain justified, given the 4 default handles' ids are referenced directly by existing saved diagrams' edges. **Reversed in Revision 2 above** — the user identified that keeping the default fixed wasn't just extra scope avoided, it was the actual root cause of two real bugs (unreachable symmetry, wrong-neighbor transfers), so the "migration story" concern turned out to be smaller than feared: the fixed ids are preserved as a pure on-demand synthesis for untouched sides, not a stored migration, so old files still load and resolve identically.
- **Preserving "evenly spread" as a continuously-enforced invariant** rather than a generation-time computation. Rejected already when the feature was first scoped — points stay freely draggable/removable after generation, so "evenly spread" only needs to be true the moment a count changes, not maintained afterward.

## Consequences
- **File-format semantics change (Revision 2), though the schema shape doesn't**: `connectionPoints` is still `{ id, side, offset }[]`, but it can now legitimately contain an entry with id `"top"`/`"right"`/`"bottom"`/`"left"` and a non-0.5 offset, and a side's *only* point can be one of those ids. `docs/file-format.md` needs an update reflecting "every side always has ≥1 point; absent means exactly one, centered, using the side name as its id" in place of the old "4 always-present, un-removable, never-listed defaults" language.
- `src/renderer/src/nodes/connectionPoints.ts` gains the pure algorithm (`setSideCustomPointCount`, `removeCustomPointWithTransfer`, `insertConnectionPointAt`, `respaceClockwise`, `reassignConnectionPointHandles`, `effectivePointsForSide`/`effectiveConnectionPoints`/`connectionPointCountForSide`, clockwise sort) — no React, testable independent of the hook/component layer.
- `useConnectionPointMenu`'s remove handler loses its `hasEdge`/`alert` branch entirely, and gains a much narrower one (refuse removing a side's last point). Its add handler now calls `insertConnectionPointAt` instead of appending the raw clicked point.
- `ConnectionHandles.tsx` renders from `effectiveConnectionPoints` alone — no more hardcoded always-4 JSX, so every point (including a side's originally-implicit one) gets the same style override and the same context menu.
- `Canvas.tsx` gains `setConnectionPointCount`, the bulk entry point used by the property panel — reads current node state directly (not from inside a `setNodes` updater) so the edge-reassignment map is available synchronously for the following `setEdges` call. Takes the side's whole target count directly now, no default/custom conversion.
- `preferences.ts`: new `maxConnectionPointsPerSide` field, default 12.
