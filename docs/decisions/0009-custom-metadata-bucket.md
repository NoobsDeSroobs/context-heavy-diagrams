# 0009: Custom metadata bucket, separate from standard node/edge/diagram data

## Status
Accepted

## Context
Discussing how well this tool supports being driven both graphically and textually/programmatically (e.g. a script or an AI generating most of a diagram's structure, then a person opening it to visually arrange shapes and connections), investigation into the actual code — not just the docs — found a real gap: `src/shared/diagram.ts`'s `serializeDiagram` and `src/renderer/src/Canvas.tsx`'s `toDiagramFile`/`fromDiagramFile` all reconstruct every node/edge/file object from a fixed whitelist of known fields, on both save *and* load. Any field outside that whitelist is silently dropped the moment a file is opened in the app — before any edit happens, not just on the next save.

The documented schema fields (position, size, rotation, label, icon refs, detail refs, links) already round-trip perfectly — that part of the architecture works exactly as intended (see [ADR 0005](0005-diagram-identity-and-linking.md), [file-format.md](../file-format.md)). The gap is specifically about a generator or external tool wanting to attach its *own* bookkeeping data — a stable external ID, a "generated by" marker, a source-system reference, anything the app itself has no opinion on — and have it survive being opened and edited in the GUI.

The requirement, as stated: two distinct kinds of metadata should exist per element — **standard metadata** the tool itself understands and manages (the existing `data.label`/`icons`/`details`/`linkedDiagram` fields), and a **custom metadata bucket** — a free-form dict — that is both viewable/editable from the GUI *and* through the raw file, on nodes, edges, and the diagram as a whole, and that must survive storage and loading.

## Decision
Add a `metadata` field, typed as an arbitrary JSON value dict, to `DiagramNode`, `DiagramEdge`, and `DiagramFile` in `src/shared/diagram.ts`:

```ts
export type JsonValue = string | number | boolean | null | JsonValue[] | { [key: string]: JsonValue }
```

- **Nodes**: `metadata?: Record<string, JsonValue>` as a **top-level sibling to `data`** (not nested inside it) — `{ id, type, position, size, rotation, data: {...}, metadata: {...} }`. This is the most faithful realization of "two distinct kinds of metadata": standard fields live in `data`, the custom bucket lives structurally apart from it, not folded into the same object. (React Flow's own `Node` type has no such extension point — everything custom has to live inside its `data` bag in memory — so the in-memory shape will be `node.data.metadata`, translated to/from the file's top-level `metadata` by the same `toDiagramFile`/`fromDiagramFile` layer that already does this kind of shape translation for `size`↔`width`/`height`.)
- **Edges**: `metadata?: Record<string, JsonValue>` as a new top-level field, sibling to the existing flat `label`/`source`/`target` fields — edges have no `data` wrapper in the file schema today and don't need one introduced just for this; the schema evolves additively, per its own Versioning section, not by restructuring what's already shipped.
- **Diagram**: `metadata?: Record<string, JsonValue>` as a new top-level field, sibling to `version`/`viewport`/`nodes`/`edges`.

Because `metadata` becomes a genuinely known, whitelisted field — not an unrecognized one — it gets carried through explicitly at every step (`parseDiagram`, `fromDiagramFile`, `toDiagramFile`, `serializeDiagram`), the same way `details` and `linkedDiagram` already are. This resolves the round-trip requirement directly, without needing to preserve arbitrary unrecognized fields in general (see Alternatives).

**Determinism**: metadata dict keys are sorted alphabetically (recursively, at every nesting level) during `serializeDiagram`, consistent with this format's existing fixed-key-order philosophy for clean git diffs (see file-format.md's Determinism section). This means metadata may come back in a different key order than it was typed or generated in — a deliberate tradeoff, see Consequences.

**Validation**: `parseDiagram` rejects a `metadata` value that isn't a plain object (an array, string, or primitive at that position) with the same clear-error style already used for a malformed file — but validates no deeper than that. What's inside the bucket is never the app's business.

**GUI editing**: a raw JSON textarea, not a structured key-value table editor, matching the existing Markdown details editor's own philosophy (the brief explicitly states internal Markdown editing doesn't need to be a rich WYSIWYG editor — most substantial edits happen in an external editor). Concretely:
- **Nodes**: extends the existing details panel (`DetailsPanel.tsx`) with a second tab/section alongside the current Notes edit/preview toggle — a "Metadata" tab holding the JSON textarea. Reuses the existing right-click → "See details" entry point rather than adding a new one.
- **Edges**: edges have no context menu today at all (`LabeledEdge.tsx` only has an inline double-click-to-edit label). This decision adds their first one, reusing the same generic `ContextMenu` component nodes already use, with an "Edit metadata…" item opening a small popup (same fixed-positioned-popup pattern as the icon picker).
- **Diagram-level**: a new toolbar button ("Diagram metadata…") opening the same style of popup, editing the top-level `metadata`.
- Invalid JSON in any of these blocks that save (a clear error, not a silent drop or a corrupted file) — matching the project's established "never a silent failure" handling already applied to missing links and failed opens/saves.

## Alternatives considered
- **Preserve all unrecognized fields opaquely**, end to end, rather than defining one sanctioned bucket: strictly more flexible (anything a generator puts anywhere survives), but a much bigger blast radius — every parse/serialize/translate path would need to carry an "everything else" bag through untouched, it's undocumented/undiscoverable (a reader of file-format.md wouldn't know such fields are even meaningful to preserve), and it blurs exactly the "two distinct kinds of metadata" separation that was the actual requirement. Rejected in favor of one well-defined, documented extension point.
- **Structured key-value table editor** instead of a raw JSON textarea: friendlier for non-technical editing and avoids requiring JSON literacy, but real UI work and awkward for representing nested values (a stated requirement — "a simple dict" implies arbitrary structure, not just flat key→string pairs). Deferred, not rejected outright — it can be added later as a different editor UI over the same `metadata` field without any schema change, so it's a pure GUI-layer decision to revisit if raw JSON proves too friction-heavy in practice.

## Consequences
- Editing metadata in-app requires basic JSON literacy (matching bracket/quote syntax) — consistent with how Markdown details already work, but worth knowing going in as a real usability cost for non-technical users, not a hidden one.
- Metadata keys get reordered alphabetically on every save, regardless of how they were typed or generated — favors clean diffs over preserving authoring order. If this turns out to matter for a specific workflow (e.g. a generator wants its own semantically meaningful key order preserved), that's a legitimate reason to revisit this specific choice later; it isn't load-bearing for the rest of the decision.
- Edges gain their first-ever context menu as a side effect — a new interaction surface other future edge features can reuse, not just this one.
- `docs/file-format.md` needs a real `metadata` entry once this ships, matching the existing per-field table format.
- Anything genuinely unrecognized (not `metadata`, not one of the existing known fields) still gets silently dropped on open, same as before this decision — that's intended, not a residual gap: the custom-extensibility need is now met by the sanctioned `metadata` bucket, not by making the whole format permissive.
