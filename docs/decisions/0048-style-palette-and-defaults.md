# 0048: Custom style palette and per-type default styles

## Status
Accepted

## Context
Raised while reviewing the styling panel, this bundles two related asks: (1) reusable user/org-owned colors and fonts surfaced in the existing color fields and font dropdown, and (2) a configurable default style for freshly created Shape/Container/Text elements (edges already have this via [ADR 0045](0045-default-edge-style-setting.md)'s `defaultEdgeStyle`). Several real open questions were left deliberately unresolved (multiple palettes vs. one, import merge-vs-replace, where editing happens, exact surface area, how defaults get set/scoped, naming) — this ADR resolves them before implementation.

## Decision
- **One active palette, not several merged ones.** Importing a file replaces the current working copy outright. No concrete need for "Personal + Acme Corp side by side" was raised — YAGNI, and it avoids real complexity (grouping, ordering, cross-palette collisions) with no driving use case.
- **Storage: `AppPreferences.stylePalette`/`AppPreferences.defaultStyles`, in `localStorage`** — consistent with every other global setting today (`preferences.ts`), not a new per-app-user file mechanism. Moving settings off `localStorage` is its own separate, deferred concern ([ADR 0053](0053-os-conventional-settings-storage.md)); this doesn't get ahead of it.
- **Sharing stays file-based** (already decided in the epic doc): explicit Export/Import buttons, real native save/open dialogs via new `stylePalette:exportToFile`/`stylePalette:importFromFile` IPC (`src/main/stylePalette.ts`) — not a browser-download/file-input hack, matching every other file operation in this app (`diagram.ts`, `icons.ts`, `links.ts`).
- **Import confirmation is in-panel, not `window.confirm()`** — only asked when there's actually something to lose (the current palette is non-empty); applies directly otherwise. Deliberately avoids the native dialog after the confirm()-breaks-`<select>` bug found live in the allowed-values editor work (see [docs/known-issues.md](../known-issues.md)) — this panel doesn't currently have a `<select>` of its own, but the precedent is followed anyway rather than risking it.
- **Editing happens directly in a new dock panel** (`StylePalettePanel.tsx`, same fixed right-dock family as `RequiredTagsPanel`/`PreferencesPanel`, ADR 0013) — add/edit/remove colors and fonts as rows, reusing the exact list-editor shape the `AllowedValuesEditor` established (buttonless add via a trailing blank row, remove button, same CSS classes reused directly). No separate "inline add from an already-picked color" affordance for v1 — a second entry point for the same action, not requested, skippable if it turns out tedious.
- **Scope: colors and fonts only.** Line-style/marker presets stay [ADR 0010](0010-named-searchable-style-presets.md)'s separate, tool-curated-only catalog — that ADR explicitly flagged needing to be precise about this exact distinction when the time came; the time has come, and the answer is "not bundled into this epic."
- **Palette colors surface inside the existing `ColorField` component directly** (a new optional `paletteColors` prop — a row of clickable swatches, shown whenever non-empty) — covers the property panel and the Fill…/Border… context-menu popup automatically, since both already share that one component (exactly matching the epic's own stated surface-area goal). Font palette entries are appended to the existing `FONT_FAMILY_OPTIONS` list for the Family dropdown, both node and edge variants.
- **Defaults: one style per element type, no named presets/themes to switch between.** Shape/Container/Text default styles live in `settings.defaultStyles`; Edge continues to use the existing `defaultEdgeStyle` ([ADR 0045](0045-default-edge-style-setting.md)) rather than a duplicate parallel field.
- **No second style-editing UI for defaults.** Style an element exactly how you want using the property panel that already exists, then a new "Set as default style" button (shown only when exactly one node of that type is selected — a style is only well-defined for one element, not a multi-selection) copies its current style into the setting. Building a full parallel style editor inside `StylePalettePanel` for four element types would have roughly doubled this epic's size for no real gain over reusing the panel that already does this job.
- **Explicit action only — no "last used becomes default."** Matches the user's own framing when the epic was first raised, and avoids a surprise where styling one element for a one-off purpose silently changes what every future element looks like.
- **Container keeps its existing hardcoded fallback** (`{ fill: 'var(--ev-c-gray-1)', fillOpacity: 20 }`) until a real default is set — the user's own choice then wins outright, not merged with the hardcoded one.
- **Naming: "Style Palette."** Simple and accurate — covers personal use as well as a company's shared set, not overly branded-sounding.

## Addendum (same day): canvas background color
Raised by the user after the initial build shipped: a diagram's canvas background was entirely React Flow's own light/dark theme default — no app-level override existed. Confirmed as a real gap (`grep` found zero background-color CSS for `.react-flow`/`Background` anywhere in this app) and added as a small extension of the same settings:
- **`AppPreferences.canvasBackgroundColor?: string`** — global, not per-diagram (same reasoning as the rest of this palette: an org-wide default, not diagram content). Optional; absent means today's existing theme-based background, unchanged.
- **Applied via the CSS custom property `--xy-background-color`, not the literal `backgroundColor`.** First attempt used `style={{ backgroundColor: ... }}` and visibly did nothing — the user caught it immediately. Root cause, found by reading React Flow's actual source (`node_modules/@xyflow/react/dist/style.css`): the real paint comes from `<Background>`'s own absolutely-positioned SVG (`.react-flow__background`, covering the whole pane), whose CSS rule is `background-color: var(--xy-background-color-props, var(--xy-background-color, var(--xy-background-color-default)))` — it reads a CSS custom property, not the plain property, and inherits it down the DOM tree from whichever ancestor sets it. Fixed to `style={{ '--xy-background-color': settings.canvasBackgroundColor } as React.CSSProperties}`. `undefined` is still a no-op, so this falls back to React Flow's own default exactly like before whenever unset.
- **Reuses `ColorField` directly** (already supports an unset/clear state, unlike `PreferencesPanel`'s plain swatch inputs which always need a concrete value) — a "Canvas background" section in `StylePalettePanel`.

## Alternatives considered
- **Multiple simultaneously active palettes.** Rejected — see Decision.
- **A second full style-editing UI inside the palette panel for defaults.** Rejected — reusing the property panel via a "Set as default" action is far smaller and there's no real workflow gap it leaves open.
- **`window.confirm()` for the import-replace decision.** Rejected on the strength of the allowed-values editor's live-tested bug — see Decision.
- **Extending `StylePicker`'s named-preset catalog with a custom/company section**, bundling line-style presets into this same palette concept. Rejected for v1 — real, separable scope, not requested by the epic's own stated goal.

## Consequences
- `preferences.ts`: new `PaletteColor` type, `AppPreferences.stylePalette`/`AppPreferences.defaultStyles`.
- `src/main/stylePalette.ts` (new), registered in `src/main/index.ts`; preload gains `exportStylePalette`/`importStylePalette`.
- `panels/fields.tsx`'s `ColorField` gains an optional `paletteColors` prop; `.property-field` CSS gains `flex-wrap` so the new swatch row drops onto its own line.
- `DiagramContext` gains `paletteColors`/`paletteFonts`, read by `PropertyPanel.tsx`'s `NodeStyleFields`/`EdgeFields` and by `ColorPickerPopup.tsx` directly.
- `PropertyPanel.tsx`/`DiagramDock.tsx`: new `onSetDefaultStyle` prop threaded through; a "Set as default style" button shown for a single-node shape/container/text selection.
- `Canvas.tsx`: `addShapeNode`/`addContainerNode`/`addTextNode` seed `data.style` from `settings.defaultStyles.<type>` (falls back to Container's existing hardcoded look when unset); new `StylePalettePanel` joins the existing 5-way mutually-exclusive dock family (View menu, Escape-to-close, closes/closed-by the other five).
- New `StylePalettePanel.tsx` reuses `RequiredTagsPanel`'s CSS classes (`.required-tags-panel`, `.required-tag-value-row`, `.required-tag-value-confirm`, etc.) directly rather than duplicating them.
- No `.chd` schema change — `NodeStyle`/`EdgeStyle` are unchanged; this only affects what a freshly created element's `style` field gets seeded with, and what quick-pick options a color/font field offers.
