# 0195: Stories are steps over the visibility sets

## Status
Accepted (2026-11-21), and kept up to date as the design is tried.
Builds on: [0194](0194-visibility-sets-hide-and-show-parts-of-a-diagram.md) (the rule that decides what is visible, and sets as session state), [0118](0118-saved-with-version-marker.md) (what an older application does with a field it does not know), [0109](0109-stale-edit-check-for-every-ai-write-path.md).
Supersedes: none
Superseded by: none

## Context
Visibility sets let one diagram hold several pictures, but a person tells a diagram in order: "this is what we have today", then "this is how it is connected", then "this is how we could fix it". Toggling sets by hand while talking is slow and easy to get wrong, and the order lives only in the presenter's head.

## Decision
- **A story is an ordered list of steps over the visibility sets.** A new optional diagram-level field `stories`, a list of `{ id, name, steps }`, left out of the file when empty. The id is opaque and unique among the stories and never shown; the name is free text, unique ignoring case (the editor refuses a duplicate, the file does not enforce it). A diagram can hold several stories, so one diagram can serve more than one audience. The order of the stories and of the steps is kept.
- **A step is an ordered list of actions**: `{ actions? }`, left out when empty, each action `{ action, set }`. The actions of this version are `show` and `hide`, each naming a visibility set by id. They run in order, so the last action on a set wins and nothing needs a rule about a set named twice. The shape is open: a later action (grow, highlight, emphasise) is a new `action` value with its own fields, with no change to the file's structure. A reader ignores an action it does not know and keeps its fields, so a file moves between versions without losing what it holds, and the validator warns about one.
- **Steps accumulate.** The state at step n is the state before step 1 with steps 1 to n applied in order. Step 0 is the state before step 1: every set the story names is hidden and every other set is shown. The state depends only on the step number, so going back or jumping to a step is a replay from step 0, and inserting a step does not mean redoing the later ones. One pure function in `src/shared/visibility/story.ts` gives the hidden sets at a step; the result goes through the rule of 0194, so nothing else decides whether an element is visible. An id that is not in the catalogue is ignored and kept, and Diagnostics lists it.
- **"All sets" is a meta target.** In place of a set, an action can be about all sets: every set the catalogue holds when the step runs, so one added later is included. "Hide All sets, then Show Today" leaves only Today whatever else the diagram has, and "Show All sets" ends a story with everything. A story that uses it names every set, so it starts with all of them hidden. Elements in no set stay visible, as ever ([0194](0194-visibility-sets-hide-and-show-parts-of-a-diagram.md)). In the file it is the reserved value `*` in `set`; set ids are generated, so it cannot collide, and a reader that does not know it ignores the action like any id no set holds. The editor lists it above the real sets, apart from them, so it cannot be taken for a set. The edit operations take `all: true` instead of a set name, since a set may be named anything.
- **The step being shown is session state.** It is not saved and is not an edit. Stories are content and are saved.
- **Changing between steps fades.** In the presenter an element that becomes visible fades in and one that becomes hidden fades out, over a short fixed time, and not at all when the system asks for reduced motion. The editor's own changes (picking a step, ticking a set) are immediate.
- **The presenter view** is the editor window with its docks and toolbar out of the way, over the same canvas. Entering sets the step to 0 and leaves the view of the canvas where it is; next and previous change the step, and the view stays where the presenter put it. Nothing in the view can be selected, moved or edited. Leaving returns the sets to what was hidden before (or, with the panel open, to the step the presenter ended on). The first version has no captions.
- **Writing a story** happens in a panel in the right-hand dock, opened from a play button in the toolbar: a list of steps, like the slide list of a presentation program, and for the selected step its actions, one row each, each a pair of choices: the action (Show, Hide) and then what it is about (a set). A new step has no actions, and an action is added with a button. The actions of a step can be reordered and removed. The action comes first because it reads as a sentence and because what the second choice offers depends on the action. Selecting a step shows its state on the canvas, so the person sees what the audience will, but only while the panel is open: closing it puts the sets back as they were before the preview, and opening it previews the step again; a step in the list says what it does, and its tooltip says which sets are shown after it. The panel can add, duplicate, move and delete steps, and, at the bottom, make a story from the sets in the order of the catalogue, one step per set, each showing the next set and hiding nothing.
- **Exports draw what is shown** ([0194](0194-visibility-sets-hide-and-show-parts-of-a-diagram.md)), so while a step is on screen they draw that step. An export of a whole story is not part of the first version.
- **Format.** An additive change, a minor version. An older application ignores `stories`; its newer-file warning applies on save ([0118](0118-saved-with-version-marker.md)). `docs/file-format.md` and the schema change together.
- **Writers.** The command line and the extension read and write stories through edit operations with the stale-edit check ([0109](0109-stale-edit-check-for-every-ai-write-path.md)): `add_story`, `rename_story`, `remove_story`, `add_story_step`, `remove_story_step`, `add_story_action` and `remove_story_action`; a story and a set are named by their names. The inspect answer lists the stories and their steps by set name, and the file validator warns about two stories with one name and about an id that no set holds.

## Alternatives considered
- **A snapshot of the shown sets at each step.** Rejected: every step would repeat the whole state, so adding a set or inserting a step means editing every later step, and what a step *does* ("today gives way to proposed") is lost.
- **A step as two lists, `show` and `hide`.** Used first. Rejected once more actions were wanted: every new action would need a new list, and the editor drew a row per set in every step, which does not scale to a diagram with many sets.
- **A number on each element, shown up to a step.** Rejected for the reason in 0194: it only adds elements.
- **One story per diagram.** Rejected: a second audience would need a second diagram, or a format change later.
- **The view fits what is shown at each step.** Rejected for now: it moves under the presenter's hands and fights a manual zoom. It can be added later as an option without changing the file.
- **Captions on steps.** Left out of the first version; a `caption` field can be added to a step later without breaking older readers.

## Consequences
- Stories refer to sets by id, so renaming a set changes no story. Deleting a set leaves its id in the steps, ignored, so a story keeps working and nothing is rewritten behind the person's back.
- A later action that is not about visibility (it lasts one step, say, instead of carrying on) needs the state function to return more than the hidden sets. That is decided when the first such action is added.
- The editor and the presenter drive the same session state as the sets panel (which sets are hidden), so the panel shows what a step did, and the person can toggle a set by hand while editing. The presenter is the one place that locks this.
