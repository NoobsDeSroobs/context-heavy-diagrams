A second real bug surfaced while testing the new landscape's dense edge convergences: grabbing a selected edge's reconnect handle at a shared connection point could still grab a different edge's handle instead — the exact scenario epic 0046 (2026-08-21) already tried to fix, recurring. This time root-caused properly (live `console.log` instrumentation, then reading React Flow's actual source) rather than re-guessing: each edge renders in its own independently-z-indexed `<svg>` wrapper, and React Flow's selection-based z-index elevation (`elevateEdgesOnSelect`) defaults to off and was never enabled here — so selection had *zero* effect on which edge won a shared point the whole time, and epic 0046's original DOM-reordering fix only appeared to work in its one test case by coincidence. Real fix: `zIndexedEdges` now adds a large explicit z-index boost to whichever edge is actually selected. Full writeup in [docs/known-issues.md](docs/known-issues.md).

Small follow-on improvement once that landed: a selected edge's stroke now swaps to a dedicated, user-configurable highlight color (`selectedEdgeHighlightColor` in Settings, on by default with a vivid magenta unlikely to collide with normal diagram colors) — the width bump alone still wasn't enough to easily track a selected edge through a busy diagram. Overrides both the edge's own explicit color and any highlight-match color; edges only, not nodes. See [ADR 0042](docs/decisions/0042-selected-edge-highlight-color-setting.md).

Also logged, not fixed: a connection-point drag once snapped onto the wrong side's point after a count change, unreproduced (see [docs/known-issues.md](docs/known-issues.md) — off-by-one hypothesis checked out structurally but not in the actual data path, more likely a `updateNodeInternals` timing race), and a real UX gap in the required-tags panel's allowed-values editor (one cramped comma-separated text field) — [epic 0055](docs/planning/epics/0055-required-tags-allowed-values-list-editor.md), not designed yet.

Another real feature landed from the same testing session: **per-element lock** (shapes/containers/text, not edges) — blocks drag/resize/rotate/accidental-delete via the canvas while keeping the element selectable and every property-panel edit (style, tags, connection points) still allowed. A "Locked" checkbox in the property panel (tri-state for mixed selections), independent per element (no container-to-child cascade — multi-select applies uniformly to everything currently selected, though), and a small grey lock glyph centered on the element's own top edge when locked. New `DiagramNode.locked` field, additive per ADR 0029's standing rule. Full design reasoning (including why transform-only turned out to be *less* work than full read-only, not more) in [ADR 0043](docs/decisions/0043-per-element-lock.md).
